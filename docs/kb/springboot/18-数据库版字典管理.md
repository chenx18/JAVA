## 2. 先看一个完整业务示例

后台管理系统里通常有一个菜单：

```text
系统管理 / 字典管理
```

管理员可以新增一个字典类型：

```text
字典名称：部门状态
字典类型：department_status
状态：启用
```

然后维护这个字典类型下面的字典数据：

```text
标签：禁用，值：0，排序：1
标签：启用，值：1，排序：2
```

前端页面需要部门状态下拉框时，请求：

```http
GET /dict/data/type/department_status
```

返回：

```json
{
  "code": 200,
  "message": "success",
  "data": [
    { "label": "禁用", "value": "0" },
    { "label": "启用", "value": "1" }
  ]
}
```

部门列表接口仍然只返回：

```json
{
  "id": 1,
  "name": "研发部",
  "status": 1
}
```

前端用字典翻译：

```text
1 -> 启用
0 -> 禁用
```

这就是数据库版字典的核心。

## 3. enum 字典和数据库字典的区别

### 3.1 enum 字典

例如：

```java
public enum DepartmentStatusEnum {
  DISABLED(0, "Disabled"),
  ENABLED(1, "Enabled");
}
```

适合：

```text
选项少
变化少
和代码逻辑强相关
```

例如：

```text
启用/禁用
是否删除
是否默认
```

### 3.2 数据库字典

字典项存在数据库里，后台页面可以维护。

适合：

```text
选项多
经常变化
需要后台配置
需要排序、颜色、备注
不想每次修改都发版
```

例如：

```text
学历
民族
设备类型
告警类型
业务分类
```

---

## 4. 两张核心表

数据库字典通常拆成两张表：

```text
dict_type
dict_data
```

### 4.1 dict_type：字典类型表

它描述“这是一类什么字典”。

示例：

```text
id: 1
dict_name: 部门状态
dict_type: department_status
status: 1
```

### 4.2 dict_data：字典数据表

它描述“这个字典类型下面有哪些选项”。

示例：

```text
id: 1
dict_type: department_status
dict_label: 禁用
dict_value: 0
sort: 1
status: 1
```

```text
id: 2
dict_type: department_status
dict_label: 启用
dict_value: 1
sort: 2
status: 1
```

关系：

```text
dict_type.dict_type
  ↓
dict_data.dict_type
```

注意：

```text
这里通常不是用 id 关联，而是用 dict_type 字符串关联
```

例如：

```text
department_status
```

## 5. 建表示例

字典类型表：

```sql
create table dict_type (
  id int primary key auto_increment,
  dict_name varchar(100) not null,
  dict_type varchar(100) not null unique,
  status int not null default 1,
  remark varchar(255)
);
```

字典数据表：

```sql
create table dict_data (
  id int primary key auto_increment,
  dict_type varchar(100) not null,
  dict_label varchar(100) not null,
  dict_value varchar(100) not null,
  sort int not null default 0,
  status int not null default 1,
  remark varchar(255)
);
```

为什么 `dict_value` 用字符串？

```text
有些字典值是数字：0 / 1
有些字典值是字符串：male / female
为了通用，很多系统会把 dict_value 设计成 varchar
```

## 6. 实际后台常见接口

字典类型接口：

```text
GET    /dict/types           查询字典类型列表
GET    /dict/types/{id}      查询字典类型详情
POST   /dict/types           新增字典类型
PUT    /dict/types/{id}      修改字典类型
DELETE /dict/types/{id}      删除字典类型
```

字典数据接口：

```text
GET    /dict/data            查询字典数据列表
GET    /dict/data/{id}       查询字典数据详情
POST   /dict/data            新增字典数据
PUT    /dict/data/{id}       修改字典数据
DELETE /dict/data/{id}       删除字典数据
```

给前端业务页面使用的接口：

```text
GET /dict/data/type/{dictType}
```

例如：

```http
GET /dict/data/type/department_status
```

返回当前类型下启用的字典选项。


此处目标是先理解数据库字典如何服务前端展示。

## 8. Entity 设计

字典类型：

```java
public class DictType {

  private Integer id;

  private String dictName;

  private String dictType;

  private Integer status;

  private String remark;
}
```

字典数据：

```java
public class DictData {

  private Integer id;

  private String dictType;

  private String dictLabel;

  private String dictValue;

  private Integer sort;

  private Integer status;

  private String remark;
}
```

给前端返回的选项：

```java
public class DictOptionResponse {

  private String label;

  private String value;
}
```

注意：

```text
数据库 dict_value 是 varchar
所以这里 value 推荐先用 String
```

如果示例项目已有 `Integer value` 版本，也可以后面再调整。

---

## 9. Mapper 查询字典选项

Mapper 接口：

```java
List<DictOptionResponse> findOptionsByType(@Param("dictType") String dictType);
```

XML：

```xml
<select id="findOptionsByType" resultType="com.example.week4.common.response.DictOptionResponse">
  select
    dict_label as label,
    dict_value as value
  from dict_data
  where dict_type = #{dictType}
    and status = 1
  order by sort asc, id asc
</select>
```

这里不需要查 `dict_type` 表也能返回选项。

但实际开发中可能会先判断字典类型是否存在或是否启用。

## 10. Service 逻辑

```java
public List<DictOptionResponse> getOptionsByType(String dictType) {
  if (dictType == null || dictType.isBlank()) {
    throw new IllegalArgumentException("dictType cannot be blank");
  }

  return mapper.findOptionsByType(dictType);
}
```

这个方法只是查询，不需要事务。

## 11. Controller 逻辑

```java
@GetMapping("/data/type/{dictType}")
public ApiResponse<List<DictOptionResponse>> getDictOptionsByType(
    @PathVariable String dictType) {

}
```

## 12. 知识盲区：为什么 dict_value 常用字符串

因为字典值不一定都是数字。

例如：

```text
部门状态：0 / 1
性别：male / female
设备类型：camera / sensor
颜色：red / blue
```

如果 `dict_value` 设计成 int，字符串类型字典就不好存。

所以很多系统会设计成：

```sql
dict_value varchar(100)
```

前端拿到字符串后，再根据业务需要转换。

---

## 13. 知识盲区：字典类型为什么用字符串关联

字典数据表里存：

```text
dict_type = department_status
```

而不是：

```text
dict_type_id = 1
```

原因：

```text
前端和后端业务代码更容易通过 department_status 获取字典
数据迁移时不依赖数据库自增 id
接口语义更清楚
```

所以请求通常是：

```http
GET /dict/data/type/department_status
```

而不是：

```http
GET /dict/data/type/1
```

---

## 14. 知识盲区：字典通常需要缓存

字典数据访问频率高，变化频率低。

所以真实项目经常会缓存：

```text
dict:department_status -> [{label,value}, ...]
```

常见缓存位置：

```text
前端内存
浏览器本地缓存
后端内存
Redis
```

如果后台修改了字典，就需要：

```text
刷新缓存
```

RuoYi 这类项目通常会有“刷新字典缓存”的功能。

此处先不实现缓存，但需要理解它为什么存在。

---

## 15. 知识盲区：不是所有状态都应该进字典表

有些状态强依赖代码逻辑，比如：

```text
是否删除
账号是否锁定
流程状态
支付状态
```

这些状态如果随意在后台改，可能影响业务逻辑。

这种更适合：

```text
enum 管理
```

有些只是展示选项，比如：

```text
学历
设备类型
业务分类
```

更适合：

```text
数据库字典表
```

## 17. 面试小题

如果面试问：

> 后台系统里的字典管理怎么设计？

可以这样回答：

```text
一般会拆成字典类型表和字典数据表。
字典类型表保存 dict_type、dict_name 等信息，字典数据表保存 dict_label、dict_value、sort、status 等选项。
业务接口通常只返回状态 code，前端通过 dictType 请求字典数据，再把 code 翻译成 label。
如果字典项固定且和代码逻辑强相关，可以用 enum；如果字典项需要后台维护，就用数据库字典表。
字典访问频率高、变化少，所以实际项目中通常会做缓存，并提供刷新缓存功能。
```
