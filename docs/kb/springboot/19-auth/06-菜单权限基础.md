# 菜单权限基础

菜单权限用于解决“不同角色登录后，前端显示不同菜单和按钮”的问题。

角色决定用户属于哪一类人，菜单权限决定这类人能看到哪些页面、能操作哪些按钮。

---

## 1. 本节目录 / 学习目标

本节按以下路线学习：

```text
用户 User
  ↓
角色 Role
  ↓
菜单 Menu
  ↓
角色菜单关系 RoleMenu
  ↓
根据 userId 查询菜单权限
  ↓
后端返回菜单树
  ↓
前端根据菜单树生成路由和按钮权限
```

学完本节应能掌握：

- 菜单权限和角色权限的区别
- `sys_menu` 和 `sys_role_menu` 如何设计
- 如何根据用户 id 查询菜单
- 为什么菜单通常要返回树结构
- 前端如何使用菜单权限

---

## 2. 菜单权限解决什么问题

同一个系统，不同用户看到的内容可能不同：

```text
管理员：用户管理、角色管理、菜单管理、部门管理
普通用户：个人中心、个人数据
审计员：日志查询、报表查看
```

推荐做法：

```text
后端根据当前用户权限返回菜单列表
前端根据返回结果渲染菜单和路由
```

---

## 3. 关系模型

```text
User 用户
  ↓
UserRole 用户角色关系
  ↓
Role 角色
  ↓
RoleMenu 角色菜单关系
  ↓
Menu 菜单 / 按钮权限
```

可以理解为：

```text
用户拥有什么角色
  ↓
角色拥有哪些菜单
  ↓
用户最终能看到哪些菜单
```

## 4. 数据库表设计

菜单表：

```sql
create table sys_menu (
  id int primary key auto_increment,
  parent_id int not null default 0,
  menu_name varchar(50) not null,
  menu_type varchar(10) not null,
  path varchar(100),
  component varchar(100),
  perms varchar(100),
  order_num int default 0,
  visible int default 1,
  status int default 1
);
```

角色菜单关系表：

```sql
create table sys_role_menu (
  role_id int not null,
  menu_id int not null,
  primary key (role_id, menu_id)
);
```

菜单类型常见约定：

```text
M：目录
C：菜单
F：按钮
```

测试数据：


## 7. MenuMapper.xml

```xml
<select id="findMenusByUserId" resultMap="MenuResultMap">
  select distinct m.id, m.parent_id, m.menu_name, m.menu_type,
         m.path, m.component, m.perms, m.order_num, m.visible, m.status
  from sys_menu m
  inner join sys_role_menu rm on m.id = rm.menu_id
  inner join sys_user_role ur on rm.role_id = ur.role_id
  inner join sys_role r on ur.role_id = r.id
  where ur.user_id = #{userId}
    and m.status = 1
    and r.status = 1
  order by m.parent_id, m.order_num, m.id
</select>

<select id="findPermsByUserId" resultType="string">
  select distinct m.perms
  from sys_menu m
  inner join sys_role_menu rm on m.id = rm.menu_id
  inner join sys_user_role ur on rm.role_id = ur.role_id
  inner join sys_role r on ur.role_id = r.id
  where ur.user_id = #{userId}
    and m.status = 1
    and r.status = 1
    and m.perms is not null
    and m.perms != ''
</select>
```

核心关联：

```text
sys_user_role -> sys_role -> sys_role_menu -> sys_menu
```

## 8. MenuService 组装树

```java
public List<Menu> getMenuTreeByUserId(Integer userId) {
  List<Menu> menus = menuMapper.findMenusByUserId(userId);
  return buildTree(menus);
}

private List<Menu> buildTree(List<Menu> menus) {
  Map<Integer, Menu> menuMap = menus.stream()
      .collect(Collectors.toMap(Menu::getId, menu -> menu));

  List<Menu> roots = new ArrayList<>();

  for (Menu menu : menus) {
    if (menu.getParentId() == null || menu.getParentId() == 0) {
      roots.add(menu);
    } else {
      Menu parent = menuMap.get(menu.getParentId());
      if (parent != null) {
        parent.getChildren().add(menu);
      }
    }
  }

  return roots;
}
```

### 9.1 实际开发中的路由和权限接口

后台管理系统登录成功后，前端通常会调用菜单路由接口：

```http
GET /user/menus
Authorization: Bearer JWT
```

或者使用更接近后台框架习惯的命名：

```http
GET /getRouters
```

它的作用是返回当前用户能访问的菜单树 / 路由树。

另外，前端还可能单独调用权限标识接口：

```http
GET /user/perms
Authorization: Bearer JWT
```

它的作用是返回按钮权限列表，例如：

```json
[
  "system:user:list",
  "system:user:add",
  "system:user:delete"
]
```

实际登录后初始化流程通常是：

```text
POST /user/login
  ↓
保存 token
  ↓
GET /user/info
  ↓
保存用户信息、角色、权限
  ↓
GET /user/menus 或 /getRouters
  ↓
动态生成侧边栏和路由
```

不一定每个项目都把 `info`、`menus`、`perms` 拆成三个接口，也可以合并返回。学习阶段建议先拆开，方便理解每个接口的职责。

前端使用：

```text
菜单树：生成侧边栏和路由
perms：控制按钮显示
```

## 10. 后端仍然要校验权限

前端隐藏按钮不等于接口安全。

用户仍然可能直接调用接口：

```http
DELETE /user/delete/1
```

所以敏感接口仍然需要后端权限校验。

---

## 11. 实际开发注意点

- 菜单权限通常依赖角色权限。
- 菜单表既可以表示页面菜单，也可以表示按钮权限。
- `perms` 用于按钮级权限，不一定对应可见菜单。
- 后端不能只依赖前端隐藏按钮。
- 菜单权限数据可以缓存，但角色或菜单变化后要考虑刷新。

## 12. 面试小题

### 12.1 菜单权限和角色权限有什么区别？

答：角色权限说明用户属于哪个角色；菜单权限说明角色能访问哪些菜单和按钮。

### 12.2 为什么后端也要做按钮权限校验？

答：前端隐藏按钮不能阻止用户直接调用接口，真正的权限控制必须在后端完成。

### 12.3 菜单为什么要返回树结构？

答：菜单通常有父子层级，树结构更适合前端渲染侧边栏、路由和多级菜单。

## 13. 小结

```text
当前用户 userId
  ↓
查询用户角色
  ↓
查询角色菜单
  ↓
得到菜单列表
  ↓
组装菜单树
  ↓
返回给前端渲染
```

完成本节后，系统就可以根据不同用户返回不同菜单。
