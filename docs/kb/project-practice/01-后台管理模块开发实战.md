# 后台管理模块开发实战

## 1. 实战路线清单

这一篇是后台管理模块的实战模板，用于指导新业务模块开发。

实战路线：

```text
1. 先看一个后台模块最终由哪些文件组成
2. 再理解每一层的职责边界
3. 再按接口链路梳理新增、修改、删除、分页、批量删除
4. 再理解事务、日志、enum、字典分别放在哪里
5. 最后给一个 User 模块实战模板
```

实战目标：

> 以后写新模块时，不是从零想，而是按模块模板往里填。

## 2. 一个后台模块通常包含哪些文件

以 Department 模块为例，一个较完整的后台模块可能包含：

```text
project/system
  controller
    DepartmentController.java

  service
    DepartmentService.java

  mapper
    DepartmentMapper.java
    DepartmentLogMapper.java

  domain
    Department.java
    DepartmentLog.java

    request
      DepartmentCreateRequest.java
      DepartmentUpdateRequest.java
      DepartmentQueryRequest.java

    vo
      DepartmentResponse.java
      DepartmentDetailResponse.java
```

MyBatis XML：

```text
resources/mapper/system
  DepartmentMapper.xml
  DepartmentLogMapper.xml
```

公共能力：

```text
common
  response
    ApiResponse.java
    PageResponse.java

  exception
    DepartmentNotFoundException.java

  enums
    DepartmentStatusEnum.java
```

## 3. 每一层的职责

### 3.1 Controller

Controller 负责：

```text
接收 HTTP 请求
接收参数
调用 Service
返回 ApiResponse
```

不应该负责：

```text
复杂业务判断
直接写 SQL
直接操作 Mapper
```

示例：

```java
@PostMapping("/add")
public ApiResponse<DepartmentResponse> createDepartment(
    @Valid @RequestBody DepartmentCreateRequest request) {
  return ApiResponse.success(service.createDepartment(request));
}
```

---

### 3.2 Service

Service 负责：

```text
业务校验
组织业务流程
抛业务异常
控制事务
调用 Mapper
组装返回对象
```

示例：

```java
@Transactional
public DepartmentResponse createDepartment(DepartmentCreateRequest request) {
  // 参数校验
  // 唯一性校验
  // Entity 组装
  // mapper.insert
  // 写日志
  // 返回 Response
}
```

---

### 3.3 Mapper

Mapper 负责：

```text
定义数据库操作方法
和 XML 中的 SQL 一一对应
```

不应该负责：

```text
业务校验
抛业务异常
组装复杂业务流程
```

示例：

```java
Department findById(@Param("id") int id);

int insert(Department department);

int deleteByIds(@Param("ids") List<Integer> ids);
```

---

### 3.4 XML

XML 负责：

```text
写 SQL
写动态 SQL
写 resultMap
写 foreach
写 join
```

示例：

```xml
<select id="findById" resultMap="DepartmentResultMap">
  select id, name, description, status
  from department
  where id = #{id}
</select>
```

---

## 4. Entity / Request / Response 怎么分

### 4.1 Entity

Entity 对应数据库表。

```java
public class Department {
  private Integer id;
  private String name;
  private String description;
  private Integer status;
}
```

它关心：

```text
数据库字段
```

---

### 4.2 Request

Request 对应前端传来的参数。

新增请求：

```java
public class DepartmentCreateRequest {
  private String name;
  private String description;
  private Integer status;
}
```

修改请求：

```java
public class DepartmentUpdateRequest {
  private String name;
  private String description;
  private Integer status;
}
```

查询请求：

```java
public class DepartmentQueryRequest {
  private String name;
  private Integer pageNum;
  private Integer pageSize;
}
```

它关心：

```text
前端允许传什么
参数怎么校验
```

---

### 4.3 Response / VO

Response 对应返回给前端的数据结构。

```java
public class DepartmentResponse {
  private Integer id;
  private String name;
  private String description;
  private Integer status;
}
```

详情返回可能更复杂：

```java
public class DepartmentDetailResponse {
  private Integer id;
  private String name;
  private String description;
  private Integer status;
  private List<DepartmentLog> logs;
}
```

它关心：

```text
前端需要看到什么
```

## 5. 新增接口完整链路

接口：

```http
POST /departments/add
```

请求体：

```json
{
  "name": "研发部",
  "description": "负责研发",
  "status": 1
}
```

链路：

```text
Controller 接收 DepartmentCreateRequest
  ↓
Service 校验 request
  ↓
Service 校验 name 是否重复
  ↓
Service 校验 status 是否合法
  ↓
Service 组装 Department
  ↓
Mapper insert
  ↓
Service 写操作日志
  ↓
返回 DepartmentResponse
```

是否需要事务：

```text
如果只是单表 insert，可以不强制；
如果 insert 后还要写日志，必须考虑 @Transactional。
```

---

## 6. 修改接口完整链路

接口：

```http
PUT /departments/update/{id}
```

链路：

```text
Controller 接收 id + DepartmentUpdateRequest
  ↓
Service 校验 id
  ↓
Service 校验 request
  ↓
Service 判断是否有字段要更新
  ↓
Service 判断数据是否存在
  ↓
Service 判断 name 是否和其他数据重复
  ↓
Service 校验 status
  ↓
Mapper updateById
  ↓
Mapper findById 查询更新后的数据
  ↓
Service 写修改日志
  ↓
返回 DepartmentResponse
```

核心点：

```text
修改时要处理“空更新”
修改名称时要排除自己
```

---

## 7. 删除接口完整链路

接口：

```http
DELETE /departments/delete/{id}
```

链路：

```text
Controller 接收 id
  ↓
Service 校验 id
  ↓
Service 删除前先查数据
  ↓
Mapper deleteById
  ↓
Service 写删除日志
  ↓
返回 ApiResponse<Void>
```

为什么删除前先查？

```text
删除后就查不到名称了；
如果日志要记录名称，必须删除前查出来。
```

---

## 8. 分页查询完整链路

接口：

```http
GET /departments/list?pageNum=1&pageSize=10&name=研发
```

链路：

```text
Controller 接收 DepartmentQueryRequest
  ↓
Service 计算 offset
  ↓
Mapper countQuery 查询总数
  ↓
Mapper findPage 查询当前页数据
  ↓
Service Entity 转 Response
  ↓
返回 PageResponse
```

核心 SQL：

```sql
limit #{offset}, #{pageSize}
```

offset 计算：

```java
int offset = (pageNum - 1) * pageSize;
```

---

## 9. 批量删除完整链路

接口：

```http
DELETE /departments/batch
```

请求体：

```json
[1, 2, 3]
```

链路：

```text
Controller 接收 List<Integer>
  ↓
Service 校验 ids 不为空
  ↓
Service 校验每个 id 合法
  ↓
Mapper findByIds 查询要删除的数据
  ↓
Service 写删除日志
  ↓
Mapper deleteByIds 批量删除
  ↓
返回 ApiResponse<Void>
```

MyBatis XML：

```xml
<foreach collection="ids" item="id" open="(" separator="," close=")">
  #{id}
</foreach>
```

批量删除属于写操作，建议加：

```java
@Transactional
```

## 10. 事务和日志什么时候加

只查询：

```text
一般不需要事务
```

单表简单新增：

```text
可以不强制，但实际项目常会保留扩展空间
```

多次数据库写操作：

```text
必须考虑事务
```

典型场景：

```text
新增部门 + 写日志
修改部门 + 写日志
删除部门 + 写日志
批量删除 + 写多条日志
```

事务通常写在：

```text
Service 层
```

## 11. status / enum / 字典怎么处理

数据库通常保存数字：

```text
0 / 1
```

后端代码不要到处裸写：

```java
status != 0 && status != 1
```

推荐用 enum：

```java
DepartmentStatusEnum.containsCode(status)
```

接口可以只返回：

```json
{
  "status": 1
}
```

前端展示文字时通过字典：

```text
1 -> 启用
0 -> 禁用
```

## 12. 写新模块时的固定顺序

以后写新模块，不要乱开文件。

推荐顺序：

```text
1. 建表
2. 写 Entity
3. 写 Request
4. 写 Response
5. 写 Mapper 接口
6. 写 Mapper XML
7. 写 Service
8. 写 Controller
9. 编译
10. 接口测试
```

为什么先 Mapper 再 Service？

```text
Service 需要调用 Mapper；
先知道 Mapper 能提供哪些数据库能力，再组织业务流程。
```

## 13. 常见误区

### 13.1 Mapper 方法名和 XML id 不一致

Mapper：

```java
int deleteByIds(...);
```

XML：

```xml
<delete id="batchDeleteById">
```

会导致运行时异常。

---

### 13.2 resultType 和 resultMap 混用

简单映射：

```xml
resultType="完整类名"
```

复杂映射：

```xml
resultMap="映射ID"
```

一对多 JOIN 用：

```text
resultMap + collection
```

---

### 13.3 foreach 的 close 属性配置不正确

不推荐写法：

```xml
colse=")"
```

正确：

```xml
close=")"
```

---

### 13.4 Controller 返回类型不匹配

如果返回：

```java
ApiResponse.success(...)
```

方法返回类型就应该是：

```java
ApiResponse<T>
```

---

### 13.5 private 方法给 Controller 调

Controller 要调用的 Service 方法必须是：

```java
public
```

不能是：

```java
private
```

## 14. User 模块实战目标

下一步建议写一个简单 User 模块。

表结构：

```sql
create table sys_user (
  id int primary key auto_increment,
  username varchar(50) not null unique,
  nickname varchar(50),
  email varchar(100),
  status int not null default 1
);
```

接口目标：

```text
GET    /users/list        分页查询
GET    /users/{id}        查询详情
POST   /users/add         新增
PUT    /users/update/{id} 修改
DELETE /users/delete/{id} 删除
DELETE /users/batch       批量删除
```

需要掌握的能力：

```text
Request / Response / Entity
唯一约束 username
分页查询
动态 SQL
Service 校验
Mapper XML
enum 状态
foreach 批量删除
```

暂时不要求：

```text
JOIN
操作日志
权限角色
登录密码
Redis
```

## 15. 面试怎么讲一个模块

可以这样讲：

```text
项目中常见的后台管理模块通常采用 Controller、Service、Mapper、XML 分层。
Controller 负责接收请求和返回统一 ApiResponse。
Service 负责参数校验、业务校验、事务控制和异常抛出。
Mapper 和 XML 负责数据库操作，包括分页、动态 SQL、批量删除和关联查询。
新增、修改、删除这类写操作会在 Service 层加事务，如果涉及操作日志，会保证业务数据和日志一起成功或一起失败。
状态字段不会在代码里直接写 0/1，而是用 enum 统一管理，前端展示则可以通过字典接口翻译。
```

## 16. 本节小结

现在重点不是背代码，而是掌握模块结构：

```text
1. 一个模块有哪些文件
2. 每一层负责什么
3. CRUD 每条链路怎么走
4. Mapper 和 XML 怎么对应
5. Request / Response / Entity 怎么分
6. 什么时候需要事务
7. 批量操作怎么用 foreach
8. 状态字段怎么用 enum 管理
```

做到这个程度，就可以开始独立写新模块。
