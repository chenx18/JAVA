# 02 Prompt、上下文组织与评估

提示工程是把任务、约束和证据组织成可执行输入，并通过评估验证效果。可靠应用不能依赖一句万能指令或把所有问题都归因于用户不会提问。

## 二、知识讲解

<a id="k01"></a>

### 1. 任务契约与信息层次

先明确输入、期望结果、必须遵守的约束和失败时行为，再组织固定规则、用户请求、检索内容与工具结果。外部文档中的文字即使自称系统指令，也只是数据来源，不应自动获得控制权。

```text
任务：从给定订单文本提取字段。
输入：原文，可能缺失信息。
输出：符合约定schema的对象。
约束：不猜订单号；缺失字段按协议返回null。
失败：输入不属于订单时返回明确的不可处理状态。
证据：保留字段来源位置供核查。
```

分隔符和标签有助模型理解来源，但不是安全沙箱，权限仍由程序层执行。

<a id="k02"></a>

### 2. 示例、schema 与歧义

few-shot示例应覆盖关键边界，不只提供一种理想格式。示例数量增加也占token，且可能让模型过度模仿无关内容；选择代表性而非堆积。

schema定义字段类型、必选、枚举、长度和额外字段策略；自然语言解释业务含义。不能把“输出JSON”当完整schema约束，也不能认为schema涵盖所有跨字段与权限规则。

需求存在歧义时允许澄清，证据不足时表达限制。若产品必须强制选择，应在程序中明确默认策略与风险归属，而非让模型暗中猜。

<a id="k03"></a>

### 3. 上下文检索与抗干扰

只提供任务相关、当前有权访问且版本明确的上下文，保留来源ID。长文压缩可能丢失否定条件或例外，摘要需能追溯原文，不作为不可质疑事实。

检索内容、网页和工具输出可能包含诱导指令，模型侧规则可降低风险，但不能代替工具白名单、数据隔离和执行授权。把安全约束放在真正执行动作的边界，而不是仅写“不要做坏事”。

<a id="k04"></a>

### 4. 版本化与小规模实验

prompt、模型、参数、schema和检索配置一起版本化。建立固定评估集与新增失败样本，按错误类别比较修改前后，关注是否修复一类问题却伤害另一类。

指标可包括任务成功率、字段正确率、拒绝/澄清质量、成本与延迟，人工评审要有规则和代表样本。模型打分可辅助，但评分模型本身也要校准，不能把自我评为满分当质量证明。

<a id="summary"></a>

## 三、知识小结

好prompt来自清楚契约、相关上下文、边界示例和评估迭代。模型输入组织与程序安全执行各负其责，改词句之前先确认失败原因。

参考：[JSON Schema](https://json-schema.org/understanding-json-schema/)；[MDN Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="ai02-01"></a>

### AI02-01 [P0·工程取舍] Prompt越长越好吗？

**回答：** 不是，冗余指令与无关历史会占预算并增加干扰。应保留任务、约束、必要证据和代表边界，通过评估验证收益，而不是按字数判断质量。

对应讲解：[任务契约与信息层次](#k01)。

<a id="ai02-02"></a>

### AI02-02 [P0·原理] 为什么分隔符不能彻底防Prompt Injection？

**回答：** 它只帮助模型区分文本结构，外部内容仍可能影响语言决策。真正的动作权限、参数与资源范围需要程序验证，不能只靠自然语言自律。

对应讲解：[上下文检索与抗干扰](#k03)。

<a id="ai02-03"></a>

### AI02-03 [P1·工程取舍] 怎样证明改prompt有效？

**回答：** 使用版本化固定样本和真实失败案例，比较任务正确性、边界行为、成本与延迟，再做人工抽检和回归。只展示一个成功例子不够。

对应讲解：[版本化与小规模实验](#k04)。

<a id="ai02-04"></a>

### AI02-04 [P1·基础] few-shot与schema分别解决什么？

**回答：** 示例帮助表达任务模式和边界，schema约束结构；两者都不保证事实和授权。代表性与约束完整性比堆示例更重要。

对应讲解：[示例、schema 与歧义](#k02)。
