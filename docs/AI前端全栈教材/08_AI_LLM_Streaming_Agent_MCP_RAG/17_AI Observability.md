# 17 AI 可观测性、评估与成本

AI系统一次请求可能跨模型、检索、工具和队列。可观测性解释发生了什么，评估判断结果是否好，成本预算约束系统能否持续运行。

## 二、知识讲解

<a id="k01"></a>

### 1. trace、span 与任务关联

```text
用户请求 trace
  ├─ 身份/预算
  ├─ 检索与重排
  ├─ 模型调用
  ├─ 工具调用
  │   ├─ HTTP
  │   └─ DB
  └─ 响应与最终状态

长任务：taskId + stepId + attempt关联跨请求trace。
```

只记录总耗时无法区分排队、模型首数据、工具或数据库。记录结束原因、错误类别、取消和重试，使UI问题能追到真实链路，而不是一律显示“模型慢”。

<a id="k02"></a>

### 2. 延迟、用量与成本口径

区分排队时间、首响应头、首数据、首可见文本、完整结果、工具等待和后处理。输出token多可能延长总时间，但首可见体验也受缓冲与渲染影响。

usage需按供应商模型/版本和缓存、模态、推理等计费规则解读，价格来自配置与当前官方口径，不硬编码永久单价。估算预算、实时限额与最终对账分开，重试/回退也可能计费。

看每成功任务成本，而不只看单次模型调用便宜；低价模型若多次失败重试，整体可能更贵。

<a id="k03"></a>

### 3. 离线评估与在线监控

离线集包含代表任务、边界、失败案例和明确评分规则，分别评估检索、工具选择、结构、事实、引用和拒答。模型评审可辅助但需人工校准，不能完全依赖模型自评。

在线监控关注真实成功率、用户修正/放弃、错误与重试、延迟分布和成本，注意样本偏差与敏感信息保留。A/B或灰度要比较同口径任务，不能只展示最佳案例。

prompt、模型、工具schema和检索版本应能关联到每次结果，支持回归和回滚。

<a id="k04"></a>

### 4. 发布门槛与故障恢复

设定质量、成本、错误和延迟门槛，先回归再灰度，出现异常能关闭新工具或回退配置。结构化输出合法率不能代替事实与任务完成率，HTTP200也不代表生成成功。

日志脱敏、访问权限和保留周期必须明确，避免为了观测收集无界原始聊天和秘密。测试还要覆盖监控本身失败时不阻断或泄露业务数据。

评估结论应说明样本、版本和限制，未来趋势用观察而非保证表达。

<a id="summary"></a>

## 三、知识小结

trace定位链路，usage核算资源，eval判断质量，灰度与回滚控制变化。以成功任务为单位综合衡量，技术成功码不能替代业务完成。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[OWASP GenAI](https://genai.owasp.org/)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="ai17-01"></a>

### AI17-01 [P0·工程取舍] AI请求慢怎样拆解？

**回答：** 看排队、网络、模型首数据与持续输出、检索重排、工具、数据库和渲染各阶段，借trace/span和taskID关联。只看总耗时或HTTP状态无法定位。

对应讲解：[trace、span 与任务关联](#k01)。

<a id="ai17-02"></a>

### AI17-02 [P1·原理] 为什么单次token便宜不一定总成本低？

**回答：** 失败、重试、长上下文、多工具和回退都会增加总资源，低价模型可能需要更多步骤。应按成功任务成本和质量共同比较。

对应讲解：[延迟、用量与成本口径](#k02)。

<a id="ai17-03"></a>

### AI17-03 [P0·工程取舍] 模型自评能否作为唯一验收？

**回答：** 不能，评审模型也有偏差和错误。使用明确rubric、代表样本和人工校准，并分别验证工具执行、证据与最终结果。

对应讲解：[离线评估与在线监控](#k03)。

<a id="ai17-04"></a>

### AI17-04 [P1·工程取舍] 模型或prompt升级如何控制回归？

**回答：** 将模型、prompt、schema和检索配置版本化，运行固定与新增失败样本，再灰度监控质量、延迟和成本，并准备回退。不能仅靠一轮演示好看来发布。

对应讲解：[发布门槛与故障恢复](#k04)。
