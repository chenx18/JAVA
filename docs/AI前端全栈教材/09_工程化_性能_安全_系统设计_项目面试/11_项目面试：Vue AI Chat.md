# 11 项目面试：Vue AI Chat 的技术证据

本章用教学场景示范如何讲项目，不代表读者已完成相关系统。回答应填入真实负责范围、代码和测量证据，避免把教程方案直接说成工作成果。

## 二、知识讲解

<a id="k01"></a>

### 1. 背景、职责与核心流程

先用简短语言说明产品解决什么、用户是谁、你负责哪些模块，再给出一条请求流程：发送→任务/消息ID→增量事件→状态→展示→完成或失败。

不要用框架清单替代职责。可以明确负责的是parser、组件、取消、Store、API契约或部署哪部分，团队其他人的工作单独说明。

<a id="k02"></a>

### 2. 一个可复述难点：迟到结果

教学场景：用户发送A后切到B，A后返回覆盖B。分析顺序是复现完成顺序差异→定位共享当前消息引用→为运行绑定稳定ID→新请求取消旧资源→每次提交校验版本。

说明取消与版本分别解决什么，再给测试：A慢B快、旧请求失败、新请求成功、取消后完成和卸载。真正完成证据是结果归属与资源清理，不是加一个loading判断。

<a id="k03"></a>

### 3. 性能与协议的验证

另一个场景是模型输出快但页面卡，定位parser、全量Markdown、高亮和滚动布局，选择局部更新和分批渲染。报告实际测量条件与前后变化，没有数据就说明尚未量化，不编一个百分比。

SSE选择基于单向推送和请求配置，fetch流需要完整解析与恢复责任。解释没有选择WebSocket的当前约束，而非说它技术上不能做聊天。

<a id="k04"></a>

### 4. 回答结构与深挖准备

可以按“问题触发→机制原因→候选方案→采用理由→失败边界→验证→剩余限制”组织两三分钟回答。准备具体接口、状态类型、代码入口和一条失败测试。

被追问工具或后端未参与部分时明确边界，说明如何与对方协作，不伪装全栈所有层都独立完成。真实的不足与下一步也应基于当前系统，而非套通用高级名词。

<a id="summary"></a>

## 三、知识小结

项目表达用具体问题串起机制、方案和证据。职责真实、失败可复现、指标有口径，才能把前端能力与AI应用经验说清。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng11-01"></a>

### ENG11-01 [P0·工程取舍] 如何回答Chat项目最大的难点？

**回答：** 选确实参与的一个具体问题，讲触发、根因、方案和测试，例如迟到请求覆盖当前消息；给出真实代码/接口边界，不罗列所有技术栈或复制别人的成果。

对应讲解：[一个可复述难点：迟到结果](#k02)。

<a id="eng11-02"></a>

### ENG11-02 [P1·原理] 为什么版本检查比只取消更完整？

**回答：** 取消可能不及时或底层不支持，版本检查在写状态时阻止旧结果；两者一个偏资源，一个偏归属。回答需有乱序和取消后完成的测试证据。

对应讲解：[一个可复述难点：迟到结果](#k02)。

<a id="eng11-03"></a>

### ENG11-03 [P0·工程取舍] 没有性能数据如何讲优化？

**回答：** 可以准确讲定位方法和已验证行为，说明量化数据缺失与测量计划，不编造比例。若有数据，说明设备、规模、版本和指标口径。

对应讲解：[性能与协议的验证](#k03)。

<a id="eng11-04"></a>

### ENG11-04 [P1·工程取舍] 项目不是自己全做的怎样回答？

**回答：** 明确个人模块、协作接口与团队成果，深入自己能证明的部分。对未负责层说清了解程度与取舍，不把共同交付等同个人全部实现。

对应讲解：[回答结构与深挖准备](#k04)。

<a id="eng11-05"></a>

### ENG11-05 [P0·工程取舍] 项目介绍开头为什么要先说职责而不是技术栈？

**回答：** 听者需要知道产品问题和你真正负责的范围，才能判断后续方案与贡献。用一条请求流程说明模块关系，避免把团队成果和所有技术名词都包装成个人工作。

对应讲解：[背景、职责与核心流程](#k01)。
