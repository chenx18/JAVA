## 二、知识讲解

<a id="k01"></a>

### 1. 用一次用户操作串架构

例如用户提交文档并查看处理结果：Nuxt页面验证输入，BFF按需要聚合/转发，Java验证用户与工作区权限，数据库登记文档版本和任务，worker处理，页面查询或订阅。

说明哪一层是权威状态、哪一层缓存、哪些页面SSR，避免只画Browser→Nuxt→Java→Redis却说不出数据和错误怎样流动。

<a id="k02"></a>

### 2. SSR、BFF 与领域服务取舍

SSR适合某些初始内容和搜索要求，工作台也可偏客户端渲染；BFF可聚合页面接口和适配认证，核心事务与领域规则由清晰服务边界负责。不是语言本身决定必须这样拆。

代价包括一次转发、部署与追踪复杂度，简单接口可直接安全访问Java。讲清为何引入、什么情况下会简化，体现选择依据。

<a id="k03"></a>

### 3. 租户、事务与缓存

每个资源操作检查用户工作区归属，缓存和SSR数据不能跨租户共享。类型DTO、数据库约束和服务端授权分别保护不同事实。

创建任务与领域记录需要一致提交，外部模型/对象存储调用用异步状态、幂等和补偿处理。写后缓存失效与旧请求迟到都要有策略，不能把Redis当数据库事务延伸。

<a id="k04"></a>

### 4. 部署与项目证据

准备实际目录、接口契约、迁移、配置、日志trace和一条回滚/失败测试说明。秘密放服务端，前端环境变量和public配置不保密，生产代理与开发proxy不同。

面试中报告真实负责范围和可验证结果，教学架构只是分析材料。未做过高并发可说如何估算和测试，不宣称已有规模。

<a id="summary"></a>

## 三、知识小结

SaaS项目用用户操作说明页面、BFF、领域、数据与任务的责任。租户隔离、事务、缓存和部署贯穿链路，架构分层必须有实际收益和证据。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng12-01"></a>

### ENG12-01 [P1·工程取舍] 为什么不把所有后端都放Nitro或都直连Java？

**回答：** 按SSR聚合、团队能力、事务和部署需求选择，不按语言偏好绝对化。BFF有适配价值也有延迟和维护成本，简单路径可以简化。

对应讲解：[SSR、BFF 与领域服务取舍](#k02)。

<a id="eng12-02"></a>

### ENG12-02 [P0·原理] 多租户隔离只在列表查询加tenantId够吗？

**回答：** 不够，详情、写入、附件、缓存、任务和SSR输出都要保持授权范围，tenantId来自可信上下文而非任意客户端字段。

对应讲解：[租户、事务与缓存](#k03)。

<a id="eng12-03"></a>

### ENG12-03 [P1·工程取舍] 创建文档任务怎样保证可恢复？

**回答：** 先持久化领域记录和任务状态，异步步骤带版本与幂等，外部调用结果可查询/补偿，客户端根据任务ID恢复。单一长请求不提供同样可靠性。

对应讲解：[用一次用户操作串架构](#k01)。

<a id="eng12-04"></a>

### ENG12-04 [P0·工程取舍] 讲全栈项目应准备什么证据？

**回答：** 真实接口、数据模型、事务和授权路径、部署配置、trace与失败测试，明确个人负责部分。仅技术栈图不能证明端到端交付。

对应讲解：[部署与项目证据](#k04)。
