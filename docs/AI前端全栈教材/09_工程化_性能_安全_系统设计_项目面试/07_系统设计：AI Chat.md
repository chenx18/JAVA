# 07 系统设计：可恢复的 AI Chat

系统设计先明确用户行为、峰值并发、输出规模、时效和成本目标，再选组件。下面是教学设计过程，不代表已有百万用户上线结果。

## 二、知识讲解

<a id="k01"></a>

### 1. 需求与容量假设

确认是否多租户、是否支持文件与工具、生成最长多久、刷新后是否恢复、是否允许部分结果以及成本上限。DAU不能直接换算成并发生成，需要峰值到达率和平均时长等数据。

估算连接数、每任务缓冲、历史消息、供应商并发和token预算。例如同时运行C个任务、每任务缓冲上限B字节，仅该部分约C×B，还不含正文、框架与连接开销。先写单位和假设，避免拿“百万用户”直接推出Redis+微服务。

<a id="k02"></a>

### 2. 数据与请求契约

Conversation保存所有者和标题，Message保存角色及结构化parts，Run/Task保存执行状态、模型配置和版本，ToolCall保存调用关联和结果。消息展示与任务执行状态分开，稳定ID帮助取消、恢复和审计。

```text
POST /api/conversations
POST /api/conversations/{id}/runs → runId
GET  /api/runs/{id}             → 权威状态
GET  /api/runs/{id}/events      → 增量/恢复
POST /api/runs/{id}/cancel      → 取消意图
```

这是应用协议示意，每个资源都检查所有权，写入需幂等和输入schema。事件序号与终态定义必须一致。

<a id="k03"></a>

### 3. 链路与失败隔离

浏览器负责交互与增量渲染，API/AI网关负责认证、预算与适配，worker或受控运行器负责生成/工具，数据库保存权威状态，缓存用于适合的短期加速。起步可模块化部署，不必每个框都独立微服务。

慢供应商、工具失败、客户端断线和取消需隔离。长任务不依赖某个浏览器连接，必要时可重连查询；模型回退记录质量和费用变化，不默认并行烧多个请求。

<a id="k04"></a>

### 4. 一致性、性能与验收

最终消息与任务状态通过明确提交流程一致保存，事件发布可用outbox等减少数据库与消息链路错位。客户端按runId/sequence处理重复和过时事件，取消不抹掉已完成副作用。

限额与并发预算防过载，前端有界缓冲和局部渲染，服务端监控首数据、工具、总时长与成功任务成本。验收覆盖掉线恢复、重复提交、用户隔离、部分失败和发布替换。

<a id="summary"></a>

## 三、知识小结

先量需求与容量，再定义消息/任务和API，最后选择执行、持久化与缓存。可靠性靠身份、序号、幂等和恢复，架构组件数量不是设计答案。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng07-01"></a>

### ENG07-01 [P1·工程取舍] 被问百万用户Chat，第一步是什么？

**回答：** 先澄清峰值并发、请求时长、消息规模、租户与预算，用假设估算资源。用户总数不能直接决定技术栈，先有数据与SLO再选架构。

对应讲解：[需求与容量假设](#k01)。

<a id="eng07-02"></a>

### ENG07-02 [P1·原理] 为什么Message与Run状态分开？

**回答：** 消息是用户内容，Run是一次执行生命周期，可能重试、工具等待或取消。分开便于恢复、审计和多次执行关联，不让一个字符串承担任务事实。

对应讲解：[数据与请求契约](#k02)。

<a id="eng07-03"></a>

### ENG07-03 [P1·工程取舍] 连接断开后任务怎么办？

**回答：** 由服务端持久状态和运行器继续或按策略取消，客户端凭runId重连查询/订阅并验证权限。不能只把状态留在HTTP回调和浏览器内存。

对应讲解：[链路与失败隔离](#k03)。

<a id="eng07-04"></a>

### ENG07-04 [P1·工程取舍] 如何证明系统可恢复而不只可演示？

**回答：** 测试重复提交、worker故障、事件重放、用户隔离、取消和版本发布，核对持久状态与副作用。成功打字一次不代表恢复和成本控制完成。

对应讲解：[一致性、性能与验收](#k04)。
