# 09 系统设计：RAG 摄取与查询链路

RAG系统要同时保证可检索、可更新、可授权和可引用。摄取吞吐与在线回答延迟不同，应分开组织并通过版本关联。

## 二、知识讲解

<a id="k01"></a>

### 1. 文档与版本模型

Document记录所有者/租户、来源和权限，DocumentVersion记录内容hash、解析状态与模型配置，Chunk记录文本位置与版本，索引条目关联这些稳定ID。

先把原文件放合适对象存储，登记摄取任务，再解析/OCR、分块和embedding；每阶段可重试并记录错误。不要让上传HTTP一直等待所有向量完成，也不丢弃可追溯原文。

<a id="k02"></a>

### 2. 一致发布与删除

新版本索引准备完成后再切换可查询版本，避免读到一半旧块一半新块。跨数据库与向量引擎可采用状态机和幂等写，失败后重新对账，而不假装一个本地事务覆盖全部。

删除或权限撤销应先在权威访问层生效，再异步清理索引和缓存。即使旧向量暂时存在，也不能被送入模型上下文；物理删除与即时授权是两个步骤。

<a id="k03"></a>

### 3. 在线查询与证据

查询先建立用户授权范围，经过词法/向量候选、metadata过滤与重排，再选择有限证据。每块保留来源版本和位置，答案引用需支持具体陈述并可在点击时授权访问。

候选不足时允许澄清或证据不足响应，不通过扩大到其他租户“补齐答案”。索引与查询embedding版本一致，缓存键包含必要范围和版本。

<a id="k04"></a>

### 4. 容量、质量与监控

估算文档量、平均块数、维度、更新频率和查询并发，比较索引内存、构建时间、召回与延迟。向量维度相同不代表不同模型兼容。

离线评估检索召回、重排、引用和忠实度，在线观察摄取积压、失败、陈旧版本和成功任务成本。删除、重建、回滚和灾难恢复需要演练，而不是只测试新增文档。

<a id="summary"></a>

## 三、知识小结

摄取按版本幂等执行，查询按权限选择证据，发布与删除有权威边界。RAG质量依赖数据全生命周期，不只取决于向量相似度。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng09-01"></a>

### ENG09-01 [P1·工程取舍] 为什么embedding适合队列worker？

**回答：** 解析、切块和向量化耗时且可能重试，队列可控制并发并独立恢复，不占住上传连接。仍需任务状态、幂等和错误可见性。

对应讲解：[文档与版本模型](#k01)。

<a id="eng09-02"></a>

### ENG09-02 [P1·原理] 文档更新怎样避免新旧块混用？

**回答：** 用版本关联块和索引，准备完成后切换可查询版本，失败可恢复/对账。不能边写新块边默认所有查询天然一致。

对应讲解：[一致发布与删除](#k02)。

<a id="eng09-03"></a>

### ENG09-03 [P1·工程取舍] 删除文档后向量还没删完怎么办？

**回答：** 权威权限和版本层先禁止它进入上下文，再清理索引与缓存。不能等待异步物理删除才实现访问撤销。

对应讲解：[一致发布与删除](#k02)。

<a id="eng09-04"></a>

### ENG09-04 [P1·工程取舍] 怎样验证RAG架构而非演示一个问答？

**回答：** 覆盖摄取失败、更新切换、删除、权限、模型迁移、检索与引用质量及负载，观察队列和索引状态，不能只看答案流畅。

对应讲解：[容量、质量与监控](#k04)。

<a id="eng09-05"></a>

### ENG09-05 [P1·原理] 向量top1为何不能直接作为最终答案证据？

**回答：** 相似分数不保证相关、有效、授权或支持具体陈述。要结合过滤、重排、版本与证据核验；候选不足时允许澄清或说明限制。

对应讲解：[在线查询与证据](#k03)。
