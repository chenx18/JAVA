# 05 Web Performance：定位、方案与回归

性能优化以用户目标和证据开始。资源传输、CPU计算、浏览器渲染和交互等待可能同时造成慢，方案必须对应瓶颈。

## 二、知识讲解

<a id="k01"></a>

### 1. 分层指标与基线

TTFB观察首字节等待，FCP/LCP观察内容出现，INP观察交互响应，CLS观察视觉稳定性。现场分位数与实验室固定条件互补，不把单次总分当所有用户体验。

按路由、设备、网络和版本分群，记录样本规模与采样方式。优化前固定任务与数据量，避免把更小测试数据当性能进步。

<a id="k02"></a>

### 2. 资源与关键路径

检查入口包、动态chunk、图片、字体、第三方脚本及接口串行依赖。拆包与懒加载减少初始工作，preload/preconnect仅用于真正关键资源，过度预取会争带宽。

图片格式、尺寸、响应式来源和预留空间影响LCP/CLS，字体策略影响可见性与布局。CDN与HTTP缓存减少传输成本，但源站处理和客户端执行仍可能是瓶颈。

<a id="k03"></a>

### 3. CPU、DOM 与调度

减少重复解析、全量过滤和不必要组件更新；大列表分页或虚拟化，布局读写分离，合适计算分片或Worker。rAF合并视觉更新，不把重计算变成免费。

长任务会影响交互等待，事件处理后还有呈现延迟，INP不只等于回调函数耗时。memo/computed等缓存有依赖和身份成本，先确认复用真的有效。

<a id="k04"></a>

### 4. 实验、回归与收益证明

形成可检验假设，例如“主图发现晚导致LCP”，然后改一组相关因素，比较网络时间线和指标变化。生产灰度观察不同设备，防止某项优化伤害其他路径。

报告注明基线、改动、样本和代价，保留正确性、可访问性和缓存隐私回归。不能用减少校验、隐藏内容或丢失结果换取漂亮指标。

<a id="summary"></a>

## 三、知识小结

性能路径是测量→定位→假设→对应改动→同条件验证→现场回归。工具和缓存是手段，用户完成任务的体验与正确性是目标。

参考：[Web Vitals](https://web.dev/articles/vitals)；[MDN Performance API](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng05-01"></a>

### ENG05-01 [P0·工程取舍] 页面慢怎样开始排查？

**回答：** 先按加载、交互和稳定性定义问题，查Network关键路径和Performance主线程，再选择对应方案。不要先背一串懒加载、CDN、memo。

对应讲解：[分层指标与基线](#k01)。

<a id="eng05-02"></a>

### ENG05-02 [P1·原理] 拆包越细越好吗？

**回答：** 不一定，更多chunk有请求、依赖和调度成本，交互时还可能出现加载等待。按路由和功能边界以及实际使用概率设计。

对应讲解：[资源与关键路径](#k02)。

<a id="eng05-03"></a>

### ENG05-03 [P1·工程取舍] 如何证明性能提升不是测量偶然？

**回答：** 固定设备、数据和任务，重复测试并观察分位数，再灰度检查现场分群。说明样本与代价，回归功能和可访问性。

对应讲解：[实验、回归与收益证明](#k04)。

<a id="eng05-04"></a>

### ENG05-04 [P0·原理] 为什么只缩短事件回调仍可能INP差？

**回答：** 此前主线程排队和回调后的呈现也计入响应体验。需看长任务、状态更新、布局绘制的完整链路。

对应讲解：[CPU、DOM 与调度](#k03)。
