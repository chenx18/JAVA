# 06 AI 前端的增量渲染与性能

模型输出快不代表界面流畅。AI前端需要控制解码、状态更新、Markdown、高亮和滚动成本，同时保持取消与最终结果正确。

## 二、知识讲解

<a id="k01"></a>

### 1. 分开模型与前端时间

区分请求等待、模型首数据、首可见文本、持续吞吐、工具等待与完整答案。服务端输出很多小事件，前端可能因每次全量重算而落后。

用trace与浏览器Performance对齐时间，检查代理缓冲、parser、reducer、组件和布局，不能把所有卡顿都归咎于供应商。

<a id="k02"></a>

### 2. 增量状态与昂贵转换

网络解析产生领域事件，仅更新对应requestId/messageId的当前片段。历史消息尽量保持稳定，避免每个delta复制整份大列表并重跑全部Markdown。

解析与渲染可采用分阶段策略：接收层持续累积，展示层小批次更新，昂贵高亮按更低频率或完成后处理。增量解析器要正确处理未闭合代码块等边界，不通过错误截断换速度。

数据和UI状态分开，最终完成应保证所有内容已落入权威状态，不依赖最后一帧恰好触发。

<a id="k03"></a>

### 3. 滚动、虚拟化与后台页面

用户在底部时可跟随增量，主动向上阅读后停止强制滚动；提供回到底部入口。大量历史消息可分段加载或虚拟化，但可变高度、代码块和引用展开需维护滚动锚点。

rAF可能在后台标签暂停，所以取消、完成、持久化和缓冲限制不能全部放rAF回调。长流需要有界缓冲与异常策略，内存增长也要测。

<a id="k04"></a>

### 4. 性能验收场景

固定输出长度、事件频率、历史条数和设备，测首可见、输入延迟、长任务、内存和最终完整性。覆盖中文/emoji分块、长代码、快速切换会话、取消和后台恢复。

前端节流不减少已经发生的模型token费用，停止按钮需真正传播取消；供应商是否及时停止仍由下游协议决定，观测实际结果。

<a id="summary"></a>

## 三、知识小结

接收、状态和视觉三个节奏分开，局部更新与有界缓冲降低成本，滚动尊重用户，完成/取消不依赖绘制。性能必须同时验完整性。

## 四、面试题与答案

<a id="eng06-01"></a>

### ENG06-01 [P0·原理] 模型生成很快，页面为何还卡？

**回答：** 前端可能每次增量全量解析Markdown、重渲染历史和同步滚动布局，主线程来不及处理。分层测量后减少重复工作，而不是只换模型。

对应讲解：[分开模型与前端时间](#k01)。

<a id="eng06-02"></a>

### ENG06-02 [P1·工程取舍] 流式更新怎样避免全列表重算？

**回答：** 以稳定消息和片段ID局部更新，保持历史引用，分批视觉刷新并降低昂贵解析频率。仍需正确处理未完整语法和最终flush。

对应讲解：[增量状态与昂贵转换](#k02)。

<a id="eng06-03"></a>

### ENG06-03 [P1·原理] 后台页rAF暂停会带来什么风险？

**回答：** 若业务完成和持久化只在rAF做，状态可能长时间不结算且缓冲增长。接收和权威状态应独立推进，恢复后从状态重建UI。

对应讲解：[滚动、虚拟化与后台页面](#k03)。

<a id="eng06-04"></a>

### ENG06-04 [P1·工程取舍] AI前端性能如何测试？

**回答：** 用固定输出、频率、历史规模和设备比较首可见、交互、长任务与内存，同时验证无丢字、取消、切换和后台恢复。不能只录一段顺畅动画。

对应讲解：[性能验收场景](#k04)。
