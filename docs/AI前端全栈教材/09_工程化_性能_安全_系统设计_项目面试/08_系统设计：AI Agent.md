# 08 系统设计：Agent 运行器与持久执行

Agent运行器把不确定模型决策连接到确定状态和受控工具。设计重点是步骤边界、恢复和权限，而不是把循环放进一个超长HTTP请求。

## 二、知识讲解

<a id="k01"></a>

### 1. 任务、步骤与执行租约

任务记录目标、用户、预算、工作流版本和状态，每步记录输入、决策、工具、结果与尝试版本。worker领取任务时需要明确所有权/lease，防止崩溃后两个worker同时提交。

队列通常至少一次投递，重复消息是正常可能。数据库唯一键、步骤状态版本和工具幂等共同保护结果，不依赖“队列不会重投”。

<a id="k02"></a>

### 2. Checkpoint 与副作用边界

在可恢复的确定边界保存checkpoint，例如某工具结果已确认并入库。恢复时先判断该步骤是否已执行或结果可查询，再继续，不能从模型思考文本猜测。

外部写动作与本地状态无法天然原子提交，可使用幂等键、outbox、结果查询或补偿。checkpoint早/晚都会有窗口，需要画出崩溃发生在调用前后各位置的结果。

<a id="k03"></a>

### 3. 预算、人工输入与取消

控制总步数、时间、token、工具次数和并发，预算由运行器执行，不由模型自我声明。需要输入时持久化具体提案和等待状态，恢复后重新校验权限与提案版本。

取消请求进入状态并传播到底层，不能立刻把所有外部动作视为撤销；已完成写入可能需要补偿。任务TTL、审计保留和用户可见历史是不同生命周期。

<a id="k04"></a>

### 4. 运营、评估与演进

trace关联task/step/attempt，区分模型决策失败与执行故障。按任务完成、无效循环、工具越权拒绝、恢复成功和成本评估，比较固定workflow基线。

工作流和工具schema版本化，旧任务的恢复策略随版本显式管理。灰度新模型和工具，保留停止开关与回退，不让升级悄悄改变运行中的动作语义。

<a id="summary"></a>

## 三、知识小结

持久Agent需要任务/步骤状态、执行所有权、幂等和checkpoint。预算与权限由程序控制，模型记录帮助理解但不替代执行事实。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng08-01"></a>

### ENG08-01 [P1·原理] 为什么只保存聊天历史不能恢复Agent？

**回答：** 历史可能没有可靠反映工具是否已执行和事务是否提交，还可能被摘要损失细节。恢复需要权威step状态、结果和版本，不能让模型猜。

对应讲解：[Checkpoint 与副作用边界](#k02)。

<a id="eng08-02"></a>

### ENG08-02 [P1·工程取舍] worker崩溃重投如何避免重复副作用？

**回答：** 通过任务领取版本/lease、步骤唯一身份和外部幂等/结果查询，先判定已有执行再继续。仅队列确认或checkpoint一个字段不能覆盖所有窗口。

对应讲解：[任务、步骤与执行租约](#k01)。

<a id="eng08-03"></a>

### ENG08-03 [P1·原理] 取消后为何还可能完成？

**回答：** 取消是协作信号，底层可能不可中断或已经执行，需以权威终态结算。已提交副作用还可能需要补偿，不能仅改UI状态。

对应讲解：[预算、人工输入与取消](#k03)。

<a id="eng08-04"></a>

### ENG08-04 [P1·工程取舍] Agent升级怎样不破坏旧任务？

**回答：** 保存工作流、模型和工具schema版本，为进行中任务提供兼容执行、迁移或明确终止策略。先回归与灰度，再扩大范围。

对应讲解：[运营、评估与演进](#k04)。
