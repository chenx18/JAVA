# 15 从需求到前端、Java 与 AI 闭环

全栈能力体现在能把一个明确用户目标交付为可验证系统。前端作为主力，Java与AI围绕实际业务补齐链路，不需要先堆出所有企业架构组件。

## 二、知识讲解

<a id="k01"></a>

### 1. 定义最小可验收业务

将需求写成用户、输入、期望结果和失败行为，例如“有权限成员上传一份文档，处理完成后能查询并看到来源”。先明确角色、数据范围、时效和成本，再选择技术。

验收包括成功、非法输入、无权限、处理失败和恢复。只描述“支持AI知识库”太宽，容易写了许多模块仍没有一条可完成路径。

<a id="k02"></a>

### 2. 模型、契约与边界

建立User/Workspace/Document/Version/Task等必要模型，定义API请求、响应、错误和事件，数据库用约束保护事实。前端按状态机表达等待、成功、错误和取消，Java承担领域与授权，AI适配器提供受控生成/检索能力。

哪些状态在URL、本地组件、Store、服务端或缓存中，应明确唯一权威来源。先做一条纵向闭环，再扩模块，避免每层都写了一半却无法联调。

<a id="k03"></a>

### 3. 实现、测试与部署

实现顺序可按风险调整：先验证难点接口和数据约束，再接页面交互；并不永远必须从Controller或XML第一行开始。使用mock固定不确定依赖，真实集成再验证数据库和供应商协议。

并行建立日志、错误、取消和预算，发布时配置环境、迁移、健康和回滚。基础闭环通过后再按压力与业务需要加缓存、队列和更复杂拆分。

<a id="k04"></a>

### 4. 学习与面试的证据

能读懂是开始，目标是能独立实现模块并解释选择。基础接口、状态、校验和关键异步逻辑应逐步写熟；框架配置可以查文档，但要知道它解决什么和如何验证。

前端面试主线仍是JS/TS、框架、浏览器、工程化和真实项目；Java与AI提供横向交付证据。不要用技术名词长度代替深度，也不把练习项目包装成未发生的商业规模。

<a id="summary"></a>

## 三、知识小结

用用户故事限定目标，用模型与契约连接各层，用测试和部署证明闭环。学习围绕交付增长，主力前端深度与横向能力相互支撑。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng15-01"></a>

### ENG15-01 [P0·工程取舍] 从0做产品先写哪一层？

**回答：** 先明确验收与风险，再选能打通一条真实业务的实现顺序。高风险数据/接口可先验证，页面与后端按契约联调，不存在所有模块固定从同一层开始的规则。

对应讲解：[定义最小可验收业务](#k01)。

<a id="eng15-02"></a>

### ENG15-02 [P1·工程取舍] 什么时候引入Redis、队列或服务拆分？

**回答：** 当缓存时效、长任务、并发资源或团队边界有具体需求时引入，并说明新增一致性和运维成本。不是为了全栈标签先集齐组件。

对应讲解：[实现、测试与部署](#k03)。

<a id="eng15-03"></a>

### ENG15-03 [P0·工程取舍] 框架配置需要全部盲写吗？

**回答：** 可查文档，但应理解输入、作用和验证方法；高频业务流程和关键机制要逐步独立实现。面试和交付都要求能解释，而不只复制配置。

对应讲解：[学习与面试的证据](#k04)。

<a id="eng15-04"></a>

### ENG15-04 [P1·原理] 为什么先做纵向闭环？

**回答：** 它能尽早验证API、权限、数据、UI和部署的真实协作，发现跨层假设错误。每层分别堆功能却没有可完成流程，会延后风险暴露。

对应讲解：[模型、契约与边界](#k02)。
