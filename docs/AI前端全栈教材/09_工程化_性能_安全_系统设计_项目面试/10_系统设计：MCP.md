# 10 系统设计：MCP 接入与能力治理

MCP接入系统需要管理多个服务器的能力、身份和版本。协议统一了交互，不意味着所有服务器同样可信或所有工具可向所有用户开放。

## 二、知识讲解

<a id="k01"></a>

### 1. Host、连接器与能力目录

Host组织用户、模型和工具策略，客户端连接器负责对应协议与传输，服务器目录记录来源、版本、能力和授权配置。工具发现结果要分页、缓存和失效，不把初次列表当永久事实。

按用户和任务挑选有限工具集合，减少上下文成本和误选；描述和schema来自外部服务器，也需校验。工具自报只读等提示不能作为唯一安全授权依据。

<a id="k02"></a>

### 2. 身份映射与每次执行

认证客户端或用户后，映射到租户、scope和资源规则；每次tools/call验证名称、参数及目标授权。token应适合当前受众，不盲目透传其他服务凭据。

2026协议对每请求_meta与能力有要求，旧版会话式接线和当前发现流程需适配明确，使用版本匹配SDK。错误、分页和能力缺失应可观察并有降级。

<a id="k03"></a>

### 3. 长任务与交互扩展

Tasks扩展提供持久句柄、查询、中途输入和取消，但客户端/服务器都需显式支持。当前扩展通过tasks/get携带状态及终态结果，tasks/update处理输入，不能直接照搬旧tasks/result流程。

MCP Apps等交互扩展还需Host渲染支持和隔离策略，模型选择某UI不等于获得任意代码执行权。确认绑定具体提案与版本，取消按权威终态处理。

<a id="k04"></a>

### 4. 隔离、审计与测试

按服务器/工具限制网络、文件和数据范围，输出大小与耗时有预算；外部资源不能升级为高信任指令。审计关联用户、任务、工具和资源，保留必要信息但避免秘密泄露。

测试版本矩阵、认证过期、能力变化、未知工具、恶意描述、过大结果、取消和任务恢复。协议Inspector辅助发现问题，但成功列工具不代表安全与业务正确。

<a id="summary"></a>

## 三、知识小结

MCP治理是来源目录、协议适配、逐次授权和扩展生命周期。能力发现服务可用性，执行策略服务安全与业务结果，两者都要验证。

参考：[MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)；[MCP Tasks Extension](https://modelcontextprotocol.io/extensions/tasks/overview)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng10-01"></a>

### ENG10-01 [P1·原理] 工具宣称readOnly就可以放心调用吗？

**回答：** 不能把外部提示当权威，仍需可信策略、实际工具实现和用户资源权限。描述有助选择，但执行授权在Host/服务器边界落实。

对应讲解：[Host、连接器与能力目录](#k01)。

<a id="eng10-02"></a>

### ENG10-02 [P1·工程取舍] 多MCP服务器接入怎样避免混乱？

**回答：** 管理来源、版本、scope与能力目录，按任务暴露有限集合并处理缓存失效，逐次校验参数和资源。不同服务器不能默认共享全部信任和凭据。

对应讲解：[身份映射与每次执行](#k02)。

<a id="eng10-03"></a>

### ENG10-03 [P1·原理] 为何要测试Tasks客户端兼容？

**回答：** 它是可选扩展，结果形态、查询和输入流程依版本。客户端不支持时不能返回它无法理解的任务结果，应有能力检测与降级。

对应讲解：[长任务与交互扩展](#k03)。

<a id="eng10-04"></a>

### ENG10-04 [P1·工程取舍] MCP上线验收应看哪些证据？

**回答：** 除发现和调用成功，还应验证认证、授权、版本、恶意/超大结果、取消、恢复和审计。Inspector通过只覆盖其中一部分。

对应讲解：[隔离、审计与测试](#k04)。
