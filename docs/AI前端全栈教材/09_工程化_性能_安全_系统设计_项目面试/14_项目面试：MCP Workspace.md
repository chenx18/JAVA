# 14 项目面试：MCP Workspace 与工具 UI

工具工作台需要让用户理解正在访问什么、执行到哪里以及如何恢复。教学方案以受控订单查询和动作提案说明，真实经历按本人事实表达。

## 二、知识讲解

<a id="k01"></a>

### 1. 从发现到用户任务

Host发现可用服务器和工具后，按用户权限及当前任务提供适当能力。界面展示工具来源、简要作用和状态，而不是只有“AI正在思考”。

订单查询得到权威结果后可渲染OrderCard，若用户意图涉及退款，再生成具体动作提案；不能因为查询工具返回一个按钮，就自动执行退款。

<a id="k02"></a>

### 2. 工具与任务状态

工具调用可有待执行、执行中、需要输入、成功、失败和取消等应用状态，绑定callId/taskId与资源ID。MCP扩展状态映射到UI时保留版本和终态语义，不混用旧任务协议字段。

当前Tasks扩展需双方支持，中途输入由相应查询与update流程处理；客户端刷新后仍能按句柄恢复。没有扩展能力时，可降级使用自己的持久任务API而不是让界面悬挂。

<a id="k03"></a>

### 3. 确认、权限与结果核对

高影响提案展示订单、金额、币种、原因和当前版本，用户确认与执行参数绑定；执行前服务端重新授权并检查资源状态，防止确认后内容变化。

工具失败或重试需幂等，取消按权威结果结算。结果组件只显示允许字段和可信链接，不执行工具返回的任意模板或脚本。

已有授权范围内的正常读取可以连续进行，产品应把确认留在真正需要的边界，而不是每一步弹同样问题。

<a id="k04"></a>

### 4. 项目证据与可访问性

准备工具发现、授权、状态映射、恢复和确认的实际代码/测试，说明兼容哪些协议版本与Host。测试未知工具、权限变化、迟到结果、取消不生效和扩展缺失。

工具状态使用明确文本与可操作控件，焦点和键盘流程完整。屏幕上出现“成功”必须关联真实结果，不以模型叙述代替后端完成。

<a id="summary"></a>

## 三、知识小结

MCP Workspace把协议能力变成清楚的用户流程。来源、状态、具体提案和权威结果可观察，版本与权限在每个边界保持一致。

参考：[OpenTelemetry Concepts](https://opentelemetry.io/docs/concepts/)；[MCP Specification](https://modelcontextprotocol.io/specification/2026-07-28)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="eng14-01"></a>

### ENG14-01 [P0·原理] 工具调用为什么需要独立UI状态？

**回答：** 调用可能耗时、失败、需输入或取消，单一聊天文字无法正确表达可用操作与恢复。状态需绑定调用/任务ID和实际结果。

对应讲解：[工具与任务状态](#k02)。

<a id="eng14-02"></a>

### ENG14-02 [P1·工程取舍] 确认弹窗应该展示什么？

**回答：** 具体资源、参数、影响和版本，让用户审查真实动作，执行时再次验证身份与状态。泛泛“允许操作吗”不足以绑定授权。

对应讲解：[确认、权限与结果核对](#k03)。

<a id="eng14-03"></a>

### ENG14-03 [P1·原理] 知道taskId就能恢复结果吗？

**回答：** 还需服务器保留句柄、客户端支持相应协议和每次访问的所有权授权。TTL、扩展缺失与取消状态都要有处理。

对应讲解：[工具与任务状态](#k02)。

<a id="eng14-04"></a>

### ENG14-04 [P0·工程取舍] 怎样讲清MCP项目而不只列名词？

**回答：** 用一个查询→提案→执行→恢复的真实流程，说明自己负责的协议、UI和授权边界，展示失败测试和版本兼容，不把tools/list成功当全部成果。

对应讲解：[项目证据与可访问性](#k04)。

<a id="eng14-05"></a>

### ENG14-05 [P1·工程取舍] MCP工作台为什么要显示工具来源和作用？

**回答：** 用户需要理解哪些外部能力参与任务、当前访问什么及可以做何种选择。可见来源和有限工具集合帮助建立正确预期，但仍需服务端授权，不由描述本身授予权限。

对应讲解：[从发现到用户任务](#k01)。
