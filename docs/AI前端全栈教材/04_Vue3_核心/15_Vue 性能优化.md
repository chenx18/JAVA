# 15 Vue 性能优化与验证

Vue优化先确定瓶颈在网络、计算、依赖范围、组件更新还是浏览器DOM工作。选用框架API前先减少不必要工作，再用可复现数据验证收益。

## 二、知识讲解

<a id="k01"></a>

### 1. 测量与更新范围

结合Network、Performance、Vue DevTools与现场数据，观察慢的是初始加载、某次交互还是长期内存。开发模式的调试开销与生产构建不同，比较时保持版本、数据量和设备条件一致。

父组件更新不代表所有后代都必须做同样工作，props稳定、组件边界、编译优化和依赖关系共同决定开销。避免每次渲染生成无意义的新对象/回调，但也不应为此牺牲清晰逻辑或盲目缓存全部东西。

<a id="k02"></a>

### 2. 数据与响应式粒度

大块不可变或外部库数据可放shallowRef并通过替换更新，第三方实例可按需求markRaw。代价是内部深层修改不再按普通深响应式通知，必须有清楚更新契约。

computed缓存适合稳定派生数据，但昂贵计算依赖频繁变化时仍会执行。预处理、索引、增量计算或Worker可能更有效；异步计算和网络请求不要塞进computed getter当缓存。

深watch会遍历结构，不应为“保证更新”对整个业务对象无限deep。观察具体来源并使用必要的版本/ID。

<a id="k03"></a>

### 3. 大列表、虚拟化与异步组件

十万条列表首先看需要同时显示多少DOM。分页、虚拟列表和分段加载减少实际节点，key只帮助身份复用，不会消除节点数量带来的布局/绘制成本。

虚拟列表还需处理可变行高、滚动锚点、键盘焦点、选择状态与可访问性，不能只按固定高度截一段就宣称完整。用户编辑状态应绑定业务ID，而非当前可视索引。

路由懒加载和异步组件减少首屏依赖，需合理loading/error与预取策略；分包过碎会增加请求和调度成本。

<a id="k04"></a>

### 4. v-once、v-memo、KeepAlive 与验证

v-once适合确实不再变化的子树，v-memo用明确依赖控制部分更新复用；遗漏必要依赖会让UI陈旧，不是无条件安全的加速开关。KeepAlive复用实例但增加保留内存，需容量和失效策略。

高频视觉更新可按帧合并，数据接收和业务完成不能依赖后台页及时rAF。卸载/停用清理订阅与请求，避免性能优化变成资源泄漏。

优化后检查耗时、输入延迟、节点数和内存，并验证正确性、取消和异常路径；只比较一张截图或总包大小不够。

<a id="summary"></a>

## 三、知识小结

减少数据、计算与DOM工作优先，框架缓存和浅响应式按契约使用。性能改善必须与状态正确、资源释放和真实用户体验同时验证。

参考：[Vue Performance](https://vuejs.org/guide/best-practices/performance.html)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="vue15-01"></a>

### VUE15-01 [P0·工程取舍] 十万条Vue列表卡顿怎样排查和处理？

**回答：** 先看计算、响应式和DOM各占多少，通常应减少同时渲染节点，采用分页或虚拟化，再优化数据结构和依赖。key、computed或nextTick都不能单独解决海量DOM。

对应讲解：[大列表、虚拟化与异步组件](#k03)。

<a id="vue15-02"></a>

### VUE15-02 [P1·原理] shallowRef为什么可能更省成本，有什么代价？

**回答：** 它减少深层代理和依赖跟踪，但内部变更不会按普通深响应式自动通知。使用方要通过替换或明确触发管理更新，不能只换API不改数据契约。

对应讲解：[数据与响应式粒度](#k02)。

<a id="vue15-03"></a>

### VUE15-03 [P1·工程取舍] v-memo能到处加吗？

**回答：** 不能，依赖列表必须覆盖子树真正变化条件，漏项会出现陈旧UI。先量出值得优化的更新，再验证数据与交互正确性。

对应讲解：[v-once、v-memo、KeepAlive 与验证](#k04)。

<a id="vue15-04"></a>

### VUE15-04 [P0·工程取舍] 如何证明优化有效？

**回答：** 在相同数据和设备条件下对比生产模式指标、长任务、输入延迟和内存，再结合现场分群数据；同时回归列表状态、取消和错误路径，避免用错误结果换速度。

对应讲解：[测量与更新范围](#k01)。
