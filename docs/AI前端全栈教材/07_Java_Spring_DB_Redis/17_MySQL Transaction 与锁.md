## 二、知识讲解

<a id="k01"></a>

### 1. ACID 与隔离

原子性让事务作为提交单元，一致性需约束与正确业务逻辑配合，隔离性定义并发观察，持久性与日志、存储和提交配置有关。普通本地事务不自动覆盖所有外部系统。

READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ和SERIALIZABLE具有不同语义；InnoDB常见默认RR，但项目可改变。具体异常现象还要结合数据库实现与读方式。

<a id="k02"></a>

### 2. MVCC、快照与当前读

MVCC通过版本和可见性规则支持一致性读取，降低部分读写阻塞。RC通常按语句建立相应快照，RR的一致性读通常在事务中复用快照；显式一致性快照和自身写入又有具体规则。

SELECT ... FOR UPDATE等锁定读及UPDATE/DELETE观察和保护当前数据，不能直接套普通快照读的模型。看到旧值可能是隔离契约，而非数据库更新失败。

长事务会延长旧版本保留，增加undo等维护压力，不能为了“前端操作全程一致”长期持有事务。

<a id="k03"></a>

### 3. 记录、间隙与扫描范围

InnoDB锁围绕索引记录和范围，record/gap/next-key在不同条件和隔离级别下出现。唯一等值定位与范围查询不同，缺少索引可能扩大扫描及锁范围。

不要将没用索引简化为必然升级一个表锁。要看实际扫描、锁类型和引擎行为，range保护与幻读控制也需区分快照读和当前读。

统一加锁顺序、缩短事务、合理索引以及避免慢外部调用，可降低争用和死锁概率。

<a id="k04"></a>

### 4. 乐观锁、死锁与重试

```sql
UPDATE app_user
SET nickname = 'new-name', version = version + 1
WHERE id = 1 AND version = 3;
```

旧version条件限制覆盖，0行需按契约区分不存在或冲突；不是所有冲突都适合自动重试。

T1持A等B、T2持B等A可形成死锁，数据库通常回滚其中一个。应用按预算重试合适完整事务并保护副作用幂等，不无限循环或只重发中间SQL。

结合死锁日志、等待时间、事务时长和索引计划验证，不能用降低隔离级别解决一切。

<a id="summary"></a>

## 三、知识小结

隔离管可见性，MVCC管版本，锁保护当前操作与范围，版本号表达乐观冲突。短事务、索引与有界重试共同支撑正确并发。

参考：[MySQL InnoDB Transactions](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="java17-01"></a>

### JAVA17-01 [P0·原理] 快照读与FOR UPDATE有什么区别？

**回答：** 一致性读按版本规则读取，锁定读关注当前数据并获取相应锁。即便同一隔离级别，阻塞和可见行为也不能混为一谈。

对应讲解：[MVCC、快照与当前读](#k02)。

<a id="java17-02"></a>

### JAVA17-02 [P1·原理] 行锁是不是永远只影响一行？

**回答：** 不是，锁与索引记录、范围和计划有关，范围扫描可能有间隙或next-key保护。应看实际条件和执行路径。

对应讲解：[记录、间隙与扫描范围](#k03)。

<a id="java17-03"></a>

### JAVA17-03 [P0·工程取舍] 死锁重试应注意什么？

**回答：** 优先减少不一致锁顺序和长事务，失败后按预算重做合适事务并保证外部副作用幂等。无限重试或仅重发中间SQL可能破坏语义。

对应讲解：[乐观锁、死锁与重试](#k04)。

<a id="java17-04"></a>

### JAVA17-04 [P1·原理] 版本号更新怎样防止丢失修改？

**回答：** WHERE带旧version并原子递增，只有仍匹配的更新成功。冲突时需重新读取、提示或合并，不能把0行无条件当普通成功。

对应讲解：[乐观锁、死锁与重试](#k04)。

<a id="java17-05"></a>

### JAVA17-05 [P0·原理] ACID里的业务一致性能只靠事务自动得到吗？

**回答：** 不能，事务提供原子与隔离等机制，合法业务事实还需正确逻辑和数据库约束。外部HTTP等资源不自动纳入本地事务，持久保证也依存储和配置。

对应讲解：[ACID 与隔离](#k01)。
