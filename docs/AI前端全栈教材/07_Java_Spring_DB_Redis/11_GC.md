# 11 垃圾回收、停顿与内存排查

GC自动回收不可达对象，但业务仍要管理数据保留和外部资源。理解收集器的目的与测量方法，比背一个固定回收流程更实用。

## 二、知识讲解

<a id="k01"></a>

### 1. 可达性与引用类型

GC从根引用出发判断对象可达性，根可包括活动线程相关引用、静态关联和JNI等。循环引用若整体不可达仍可回收，不需要像引用计数模型那样必然泄漏。

强引用、软引用、弱引用和虚引用各有用途与时机约束，不能依赖弱/软引用实现可靠缓存时效或资源关闭。终结机制也不适合承诺何时释放连接或保存业务数据。

长期Map、监听、ThreadLocal、类加载器和缓存可能让已经无业务价值的数据继续可达。

<a id="k02"></a>

### 2. 分代假设与收集工作

很多对象很快死亡，分代策略利用这一经验减少每次扫描成本；写屏障、记忆集等帮助处理跨区域引用。并非所有JDK版本或收集器都采用完全相同代结构。

标记、复制、清理、压缩及并发阶段解决不同问题，某些阶段仍需暂停。Minor/Major/Full等术语在不同收集器资料中含义可能不同，应结合GC日志事件而非只背名字。

<a id="k03"></a>

### 3. G1、ZGC 与选择条件

G1以region组织堆并围绕停顿目标调度回收工作，ZGC等方案强调低停顿并发处理，但具体代际模式、功能和默认值随JDK版本变化。Java17、21及后续版本不能把所有GC行为当成同一套。

选择基于堆大小、吞吐、延迟目标、CPU余量和可运维性，低停顿并不等于完全无暂停或零CPU开销。通常先确认分配和保留问题，再考虑换收集器。

<a id="k04"></a>

### 4. 日志、泄漏与验收

```text
Java 17及适配环境的日志示意：
-Xlog:gc*:file=gc.log:time,uptime,level,tags
```

结合分配速率、GC频率、停顿分布、回收后基线和业务延迟。内存上升后能稳定回落可能是正常负载，长期回收后基线持续抬升更值得查保留对象。

堆分析追引用链到实际所有者，ThreadLocal和缓存需检查清理策略；数据库连接、文件和线程池用明确close/shutdown管理，不交给GC。修复后重复同负载和长时运行验证。

<a id="summary"></a>

## 三、知识小结

GC按可达性回收，分代与并发是实现策略，日志给出实际行为。先消除无效保留和资源失控，再在版本与目标约束下调收集器。

## 四、面试题与答案

<a id="java11-01"></a>

### JAVA11-01 [P0·原理] 为什么循环引用不必然内存泄漏？

**回答：** 可达性回收从根出发，如果整组互相引用对象都不可达就可回收。真正问题是不再需要的对象仍被根可达路径保留。

对应讲解：[可达性与引用类型](#k01)。

<a id="java11-02"></a>

### JAVA11-02 [P1·基础] GC为什么常用分代？

**回答：** 利用很多对象短命、少数长期存活的经验，减少反复全堆处理。具体代结构和跨代引用维护随收集器与JDK版本变化。

对应讲解：[分代假设与收集工作](#k02)。

<a id="java11-03"></a>

### JAVA11-03 [P1·工程取舍] 换成低停顿GC能自动解决内存泄漏吗？

**回答：** 不能，仍可达的无用对象不会因换算法就消失。低停顿目标也有CPU和版本约束，应先定位保留链与分配问题。

对应讲解：[G1、ZGC 与选择条件](#k03)。

<a id="java11-04"></a>

### JAVA11-04 [P1·工程取舍] 如何证明内存问题修复？

**回答：** 用相同负载和长时场景比较回收后基线、保留对象、停顿和业务延迟，检查异常与取消路径。一次手工GC或重启后下降不足以证明根因已消除。

对应讲解：[日志、泄漏与验收](#k04)。
