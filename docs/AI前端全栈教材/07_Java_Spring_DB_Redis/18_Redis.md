# 18 Redis 结构、缓存与分布式协作

Redis提供内存数据结构及命令语义，适合缓存、计数和短期协调。可靠性需结合容量、持久化、复制与业务一致性设计。

## 二、知识讲解

<a id="k01"></a>

### 1. 结构与命令

| 结构 | 常见操作 | 场景 |
| --- | --- | --- |
| String | GET/SET、INCR、EXPIRE | 值缓存、计数 |
| Hash | HGET/HSET/HGETALL | 对象字段 |
| List | LPUSH/RPOP等 | 有序队列式数据 |
| Set | SADD/SISMEMBER等 | 唯一成员 |
| ZSet | ZADD/ZRANGE等 | 排名与分数范围 |
| Stream | XADD/XREADGROUP/XACK | 可追踪消费日志 |
| Pub/Sub | PUBLISH/SUBSCRIBE | 在线通知，非同等持久重放 |

单命令原子不等于多个命令自动事务一致。Lua、事务和集群键槽有边界；后台与IO也有线程实现，不能一句“单线程”解释所有性能。大key、热key和慢命令仍可能拖累延迟。

<a id="k02"></a>

### 2. Cache Aside 与故障

读缓存未命中后查DB回填，写入常先提交DB再使缓存失效。该顺序减少一些失败窗口，却不保证强一致：旧读请求仍可能迟到回填。

穿透是不存在数据反复回源，可配校验、短期空值和过滤；热点到期集中回源需去重/互斥重建；大量同时失效或Redis故障需TTL抖动、限流和降级。

删除重试、outbox/事件或版本校验可改善一致性，延迟双删不是万能证明。key包含租户、参数和必要权限范围，退出和权限改变也要考虑失效。

<a id="k03"></a>

### 3. 容量、持久化与复制

RDB快照、AOF及fsync策略有不同性能和丢失窗口，复制与故障切换也影响确认语义。命令返回成功不等于所有副本和磁盘都已绝对持久。

maxmemory与淘汰策略限制容量，过期与淘汰不同，TTL不是有界内存充分条件。监控命中率、内存、延迟、复制滞后、大key和连接，恢复需演练。

缓存可丢失重建，账务或长任务权威状态不宜只依赖无明确持久契约的缓存。

<a id="k04"></a>

### 4. 租约锁、限流与消费

```text
获取锁：
SET lock:job:1 unique-owner-token NX PX 30000

释放：
原子比较所有者token后删除，而非GET后独立DEL。
```

token防误删，租约需考虑超时、续期和网络分区；锁过期后旧持有者仍可能执行，严格外部资源保护还可能需要fencing token及下游版本检查。

限流要明确窗口/桶与原子更新，集群跨键操作有槽限制。Pub/Sub可能丢在线外消息，Stream需pending恢复、确认、重投和幂等，不能只把“消息有序”当业务恰好执行一次。

<a id="summary"></a>

## 三、知识小结

Redis先选结构和原子边界，再设计缓存时效、容量与恢复。锁是租约协调，消息需确认和幂等，持久化与复制决定真实故障语义。

参考：[Redis Documentation](https://redis.io/docs/latest/)；[Redis Locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="java18-01"></a>

### JAVA18-01 [P0·工程取舍] 为什么常先写DB再删缓存？

**回答：** 先让DB形成权威结果，再失效旧缓存，可减少DB失败却缓存已更新的问题。但并发旧读回填和删除失败仍需版本、重试或事件机制。

对应讲解：[Cache Aside 与故障](#k02)。

<a id="java18-02"></a>

### JAVA18-02 [P1·原理] SET NX PX是否就足够实现强一致锁？

**回答：** 不够，还需所有者校验、原子释放、超时续期与故障语义。过期旧持有者可能继续写，严格场景需下游fencing或版本保护。

对应讲解：[租约锁、限流与消费](#k04)。

<a id="java18-03"></a>

### JAVA18-03 [P0·基础] 穿透、热点失效与雪崩怎么区分？

**回答：** 分别关注不存在数据反复回源、热点到期集中回源、大量过期或服务故障。对应校验过滤、去重重建、抖动限流降级，不由一个锁统一解决。

对应讲解：[Cache Aside 与故障](#k02)。

<a id="java18-04"></a>

### JAVA18-04 [P1·工程取舍] Pub/Sub与Stream差异是什么？

**回答：** Pub/Sub偏在线即时通知，Stream支持日志和消费组追踪确认。但Stream仍需恢复pending、重投与业务幂等，不能自动保证每个副作用只发生一次。

对应讲解：[结构与命令](#k01)。

<a id="java18-05"></a>

### JAVA18-05 [P1·原理] Redis命令成功是否等于所有副本和磁盘已持久？

**回答：** 不必然，AOF/RDB、fsync、复制与故障切换有各自确认和丢失窗口。缓存与权威数据的可靠性要求不同，应按实际配置和恢复演练判断。

对应讲解：[容量、持久化与复制](#k03)。
