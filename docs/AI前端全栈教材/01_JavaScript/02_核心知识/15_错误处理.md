# 15 错误处理

错误处理首先是控制流问题：错误在哪一条执行路径出现，谁有能力恢复，谁负责清理。把所有异常catch掉不等于系统更可靠。

## 二、知识讲解

<a id="k01"></a>

### 1. Error、cause 与分类

throw可以抛任意值，但Error对象通常更适合保留message、name、cause与调试栈。stack具体字符串格式不是ECMAScript统一保证的业务协议。

| 类型 | 典型情形 |
| --- | --- |
| TypeError | 调用非函数、非法类型操作 |
| ReferenceError | 未声明名字、TDZ |
| RangeError | 数值或长度越界 |
| SyntaxError | 语法不合法、JSON.parse失败 |
| URIError | 非法URI编解码 |
| AggregateError | 多个错误，如Promise.any全失败 |
| Error | 通用错误或自定义业务基类 |
| EvalError | 历史类型，现代日常少用 |

```js
try { JSON.parse('{bad'); }
catch (cause) {
  const error = new Error('配置解析失败', { cause });
  console.log(error.cause instanceof SyntaxError); // true
}
```

包装错误应保留原因，而不是只换成“失败了”。对外返回稳定错误码和安全文案，内部保留诊断信息，不向用户暴露SQL、密钥或内部路径。

<a id="k02"></a>

### 2. try/catch/finally 的结果传播

try捕获沿当前执行流程传播的异常。catch可以恢复、转换后继续抛或直接再抛；正常返回表示流程继续成功。finally在正常、return、throw路径上执行，但进程终止等情况不能保证任何JS清理都来得及。

```js
function result() {
  try { return 1; }
  finally { return 2; }
}
console.log(result()); // 2
```

finally的return/throw会覆盖先前结果，通常应只做清理。清理也失败时，要明确保留哪个错误或记录次要错误。同文件解析阶段的语法错误不能靠文件正文中的try自动补救。

<a id="k03"></a>

### 3. 异步错误与当前执行路径

try{setTimeout(callback)}catch{}包围的是注册定时器这个同步过程；未来callback抛错时，原try已经结束。因此需要在回调内部处理或用Promise适配并接管拒绝。

```js
async function work() { throw new Error('failed'); }
async function caller() {
  try { return await work(); }
  catch (error) { return error.message; }
}
console.log(await caller()); // failed
```

async函数抛错变成Promise拒绝，await或catch让调用者接管。return promise与return await在本地catch/finally中有区别；全局error/unhandledrejection适合观测，不替代业务层决定重试、降级或提示。

<a id="k04"></a>

### 4. 业务错误、取消和资源所有权

区分输入不合法、权限拒绝、冲突、暂时网络故障与用户取消。取消通常应显示停止状态，不能总弹服务器错误；重试要看类别、幂等性和预算。

跨HTTP传输后通常只是JSON数据，不能指望服务端Error原型在浏览器仍保留。稳定code、字段信息和可追踪requestId比匹配message文案可靠。

清理应由明确所有者负责：谁创建timer、订阅、reader或Worker，谁在完成、失败、取消和卸载路径释放。reader.releaseLock只释放读取锁，不等于服务器任务已经取消。

<a id="summary"></a>

## 三、知识小结

错误链按“抛出位置→传播路径→恢复决策→清理→观测”分析。不要让catch默认值或finally新异常把真实失败伪装掉。

参考：[MDN 控制流与错误处理](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Control_flow_and_error_handling)。较新 API 按目标运行时核对支持，示例各自独立。

## 四、面试题与答案

<a id="c15-01"></a>

### C15-01 [P0·原理] try/catch为什么抓不到timer回调错误？

**回答：** 原try只在同步注册阶段存在，未来回调属于另一执行流程。应在回调内部处理，或通过能正确reject的Promise适配再await/catch。源码缩进包住不代表时间上一直包住。

对应讲解：[异步错误与当前执行路径](#k03)。

<a id="c15-02"></a>

### C15-02 [P1·原理] finally中的return或throw会怎样？

**回答：** 会覆盖先前try/catch的完成结果，可能把本来成功改失败，或把异常变成成功返回。清理也可能抛错，必须决定如何保留原故障。

对应讲解：[try/catch/finally 的结果传播](#k02)。

<a id="c15-03"></a>

### C15-03 [P1·基础] 为什么建议抛Error而不是字符串？

**回答：** Error提供标准的信息承载方式，可附加cause保留底层原因，也更利于日志和调试。字符串缺少结构与来源，跨边界仍应转成明确的业务错误协议。

对应讲解：[Error、cause 与分类](#k01)。

<a id="c15-04"></a>

### C15-04 [P1·工程取舍] 所有错误都catch后重试有什么问题？

**回答：** 可能把权限、输入错误和不可幂等操作反复执行，增加负载或重复副作用；catch返回默认值还可能伪装成功。应分类、设置预算，只有可恢复的错误才按策略处理，取消与系统失败也要区别。

对应讲解：[业务错误、取消和资源所有权](#k04)。
