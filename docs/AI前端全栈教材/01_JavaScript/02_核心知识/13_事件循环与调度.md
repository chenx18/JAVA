# 13 事件循环与调度

事件循环协调当前执行、已经就绪的回调与宿主任务。先声明浏览器或Node环境，再逐步记录入队时间；“微任务优先”只能在具体检查点与就绪条件下解释。

## 二、知识讲解

<a id="k01"></a>

### 1. 主线程、调用栈与宿主工作

通常讨论的浏览器页面主线程同一时刻执行一段JS，同步函数调用入栈，返回后出栈。浏览器仍可协调网络、计时和其他工作，不是整个浏览器只能做一件事。

异步条件满足后，回调按宿主规则被调度，不会直接插入正在运行的同步函数。长循环因此能延后点击响应和timer，即使点击已经发生或计时早已满足。

Worker可以在另一执行线程工作，但不能直接修改页面DOM；主线程预算与通信成本仍然存在。

<a id="k02"></a>

### 2. Task、Microtask 与渲染机会

timer、用户交互和部分网络事件是常见task来源；Promise reaction与queueMicrotask是常见微任务。教学上常说“宏任务”，HTML规范通常使用task。

常见浏览器脚本可先按如下模型分析：

```text
运行当前同步代码/任务
  → 到微任务检查点，处理已入队微任务并继续处理其中新增的微任务
  → 浏览器在合适时机可能更新渲染
  → 调度后续就绪任务
```

这不是所有事件的全局固定队列：浏览器有多个任务源，渲染不保证每个任务后都发生，微任务检查点也不只教学图的一处。timer延迟只表示最早可调度条件，不保证精确到点。requestAnimationFrame参与渲染阶段相关调度，不应在缺少条件时硬排在所有timer前或后。

<a id="k03"></a>

### 3. 用队列表推导输出

```js
const output = [];
output.push('A');
setTimeout(() => output.push('T'), 0);
Promise.resolve().then(() => {
  output.push('P');
  queueMicrotask(() => output.push('Q'));
});
(async () => {
  output.push('B');
  await 0;
  output.push('C');
})();
output.push('D');
await new Promise(resolve => setTimeout(resolve, 20));
console.log(output); // ['A','B','D','P','C','Q','T']
```

末尾等待仅用于收集输出；例子在普通浏览器module或独立Node运行中，不加入其他业务任务源。

| 阶段 | 已输出 | 待处理相关微任务 |
| --- | --- | --- |
| 同步代码完成 | A B D | P、C |
| P运行，创建Q | A B D P | C、Q |
| C运行 | A B D P C | Q |
| Q运行 | A B D P C Q | 空 |
| timer获得执行 | A B D P C Q T | — |

Q虽然在Promise回调里创建，仍是在P运行时才入队，不能越过已经排队的C。若Promise要等未来timer才兑现，它的then当然不可能提前于兑现任务执行。

<a id="k04"></a>

### 4. 微任务饥饿、分片与rAF

不断安排下一微任务可能让检查点长时间无法结束，从而延后绘制和后续任务。循环await Promise.resolve()也可能是同类问题，它不是通用“让页面刷新”的语句。

CPU工作可切成有界小块，在支持时用scheduler.yield等协作调度，或通过任务级方式分片；合适的独立重计算可放Worker。rAF适合合并视觉更新，但其中的重计算仍阻塞主线程。

rAF频率受刷新率、主线程负载和页面可见性影响，后台页可能暂停。数据接收与持久化不应完全绑在rAF中，最终状态和资源清理也不能依赖“下一帧一定马上来”。

<a id="k05"></a>

### 5. Node 的 nextTick 与阶段差异

Node有timer、poll、check等阶段，setImmediate位于check，process.nextTick有特殊处理队列。libuv/Node版本还会影响timer相对阶段的细节。

例如典型CommonJS顶层代码中nextTick通常先于Promise微任务；ESM顶层自身处于异步求值背景，顺序可能不同。顶层setTimeout(0)与setImmediate不应承诺固定顺序；在特定I/O回调内又可有不同结论。

回答跨端题先给Node版本、CJS/ESM与调用位置，再实测。不要用“微任务永远先于宏任务”跳过宿主阶段和当前执行背景。

<a id="summary"></a>

## 三、知识小结

输出题画同步轨迹与微任务队列，标出任务何时就绪；性能题找连续占用主线程的工作，再选分片、rAF或Worker。浏览器与Node分别限定环境。

参考：[javascript.info 事件循环](https://javascript.info/event-loop)；[Node 事件循环](https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick)。较新 API 按目标运行时核对支持，示例各自独立。

## 四、面试题与答案

<a id="c13-01"></a>

### C13-01 [P0·原理] then一定比setTimeout先执行吗？

**回答：** 不是无条件。对同一普通脚本中已兑现Promise注册then，通常在同步代码后微任务检查点执行，早于后续timer任务；但若Promise要靠未来timer兑现，就必须先等那个timer。还要说明宿主环境。

对应讲解：[Task、Microtask 与渲染机会](#k02)。

<a id="c13-02"></a>

### C13-02 [P0·原理] Promise回调中新建微任务为什么不插队？

**回答：** 微任务按实际入队关系处理，回调执行期间新加入的任务通常排在已经等待的任务后面。应记录队列变化，而不是按代码嵌套层数判断优先级。

对应讲解：[用队列表推导输出](#k03)。

<a id="c13-03"></a>

### C13-03 [P0·工程取舍] await Promise.resolve为什么仍会让页面卡住？

**回答：** 它通常只续接微任务，微任务检查点不断有新任务时可能延后渲染。并且await前后的同步计算仍在主线程。需要任务级分片或Worker，视觉更新再用rAF组织。

对应讲解：[微任务饥饿、分片与rAF](#k04)。

<a id="c13-04"></a>

### C13-04 [P1·原理] rAF回调是不是每16.7ms必执行？

**回答：** 不是，取决于刷新率、主线程负载、页面可见性与渲染调度。不能把它当精确计时器，后台页业务完成和持久化也不能依赖下一次rAF。

对应讲解：[微任务饥饿、分片与rAF](#k04)。

<a id="c13-05"></a>

### C13-05 [P1·原理] Node nextTick、Promise、setImmediate怎么比较？

**回答：** 要给出版本、模块模式和执行位置。nextTick有特殊队列，Promise是微任务，setImmediate参与check阶段；ESM顶层和I/O回调场景可能改变可观察顺序，不能直接搬浏览器口诀。

对应讲解：[Node 的 nextTick 与阶段差异](#k05)。
