## 二、知识讲解

<a id="k01"></a>

### 1. 请求归属与版本检查

用户先搜索A再搜索B，B先返回，A后返回。若每次完成都直接覆盖结果，界面最后显示过时的A。发起顺序与完成顺序本来就不保证一致。

每次运行递增version，请求保存自己的版本；提交前确认仍等于当前版本。新请求启动时还可abort旧请求减少资源浪费，但取消是协作信号，旧请求可能已完成、正在解析或不支持取消。

旧任务的catch/finally也不能随意清掉新任务的loading或controller。流式每条delta都要核验归属，而不是仅在全部结束后检查。多会话并行时按会话管理各自运行器，不能用一个全局版本误杀其他会话。

<a id="k02"></a>

### 2. 从字节到业务事件

```text
fetch/ReadableStream
  → Uint8Array字节块
  → TextDecoder增量解码
  → 文本残片缓冲，按协议分行/分帧
  → 完整事件data
  → JSON.parse与schema校验
  → 校验会话ID/版本/事件序号
  → 更新业务状态
  → 按帧或节流更新视觉
```

一个chunk不等于一个字符、不等于一条SSE事件、不等于一个JSON对象，也不等于一个模型token。每层先保留未完成片段，只有边界完整才交给下一层。

TextDecoder.decode(chunk,{stream:true})保留半字符，结束时decode()刷新。fatal:true使非法编码显式失败；根据协议选择策略，不能默默把损坏的数据当成功。

<a id="k03"></a>

### 3. SSE 与 EventSource

SSE以文本字段行表示事件，空行结束一条事件；多条data行按换行连接，冒号开头常作注释/心跳，还可有event/id/retry。换行和块边界没有一一对应关系。

浏览器EventSource通常以GET建连接并提供SSE处理/重连能力，不能像fetch一样任意设置Authorization头或POST JSON。需要这些能力时常用fetch加解析器，但认证、重连、断点恢复等就需自行设计。

文末解析器是明确的教学子集：支持LF/CRLF、注释、多行data，忽略event/id/retry，不支持单独CR，不实现重连。生产通用SSE应选合规解析库并补协议测试，不能把子集冒充完整标准。

<a id="k04"></a>

### 4. 成功、断流、取消与超时

HTTP200表示响应头阶段成功；EOF表示字节流结束；业务done表示应用协议确认完成。它们是三个不同层次。本章约定缺少done就EOF判为中断，保留部分内容并给恢复选择；其他协议可有别的完成规则，但必须明确。

连接、首数据、空闲和总时长超时分别控制不同等待。收到响应头后不能清除所有后续超时。取消还应传到服务端和底层模型/任务；前端abort不保证账单或副作用立即停止。

重试可能重复任务，需要服务端幂等键、任务状态查询和恢复游标。客户端版本校验仅防止旧结果提交，不撤销已经完成的服务器写入。

<a id="k05"></a>

### 5. 缓冲、背压、渲染与可观测性

缓冲应有上限，按协议限制事件大小与未完成片段；大小上限是资源保护，不等于已经建立了端到端背压。生产节奏是否会随消费者变慢而调整，还取决于网络、服务端与模型链路。

接收与业务状态持续推进，视觉可按rAF/节流合并。用户已离开列表底部时不要强制自动滚动；后台rAF可能暂停，完成、错误和持久化不能依赖绘制回调。

日志使用requestId、任务ID和事件序号串起客户端与服务端，记录首数据时间、总时长、取消原因、错误层次和合理成本指标。只记录“接口200”不足以观察流式可靠性。

<a id="summary"></a>

## 三、知识小结

取消节约资源，版本检查保护状态；解码处理字节，分帧处理消息，schema处理结构，done处理协议结束。每一层的状态和清理都有明确所有者。

参考：[MDN Readable streams](https://developer.mozilla.org/en-US/docs/Web/API/Streams_API/Using_readable_streams)；[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。较新 API 按目标运行时核对支持，示例各自独立。

## 四、面试题与答案

<a id="c19-01"></a>

### C19-01 [P0·编码] 实现只允许最新请求提交的控制器。

**回答：** 下例先递增版本再取消旧请求，提交和失败都检查归属，finally只清理自己仍拥有的controller。task接收signal，commit约定同步提交；不响应取消的任务完成后也会被版本检查拦截。

```js
function createLatestRunner() {
  let version = 0, controller = null;
  return {
    async run(task, commit) {
      const current = ++version;
      controller?.abort();
      const own = new AbortController();
      controller = own;
      try {
        const value = await task(own.signal);
        if (current !== version || own.signal.aborted) return 'stale';
        commit(value);
        return 'committed';
      } catch (error) {
        if (current !== version || own.signal.aborted) return 'stale';
        throw error;
      } finally {
        if (controller === own) controller = null;
      }
    },
    cancel() {
      version++;
      controller?.abort();
      controller = null;
    }
  };
}
```

**追问与回答：** 测试A慢/B快、旧请求失败、新请求成功、取消后完成和commit抛错。流式每条增量也要同样检查。

对应讲解：[请求归属与版本检查](#k01)。

### C19-02 [P1·编码] 怎样处理SSE事件跨chunk与多行data？

**回答：** 先增量解码，再积累行和data，空行才派发完整payload。下例限制未完成行和事件的码元量；finish丢弃不完整尾部，由业务层判断是否缺少完成事件。它只支持正文声明的SSE子集。

```js
function createSseParser(onData, maxChars = 65536) {
  if (typeof onData !== 'function' || !Number.isSafeInteger(maxChars) || maxChars < 1) throw new TypeError('invalid parser');
  let buffer = '', data = [], size = 0;
  function consumeLine(line) {
    if (line.length > maxChars) throw new Error('line too large');
    if (line === '') {
      const payload = data.join('\n'), present = data.length > 0;
      data = []; size = 0;
      if (present) onData(payload);
      return;
    }
    if (line.startsWith(':')) return;
    const colon = line.indexOf(':');
    const field = colon < 0 ? line : line.slice(0, colon);
    let value = colon < 0 ? '' : line.slice(colon + 1);
    if (value.startsWith(' ')) value = value.slice(1);
    if (field === 'data') {
      size += value.length + 1;
      if (size > maxChars) throw new Error('event too large');
      data.push(value);
    }
  }
  return {
    push(text) {
      buffer += text;
      let index;
      while ((index = buffer.indexOf('\n')) >= 0) {
        const line = buffer.slice(0, index).replace(/\r$/, '');
        buffer = buffer.slice(index + 1);
        consumeLine(line);
      }
      if (buffer.length > maxChars) throw new Error('buffer too large');
    },
    finish() { buffer = ''; data = []; size = 0; }
  };
}
```

**追问与回答：** 测试逐字节输入中文、一个块多事件、CR/LF跨块、多行data、注释、超长事件和未结束尾部。

对应讲解：[SSE 与 EventSource](#k03)。

### C19-03 [P1·编码] HTTP200后断流，怎样确认成功？

**回答：** 下面消费器依赖上一题createSseParser，约定JSON事件为delta/text、done、error/message。它检查HTTP和内容类型、增量解码、校验事件，只有done才成功，finally释放reader。请求signal由fetch调用层传入，本函数不自行创建整套超时。

```js
async function consumeSse(response, onDelta) {
  if (!response.ok) throw new Error('HTTP ' + response.status);
  if (!response.headers.get('content-type')?.includes('text/event-stream') || !response.body) {
    throw new Error('expected SSE');
  }
  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8', { fatal: true });
  let completed = false;
  const parser = createSseParser(payload => {
    if (completed) return;
    const event = JSON.parse(payload);
    if (event === null || typeof event !== 'object') throw new Error('invalid event');
    if (event.type === 'delta' && typeof event.text === 'string') onDelta(event.text);
    else if (event.type === 'done') completed = true;
    else if (event.type === 'error' && typeof event.message === 'string') throw new Error(event.message);
    else throw new Error('invalid event schema');
  });
  try {
    while (!completed) {
      const { value, done } = await reader.read();
      if (done) { parser.push(decoder.decode()); break; }
      parser.push(decoder.decode(value, { stream: true }));
    }
    parser.finish();
    if (!completed) throw new Error('stream ended before done');
  } finally {
    try { await reader.cancel(); } catch { /* 清理不覆盖业务错误。 */ }
    reader.releaseLock();
  }
}
```

**追问与回答：** EOF不等于成功，解析失败和非法UTF-8也不能作为正常完成。生产还需处理重连游标、去重、超时及后端取消。

对应讲解：[成功、断流、取消与超时](#k04)。

### C19-04 [P1·工程取舍] rAF合并显示能解决流式背压吗？

**回答：** 只调整视觉刷新节奏，不保证接收缓冲有界或服务端减速。要分别限制缓冲、控制消费、设计生产反馈和恢复协议；后台页面业务完成与持久化也不能等待rAF才处理。

对应讲解：[缓冲、背压、渲染与可观测性](#k05)。

<a id="c19-05"></a>

### C19-05 [P1·工程取舍] 停止旧请求为何还需requestId和幂等键？

**回答：** requestId/版本保护客户端结果归属；幂等键由服务端约束重复操作；abort尝试停止不再需要的工作。它们处理的层次不同，取消既不保证阻止迟到回调，也不撤销服务器已提交副作用。

对应讲解：[成功、断流、取消与超时](#k04)。
