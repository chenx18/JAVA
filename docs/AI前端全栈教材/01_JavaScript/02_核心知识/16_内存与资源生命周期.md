# 16 内存与资源生命周期

内存问题要从可达性与业务生命周期解释。对象已经不需要，但仍有引用保留它，才是应排查的重点；一次内存升高不等于泄漏。

## 二、知识讲解

<a id="k01"></a>

### 1. 可达性与垃圾回收

现代JavaScript引擎主要根据从根对象和活动执行状态出发的可达关系判断对象是否还有必要保留。不可达的环也可以回收，循环引用本身不等于泄漏。

引擎可能使用分代、标记清除、增量/并发回收和压缩等策略，具体机制和时机取决于引擎版本，不是ECMAScript固定要求“所有变量都用某一种GC算法”。

将某变量设为null只是移除一条引用，不能保证对象没有其他路径。局部函数返回也不保证闭包所需数据被立即回收；反过来，引擎可能优化不需要保留的环境内容，不能据源码猜确切物理占用。

<a id="k02"></a>

### 2. 典型保留链与清理

```text
window → resize监听器 → 闭包环境 → 大数组/已移除节点
模块变量 → Map缓存 → 用户记录
定时器/订阅 → 回调 → 页面状态
```

移除DOM不自动删除注册在window上的监听；清空界面不自动取消请求；给变量换值也不一定清除缓存中的旧引用。

```js
function mount(target) {
  const rows = new Array(10000).fill('row');
  const handler = () => rows.length;
  target.addEventListener('resize', handler);
  return () => target.removeEventListener('resize', handler);
}
```

返回的清理函数由组件卸载或所有者结束路径调用。需要同一个listener引用和匹配capture；反复bind得到新函数会导致解绑失败。

<a id="k03"></a>

### 3. 资源不只是JS对象

| 资源 | 常见释放 |
| --- | --- |
| timer | clearTimeout/clearInterval |
| 事件监听 | removeEventListener或signal取消 |
| Observer | disconnect/unobserve |
| 网络与流 | 传播取消、reader.cancel、releaseLock按所有权执行 |
| Worker | terminate并结算待处理任务 |
| Blob URL | URL.revokeObjectURL |
| 订阅/连接 | unsubscribe/close等协议方法 |

这些清理应覆盖成功、失败、取消和卸载。GC负责回收内存，不承担“业务连接应何时关闭”的可靠调度。FinalizationRegistry不能替代明确生命周期。

<a id="k04"></a>

### 4. 容量、TTL、LRU 与弱引用

容量决定最多保留多少条或字节，TTL决定数据多久有效，LRU决定优先淘汰最近最少使用的项，WeakMap让元数据不单独延长对象键寿命。

只在get时发现过期再删除，可能让永不再访问的旧项一直占位；需要容量或周期清理补充。条目数上限也不等于固定内存上限，一个值可能很大。

文末LRU使用Map迭代顺序，每次get删除再插入刷新位置，set后超过容量则删最旧键。不包含TTL、字节预算、持久化或并发多进程一致性。

<a id="k05"></a>

### 5. 排查与证明修复

固定操作序列，例如重复进入/离开页面、发送/取消请求；在可比较的空闲阶段看内存基线和对象数量，而不是只看瞬时峰值。

Heap Snapshot找持续增加的对象，沿Retainers追溯谁持有它；关注Detached DOM、监听器、timer、订阅、缓存和闭包。DevTools控制台记录也可能保留对象，排查时避免制造新的观察干扰。

修复后重复相同次数和异常路径，验证不再每轮积累保留对象；单次手动GC使数字下降不能证明问题彻底解决。线上还要关注长会话、断网和卸载过程中未结束任务。

<a id="summary"></a>

## 三、知识小结

泄漏回答用证据链：复现→观察趋势→定位保留对象→追根引用→清理所有者→重复验证。容量、时效、淘汰顺序和弱引用分别管理不同维度。

参考：[MDN Memory management](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Memory_management)。较新 API 按目标运行时核对支持，示例各自独立。

## 四、面试题与答案

<a id="c16-01"></a>

### C16-01 [P0·原理] 循环引用或闭包一定泄漏吗？

**回答：** 不一定。现代可达性回收能处理从根不可达的环，闭包也只是保留所需环境。要看业务不再需要的数据是否仍被全局监听、缓存等强引用长期保留。

对应讲解：[可达性与垃圾回收](#k01)。

<a id="c16-02"></a>

### C16-02 [P0·工程取舍] 如何排查页面越用越占内存？

**回答：** 固定重复操作和空闲观察点，对比快照对象数量与保留大小，沿Retainers找到根引用，再修复监听/订阅/缓存等所有者。用同样操作和失败/取消路径复测，不只看一次GC后的数字。

对应讲解：[排查与证明修复](#k05)。

<a id="c16-03"></a>

### C16-03 [P1·编码] 实现容量有界的LRU缓存。

**回答：** 下例依赖Map插入顺序，访问时移动到末尾，超容量删除开头。has区分缺失键与值为undefined；不包含TTL、字节计费或持久化，生产按场景补充。

```js
class LRU {
  constructor(capacity) {
    if (!Number.isSafeInteger(capacity) || capacity < 1) throw new RangeError('positive capacity required');
    this.capacity = capacity;
    this.cache = new Map();
  }
  has(key) { return this.cache.has(key); }
  get(key) {
    if (!this.cache.has(key)) return undefined;
    const value = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, value);
    return value;
  }
  set(key, value) {
    this.cache.delete(key);
    this.cache.set(key, value);
    if (this.cache.size > this.capacity) this.cache.delete(this.cache.keys().next().value);
    return this;
  }
}
const cache = new LRU(2);
cache.set('a', 1).set('b', 2);
cache.get('a');
cache.set('c', 3);
console.log(cache.has('a'), cache.has('b')); // true false
```

**追问与回答：** 测试get刷新、重复set、容量1、undefined值和持续插入，确认数量不越界。

对应讲解：[容量、TTL、LRU 与弱引用](#k04)。

<a id="c16-04"></a>

### C16-04 [P1·工程取舍] WeakMap、TTL、LRU是不是三种等价缓存？

**回答：** 不是。WeakMap按对象键可达性关联，TTL管业务时效，LRU管淘汰顺序，容量限制才直接约束数量。按需求组合，而不是把所有内存问题交给弱引用。

对应讲解：[容量、TTL、LRU 与弱引用](#k04)。

<a id="c16-05"></a>

### C16-05 [P1·原理] 释放reader锁是不是取消服务器生成？

**回答：** 不是。releaseLock只释放流读取锁，reader.cancel与fetch取消也各有协议效果；服务器是否终止模型或任务还需取消传播。内存释放和外部业务停止不能混为同一动作。

对应讲解：[资源不只是JS对象](#k03)。
