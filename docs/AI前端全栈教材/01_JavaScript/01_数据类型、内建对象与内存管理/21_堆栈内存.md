# 堆栈内存

**本篇主线：堆栈是什么 → 通常保存什么 → 函数调用时怎样配合 → 返回后数据怎样存活 → 栈溢出与实现边界。**

**口述总览：** 在常见的 JavaScript 引擎模型中，栈内存主要保存函数调用现场，堆内存主要管理动态创建的数据。调用栈按后进先出组织尚未结束的调用。程序通过引用访问对象，多个引用可以访问同一个对象；函数返回结束的是这次调用，不代表它创建的对象全部消失。

本篇中的图采用常见实现的简化模型。先用它理解代码，具体存储位置与优化边界在第五节说明。GC、内存泄漏和资源清理接着在下一篇学习。

## 一、堆与栈内存是什么？——先建立概念

<a id="memory"></a>
<a id="stack-memory"></a>

### 1. 栈内存：保存函数调用现场

**口述：** 函数执行时，需要保存这次调用的参数、部分局部数据和返回信息。这份调用记录通常叫栈帧，常见实现利用栈内存保存它。栈内存主要服务于函数执行。

“调用现场”可以理解为：这个函数接到了什么参数，用到了哪些值，现在执行到哪里，结束后应该回到哪里。

栈帧中可能包含：

- **参数的值**：例如传入的数字或对象引用。
- **部分局部数据**：局部变量使用的值、临时计算结果。
- **对象引用**：通过它访问对象。
- **执行与返回信息**：恢复调用者执行所需的信息。

所以，栈内存不能只概括成“存放基本类型的地方”。保存调用现场，才是这里的重点。

<a id="heap"></a>

### 2. 堆内存：管理动态创建的数据

**口述：** 堆是常见引擎用于管理动态分配数据的内存区域。普通对象、数组和函数对象通常由堆管理。对象可以被不同变量、属性和函数使用，它的寿命不必与创建它的那次调用相同。

“动态分配”就是程序运行时，按需要取得存储空间。例如创建一个用户对象，随后把它交给其他代码使用。

```text
栈内存：保存调用现场，支持函数执行与返回
堆内存：管理动态数据，支持不同位置继续访问
```

对象本身与对象引用要分开理解：对象保存数据，引用用于访问对象。一个对象可以被多处引用。

**这一节要会回答：** 栈内存主要解决“调用现场怎样保存”，堆内存主要解决“动态数据怎样管理”。数据大小或类型名称不能单独决定它实际存在哪里。

## 二、栈内存与调用栈有什么关系？——连接存储与执行

<a id="call-stack"></a>

**口述：** 栈内存是存储角度，调用栈是执行角度。调用栈组织尚未结束的函数调用，内层调用先结束，再回到外层继续。常见实现用栈帧保存这些调用的现场，把两者联系起来。

“栈”首先是一种**后进先出**的组织规则：最后放上去的书，先拿下来。

如果 createUser 调用 getName，执行顺序是：

```text
createUser 开始
    ↓
调用 getName，createUser 暂时等待
    ↓
getName 返回
    ↓
createUser 继续执行并返回
```

getName 执行时：

```text
调用栈顶：getName
          createUser
          顶层代码
```

getName 返回后，退出这一层调用，createUser 才能继续。这就是普通同步调用的入栈与出栈。

三个名词分别回答三个问题：

- **栈内存**：调用现场保存在哪里、采用怎样的存储组织？
- **栈帧**：这一次调用需要保存哪些信息？
- **调用栈**：哪些调用还没结束，当前执行谁，返回后继续谁？

作用域则决定“代码可以访问哪些变量”。它与调用、存储有关联，但不是物理内存位置的名称。

## 三、一段代码看懂堆栈怎样配合——解释运行机制

<a id="cooperation"></a>

**口述：** 函数执行时，参数和局部变量可以保存访问对象的引用。调用现场与对象数据分别承担不同职责；函数调用时传递引用值，可以让不同调用访问同一个对象。

### 1. 主例：先预测输出

<!-- example: heap-main -->
```js
function getName(person) {
  return person.name;
}

function createUser() {
  const age = 18;
  const user = { name: 'Alice', age };

  console.log(getName(user)); // Alice
  return user;
}

const saved = createUser();
console.log(saved.age); // 18
```

这段代码有四个重点：

1. age 是 createUser 使用的局部值。
2. user 用于访问用户对象 A。
3. getName 的参数 person 最初也访问对象 A。
4. saved 接收返回值，继续访问对象 A。

### 2. getName 执行时，调用与对象是什么关系？

```text
调用现场的简化示意                       堆中的对象

getName 栈帧
  person：A 的引用 ────────────┐
  返回信息                    │
                              ├──> A { name: 'Alice', age: 18 }
createUser 栈帧                │
  age：18                     │
  user：A 的引用 ──────────────┘
  返回信息
```

图中的箭头是访问关系。person 和 user 是不同的绑定，但可以访问同一个对象。

传入 user 时，没有复制整个对象。getName 读取 person.name，因此返回 Alice。

### 3. 为什么需要保存调用现场？

createUser 执行到 getName(user) 时，还没有完成后面的 console.log 和 return。

引擎需要记住这些状态，才能完成下面的过程：

1. 进入 createUser，准备局部数据并创建对象 A。
2. 进入 getName，person 接收访问 A 的引用值。
3. getName 读取名字并返回，退出自己的调用。
4. createUser 继续执行，输出 Alice。
5. createUser 返回对象 A，退出自己的调用。
6. 外部 saved 继续访问 A，因此 saved.age 是 18。

**函数对象与函数调用也要分开：** getName 是一个可被调用的函数对象；getName(user) 是执行它的一次调用。反复调用同一个函数，会有不同的调用状态，不需要每次都重新创建一份函数对象。

<a id="property-reference"></a>

### 4. 对象引用一定在栈内存中吗？

**口述：** 不一定。参数和局部变量可以保存引用，另一个对象的属性、集合条目也可以保存引用。引用的持有位置不能统一归为栈。

<!-- example: heap-property-reference -->
```js
const user = { name: 'Alice' };
const holder = { user };

console.log(holder.user === user); // true
```

```text
变量 user ────────────────────┐
                              ├──> 用户对象 A
holder 对象的 user 属性 ───────┘
```

holder 是另一个对象，它的 user 属性值也是引用。按常见堆存储模型，这份属性引用属于对象数据。

因此，“局部引用可以画在栈帧中”可以帮助理解主例；“所有引用都在栈中”则不成立。JavaScript 也不提供直接读写对象物理地址的能力，日常解释用“对象引用”比“可操作的地址指针”更合适。

<a id="reference"></a>
<a id="parameter"></a>

### 5. 修改对象与更换引用，怎样推导？

在主例基础上改变一个条件：如果 getName 中执行 person.name = 'Bob'，修改的是对象 A，外部 user 和 saved 在能够访问 A 时，也会看到变化。

如果执行 person = { name: 'Bob' }，只是让本次调用的参数访问另一个对象，createUser 中的 user 仍访问 A。

这里继续使用前篇的按值传参与对象共享规则。堆栈模型帮助展示关系，不会改变赋值语义。

## 四、函数返回后，为什么数据还可以存在？——理解生命周期

<a id="lifetime"></a>

**口述：** 函数返回结束的是这次调用。只要返回值、其他对象或闭包仍能访问相关数据，它们就可以继续使用。因此，调用结束与数据不再需要保留，是两个不同的问题。

### 1. 返回对象：调用结束，访问路径仍存在

主例的 createUser 返回后：

```text
createUser 这次调用已经结束

外部 saved ──> 对象 A { name: 'Alice', age: 18 }
```

saved 接收了返回的对象引用，所以能继续读取 saved.age。返回过程没有自动复制对象。

对这个例子来说，创建对象的那次调用已经完成，但对象的使用仍在继续。这是堆栈模型中最需要理解的一点。

<a id="closure-lifetime"></a>

### 2. 返回闭包：所需绑定也可以继续使用

<!-- example: heap-closure -->
```js
function createCounter() {
  let count = 0;

  return function next() {
    count += 1;
    return count;
  };
}

const next = createCounter();
console.log(next()); // 1
console.log(next()); // 2
```

createCounter 已经返回，但 next 仍能访问这次调用产生的 count 绑定。

引擎需要保留后续调用所需的数据。这不表示 createCounter 的整个调用一直停留在调用栈上，也不能据此断言所有局部数据都被原样保存。

### 3. 这一节怎样衔接下一篇？

当一个对象已经没有其他可达路径时，才具备被回收的条件，具体时机由引擎决定。只给一个变量赋 null，不保证其他持有者也消失。

本篇先理解“谁还能访问数据”。下一篇再讲[垃圾回收、内存泄漏与资源清理](22_垃圾回收机制、内存泄漏与资源清理.md)。

## 五、进阶分析：栈溢出、性能与实现边界

<a id="analysis"></a>
<a id="overflow"></a>

### 1. 为什么有终止条件，也可能栈溢出？

**口述：** 递归会让前面的调用等待后续调用返回，尚未结束的调用不断叠加。正确的终止条件加上逐步趋近它的递归逻辑，才能保证理论上结束；但调用深度仍可能先超过运行时限制。

<!-- example: heap-recursive-count -->
```js
function countDown(n) {
  if (!Number.isSafeInteger(n) || n < 0) {
    throw new TypeError('non-negative safe integer required');
  }

  function visit(value) {
    if (value === 0) return 0;
    return 1 + visit(value - 1);
  }

  return visit(n);
}

console.log(countDown(3)); // 3
```

执行过程：

```text
visit(3) 等 visit(2)
visit(2) 等 visit(1)
visit(1) 等 visit(0)
visit(0) 返回，再逐层返回
```

输入很大时，可能在到达 0 之前，就超过运行时的调用栈限制。栈溢出通常会报告递归过深或调用栈超限，并不说明整台机器的内存已经耗尽。

能承受多少层取决于引擎、运行环境和每层开销，不能统一说成某个固定大小。

### 2. 改成循环后，解决了什么？

<!-- example: heap-loop-count -->
```js
function countDownLoop(n) {
  if (!Number.isSafeInteger(n) || n < 0) {
    throw new TypeError('non-negative safe integer required');
  }

  let count = 0;
  while (n > 0) {
    count += 1;
    n -= 1;
  }
  return count;
}

console.log(countDownLoop(10000)); // 10000
```

循环在同一次函数调用中重复执行，不为每次减 1 增加一层调用，因此不会按步数不断加深调用栈。

不过，循环仍然需要执行这些步骤。输入很大时，依然可能长时间占用线程。

这个计数例子用于比较执行过程，实际业务无需逐步计算一个已知数字。处理真实的深层遍历时，可以考虑循环配合显式工作列表，但仍要评估算法总工作量及额外数据占用。

<a id="implementation"></a>

### 3. 教学模型与实际引擎，怎样回答才准确？

**口述：** 我会用栈帧保存调用现场、用堆管理动态数据的模型解释代码，再说明物理布局由引擎决定。语言保证的是程序行为，不是每个变量必须放在某个内存区域。

需要掌握三个边界：

- 局部值和引用可能使用栈、寄存器或其他存储，内联等优化也可能改变实际栈帧。
- 字符串、BigInt 和部分数值表示也可能使用堆；原始类型不意味着大小固定。
- 作用域决定变量可见性，调用栈组织执行过程，引用关系影响数据存活；三者不能相互替代。

前面把 age、user 和 person 画在栈帧中，是为了展示本例关系，不是证明它们在某个引擎里一定具有对应的物理位置。

### 4. 面试直接问深入问题，怎样串起来？

**问：递归改循环后不报栈溢出了，为什么仍然卡？**

先说明结论：调用深度降低了，总计算量不一定减少。接着看循环次数、重复计算和分配，再用性能记录确认热点。确实需要大量计算时，评估分批或 Worker，并验证结果、取消和调度成本。

**问：函数都返回了，为什么对象还在？**

先找到外部访问路径，例如返回值、对象属性或闭包，再解释调用结束不等于数据不可达。不要仅凭“函数返回”推断数据已经释放。

**问：从代码能精确画出 V8 的真实栈与堆吗？**

可以先画调用关系和对象关系，用于预测行为。精确布局还需要引擎版本、优化状态和相应工具，源码示意不能直接证明真实地址或字节开销。

高级回答的重点是：**先判断问题属于调用深度、数据存活还是执行成本，再解释原因、适用范围及验证方法。**

## 六、面试口述与分层练习

### 1. 一段完整口述

> 栈内存主要保存函数调用现场，堆主要管理动态数据；调用栈按后进先出组织尚未结束的调用。局部变量、参数和对象属性都可以保存对象引用，所以引用不一定全部在栈里。函数返回只结束这次调用，返回对象或闭包所需的数据仍可能继续使用。分析时我会分别看调用关系和引用关系，实际物理布局则由引擎决定。

### 2. 初、中、高级分别练到哪里？

- **初级：说清概念。** 能说明堆、栈内存、栈帧和调用栈的职责，画出简单入栈、出栈顺序。
- **中级：解释机制。** 能独立推导主例，解释参数引用、对象属性引用、返回对象和闭包的数据存活。
- **高级：分析变化与取舍。** 能处理递归深度、循环后卡顿等追问，区分调用深度、计算成本和对象占用，并说明模型与实际实现的边界。

这三层限定在堆栈专题。完成标准是换一段代码后仍能解释，而不是逐字背下口述段落。

### 3. 本篇面试题与答案

<a id="d20-19"></a>

### D20-19 [P0·基础] 栈内存与堆内存是什么，通常保存什么？

**回答：** 栈内存主要保存调用现场，栈帧可能包含参数、部分局部数据、引用和返回信息；堆管理动态分配的数据，对象、数组和函数对象通常由堆管理。解释时先讲职责，具体位置要结合引擎实现。

对应解释：[堆栈概念](#memory)。

<a id="d20-20"></a>

### D20-20 [P0·基础] 调用栈与栈内存有什么联系和区别？

**回答：** 调用栈从执行角度组织未结束的调用，栈内存从存储角度保存调用现场。常见实现用栈帧联系二者。内层调用结束后继续外层，体现后进先出；抽象调用不等于固定的物理布局。

对应解释：[存储与执行](#call-stack)。

<a id="d20-21"></a>

### D20-21 [P0·原理] 对象引用一定保存在栈内存中吗？

**回答：** 不一定。局部变量和参数可以保存引用，对象属性及集合条目也可以保存引用，例如 holder.user。要区分对象本身与引用，并结合引用的持有者解释关系。

对应解释：[引用位置](#property-reference)。

<a id="d20-04"></a>

### D20-04 [P1·原理] “原始类型存栈，对象类型存堆”准确吗？

**回答：** 这是过度简化。栈帧可能保存对象引用，堆也可能保存字符串、BigInt 和部分数值表示；实际存储由引擎决定。它不能代替对赋值、对象身份和调用过程的解释。

对应解释：[实现边界](#implementation)。

<a id="d20-05"></a>

### D20-05 [P0·原理] 调用栈负责什么？函数返回后数据一定消失吗？

**回答：** 调用栈组织函数进入与返回。函数返回结束调用，但外部仍可能通过返回值、对象属性或闭包访问数据。主例中 saved 仍访问用户对象，所以对象可以继续使用。

对应解释：[函数返回与数据存活](#lifetime)。

<a id="d20-09"></a>

### D20-09 [P0·原理] 栈溢出是否说明整台机器的内存已经耗尽？

**回答：** 不一定。它通常说明调用深度超过运行时限制。先检查递归的终止条件和输入，再考虑循环或其他算法；调用栈上限依赖环境，不能用统一数值判断。

对应解释：[递归与栈溢出](#overflow)。

<a id="d20-10"></a>

### D20-10 [P1·原理] 为什么蹦床能避免深层递归的栈溢出？闭包本身可以吗？

**回答：** 蹦床让每步先返回下一步函数，当前调用结束后，再由循环执行下一步，所以不会按步数不断叠加调用。闭包用于保存下一步的数据，直接在闭包中递归仍可能增长栈深度。它属于执行转换的选读扩展。

对应解释：[调用深度与循环](#overflow)。

<a id="d20-17"></a>

### D20-17 [P1·工程取舍] 改成蹦床后不再栈溢出，页面仍然卡顿，如何继续优化？

**回答：** 控制了深度，不代表减少了计算量和临时分配。先记录热点，减少不必要的工作；再根据业务评估低分配循环、分批或 Worker。验证输出正确性、取消、交互响应和总成本，不能只看有没有报错。

对应解释：[深入问题的分析路径](#analysis)。
