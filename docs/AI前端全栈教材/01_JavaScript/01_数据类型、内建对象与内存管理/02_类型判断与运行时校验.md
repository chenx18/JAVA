## 二、知识讲解

<a id="goal"></a>

### 1. 先确定判断目标，再选择方法

“判断数据类型”可能指四种不同要求：

1. **语言分类**：它是字符串、数字、函数，还是对象？
2. **对象身份或关系**：它是真正数组吗？它与某个类有什么实例关系？
3. **数据结构**：它有必须的字段吗？数组中的每一项符合要求吗？
4. **业务契约**：页码是否大于零？用户是否有权限？当前状态是否允许提交？

没有一个运算符能一次解决这四层问题。例如 `typeof value === 'object'` 既不能排除 `null`，也不能证明它有合法的用户字段。

常用选择可以这样记：

- 判断 `null`：`value === null`。
- 判断原始字符串、布尔值、BigInt、Symbol 等：`typeof`。
- 判断数组：`Array.isArray`。
- 判断真正的 `NaN`：`Number.isNaN`。
- 判断有限 Number：`Number.isFinite`；整数、范围等条件继续校验。
- 判断受控类的实例关系：`instanceof`，同时考虑原型和环境边界。
- 查看内建对象的标签：`Object.prototype.toString.call`，用于分类和调试。
- 判断接口数据是否可用：校验字段、结构、范围和协议。

**面试口述：** 先明确要判断语言类型、实例关系，还是数据契约。简单值用 `typeof`，数组用 `Array.isArray`，实例关系用 `instanceof`；业务数据还要逐层校验，不能只凭一个类型标签放行。

<a id="typeof"></a>

### 2. typeof：基本分类与暂时性死区

`typeof` 是运算符，结果是字符串。`typeof(value)` 中的括号不代表它是函数。

<!-- example: d02-typeof-values -->
```js
console.log(typeof undefined); // 'undefined'
console.log(typeof null); // 'object'
console.log(typeof true); // 'boolean'
console.log(typeof 1); // 'number'
console.log(typeof 1n); // 'bigint'，不是 'bigInt'
console.log(typeof 'hello'); // 'string'
console.log(typeof Symbol('id')); // 'symbol'
console.log(typeof []); // 'object'
console.log(typeof new Date()); // 'object'
console.log(typeof function () {}); // 'function'
```

它适合区分大多数原始值以及通常的函数值，但不能细分数组、日期、正则和 Map 等对象。`null` 仍是原始值，返回 `'object'` 是历史兼容行为，判断它用严格比较。

`'number'` 只证明属于 Number 类型，不证明是有限数、整数或合法业务值。

<!-- example: d02-number-validation -->
```js
console.log(typeof NaN, typeof Infinity); // number number
console.log(Number.isNaN(NaN), Number.isNaN('NaN')); // true false
console.log(Number.isFinite(10), Number.isFinite('10')); // true false

function isPageNumber(value) {
  return Number.isSafeInteger(value) && value >= 1;
}

console.log(isPageNumber(2), isPageNumber(2.5), isPageNumber(0));
// true false false
```

这里没有把字符串先转数字。是否接受 `'2'` 属于接口契约和类型转换问题，不能在判断中悄悄混入转换。

#### typeof 并非永远不会报错

对完全未声明的名字，`typeof` 返回 `'undefined'`；对暂时性死区中的 `let`、`const` 或 `class` 绑定，仍会抛 `ReferenceError`。

<!-- example: d02-typeof-tdz -->
```js
console.log(typeof definitelyMissingName); // 'undefined'

{
  try {
    console.log(typeof value);
  } catch (error) {
    console.log(error.name); // ReferenceError
  }
  let value = 1;
}
```

前者没有可解析的绑定；后者已经命中块级绑定，但它尚未初始化。另外，`typeof object.field` 会先读取属性，getter 抛错时，`typeof` 也不会替你吞掉异常。

#### typeof 函数不等于安全可调用

例如声明 `class User {}` 后，`typeof User` 为 `'function'`，直接执行 `User()` 却会抛 `TypeError`。判断可接受的回调，仍需约定签名、返回值和错误行为。浏览器的 `document.all` 还有历史兼容特例，常规业务不依赖它。

**面试口述：** `typeof` 返回基本分类字符串，适合原始值和通常的函数判断，但不能细分对象，也不能判断业务合法性。它对未声明名字有特殊处理，却不能绕过暂时性死区，也不能阻止属性读取引发的异常。

<a id="instanceof"></a>

### 3. instanceof：实例关系与自定义协议

当右侧是普通未绑定构造函数，并采用原生默认的 `Symbol.hasInstance` 行为时，`value instanceof Constructor` 检查 **`Constructor.prototype` 是否出现在 value 的原型链中**。

由 `bind` 得到的绑定函数在默认机制下，会委托被绑定的目标函数继续判断；不能简单读取绑定函数自己的 `.prototype` 作为依据。

<!-- example: d02-instanceof-chain -->
```js
function User(name) {
  this.name = name;
}
const user = new User('Alice');

console.log(user instanceof User); // true
console.log(user instanceof Object); // true
console.log(Object.getPrototypeOf(user) === User.prototype); // true
```

本例的原型关系是：

```text
user → User.prototype → Object.prototype → null
```

检查依据是当前原型关系，不是追溯“最初执行了哪一行 `new`”。没有调用构造函数，也能取得对应关系：

<!-- example: d02-instanceof-imitation -->
```js
const imitation = Object.create(Array.prototype);

console.log(imitation instanceof Array); // true
console.log(Array.isArray(imitation)); // false
```

`imitation` 的原型链包含 `Array.prototype`，但它不是数组。因此不能把默认 `instanceof` 当成内建类型的不可伪造鉴定。

原始值与包装对象也不同：

<!-- example: d02-instanceof-wrapper -->
```js
console.log('hello' instanceof String); // false
console.log(new String('hello') instanceof String); // true
console.log(1 instanceof Number); // false
console.log(null instanceof Object); // false
```

`new String` 创建的是包装对象，不是“new 出来的原始类型”。判断 `null` 直接用 `=== null`，不需要转向 `instanceof`。

#### Symbol.hasInstance 可以定制结果

<!-- example: d02-custom-has-instance -->
```js
class NonEmptyString {
  static [Symbol.hasInstance](value) {
    return typeof value === 'string' && value.length > 0;
  }
}

console.log('hello' instanceof NonEmptyString); // true
console.log('' instanceof NonEmptyString); // false
```

此时检查执行的是右侧对象定义的协议，不是默认原型查找。右侧如果不满足相关要求，还可能抛 `TypeError`。

**面试口述：** 普通未绑定构造函数采用默认机制时，`instanceof` 检查原型链关系；绑定函数默认委托目标函数判断。它适合受控类的实例判断，不等于构造来源或绝对类型，还会受原型修改、跨 realm 和自定义 `Symbol.hasInstance` 影响，对任意输入也不保证只返回布尔值。

<a id="realm-array"></a>

### 4. 跨 realm 与 Array.isArray

realm 可以理解为拥有自己一套内建对象和构造器的 JavaScript 环境。例如浏览器 iframe 可以有自己的 `Array` 和 `Array.prototype`；Node.js 的 `vm` 上下文也能展示这种差异。

下面的代码仅用于 Node.js，按 ES 模块运行：

<!-- example: d02-cross-realm-array -->
```js
import vm from 'node:vm';

const foreignArray = vm.runInNewContext('[1, 2]');

console.log(foreignArray instanceof Array); // false
console.log(Array.isArray(foreignArray)); // true
console.log(foreignArray.constructor === Array); // false
```

数组是真数组，但它的原型链关联另一套 `Array.prototype`。用当前环境的构造器判断，身份不匹配。

浏览器中读取同源 iframe 创建的数组，也可能出现相同结果。跨域 iframe 的访问还受同源策略约束，这是另外一层限制。

#### 为什么数组优先用 Array.isArray？

`Array.isArray` 使用数组身份相关的内部判断，不靠可修改的 `constructor` 属性，也不只看原型链。因此它能识别跨 realm 的数组，并拒绝原型像数组的普通对象。

“类数组”和“可迭代”也不能与数组混同。`{ 0: 'a', length: 1 }` 是类数组，`new Set(['a'])` 是可迭代集合，两者都不是数组；能通过 `Array.from` 转成数组，不证明原值就是数组。`Array.isArray` 也不校验元素类型，Proxy 的特殊边界见第 7 节。

**面试口述：** 跨 realm 的内建构造器身份不同，所以真实数组也可能不满足当前环境的 `instanceof Array`。判断数组优先用 `Array.isArray`，再按照业务契约检查元素和长度。

<a id="constructor"></a>

### 5. constructor 与 prototype 的局限

许多对象通过原型继承 `constructor`，所以 `[].constructor === Array` 经常成立。但它只是普通属性，可以被遮蔽、修改或不存在。

<!-- example: d02-constructor-limits -->
```js
console.log([].constructor === Array); // true
console.log(new Date().constructor === Date); // true

const fake = { constructor: Array };
console.log(fake.constructor === Array); // true
console.log(Array.isArray(fake)); // false

const dictionary = Object.create(null);
console.log(dictionary.constructor); // undefined
console.log(null?.constructor); // undefined
```

`?.` 叫可选链。它只避免对 `null` 或 `undefined` 继续读取属性，不会提高 `constructor` 的真实性，也不会避免非空对象的 getter 或 Proxy 抛错。

`prototype` 也不是独立的类型判断运算符：

- 构造器的 `.prototype` 通常参与 `new` 创建实例的原型关系。
- `Object.getPrototypeOf(value)` 查询对象的当前原型。
- 两者可以用于分析原型关系，但不能据此证明对象字段正确或构造来源可信。
- `fn.prototype` 是否存在，也不能单独证明函数能否被 `new`。

旧式继承中“修复 constructor”，恢复的只是普通属性：

<!-- example: d02-constructor-inheritance -->
```js
function Parent() {}
function Child() {}

Child.prototype = Object.create(Parent.prototype);
Object.defineProperty(Child.prototype, 'constructor', {
  value: Child, writable: true, configurable: true
});

const child = new Child();
console.log(child instanceof Child, child instanceof Parent); // true true
console.log(child.constructor === Child); // true
```

原型关系由 `Object.create` 等操作建立，改 `constructor` 本身不会建立继承，也不会改变已经选择的构造调用目标。

**面试口述：** `constructor` 是普通属性，`prototype` 是原型机制的一部分，两者都不是通用类型证明。可选链只能防空值访问；数组、数字和接口数据应使用对应判断与契约校验。

<a id="tag"></a>

### 6. Object.prototype.toString.call：标签与伪装

直接调用值自己的 `toString`，可能执行类型重写的方法，例如数组把元素连接成文本。

<!-- example: d02-object-tag -->
```js
console.log([1, 2].toString()); // '1,2'
console.log(Object.prototype.toString.call([1, 2])); // '[object Array]'
console.log(Object.prototype.toString.call(null)); // '[object Null]'
console.log(Object.prototype.toString.call(undefined)); // '[object Undefined]'
console.log(Object.prototype.toString.call(1n)); // '[object BigInt]'
console.log(Object.prototype.toString.call(new Date())); // '[object Date]'
```

这段写法的含义是：取得 `Object.prototype.toString`，通过 `call(value)` 指定接收者，再按这个方法的规则生成标签。

它比 `typeof` 能区分更多内建对象，但不是“任何情况下最准确的方法”。`Symbol.toStringTag` 可以改变结果：

<!-- example: d02-spoofed-tag -->
```js
const fake = { [Symbol.toStringTag]: 'Array' };

console.log(Object.prototype.toString.call(fake)); // '[object Array]'
console.log(Array.isArray(fake)); // false

console.log(Object.prototype.toString.call('x')); // '[object String]'
console.log(Object.prototype.toString.call(new String('x'))); // '[object String]'
```

同样的标签也不一定区分原始值与包装对象。该方法适合受控数据的分类、日志和调试，不能代替数组身份判断、字段校验或安全校验。

**面试口述：** 通用 `toString` 按自身规则生成类型标签，区别于值自己的文本转换方法。但标签可被 `Symbol.toStringTag` 修改，原始值与包装对象也可能同名，所以它是分类线索，不是最终证明。

### 7. getter、Proxy 与判断副作用

一个判断表达式可能读取属性、执行用户代码，甚至抛错。不能因为返回值是布尔值，就认定整个过程没有副作用。

<!-- example: d02-tag-getter -->
```js
let reads = 0;
const value = {
  get [Symbol.toStringTag]() {
    reads++;
    return 'Array';
  }
};

console.log(Object.prototype.toString.call(value)); // '[object Array]'
console.log(reads); // 1
console.log(Array.isArray(value)); // false
console.log(reads); // 1
```

标签方法读取了 `Symbol.toStringTag`，执行 getter。读取 `.constructor`、接口字段，以及执行 `Symbol.hasInstance`，也可能触发代码。

Proxy 可以拦截属性读取、原型查询和属性描述符查询等操作。不同判断方法走的机制不同，不能笼统说“Proxy 一定影响类型”或“类型判断一定穿透 Proxy”。

<!-- example: d02-array-proxy -->
```js
let traps = 0;
const proxy = new Proxy([], {
  get(target, key, receiver) {
    traps++;
    return Reflect.get(target, key, receiver);
  },
  getPrototypeOf(target) {
    traps++;
    return Reflect.getPrototypeOf(target);
  }
});

console.log(Array.isArray(proxy)); // true
console.log(traps); // 0

const pair = Proxy.revocable([], {});
pair.revoke();
console.log(typeof pair.proxy); // 'object'
try {
  Array.isArray(pair.proxy);
} catch (error) {
  console.log(error.name); // TypeError
}
```

未撤销的数组 Proxy 可以被 `Array.isArray` 识别，这个判断不靠本例的 `get`、`getPrototypeOf` trap；撤销后却会抛错。`typeof` 直接检查这个代理值时仍为 `'object'`，不代表代理仍可操作。

工程上先区分数据入口：

1. **同一入口直接 `JSON.parse` 得到的数据**：不会自带函数、getter 或 Proxy，适合明确的结构校验。
2. **任意 JavaScript 对象、插件返回值、反应式代理**：可能执行访问逻辑，必须约定支持范围和异常行为。

需要支持后者时，可以在边界将访问异常转成带路径的失败结果，并记录可定位原因。`try/catch` 只能处理异常，不能撤销 getter 已造成的副作用；属性描述符能避免普通 getter 执行，但描述符查询本身也可能被 Proxy 拦截。

**面试口述：** 类型判断并非总是纯读取。先限定输入来源，选最直接的方法，再明确异常策略；受控 JSON 数据与任意运行时对象要分别处理。不能用一个 catch 宣称判断完全安全。

<a id="validation"></a>

### 8. 从类型判断到运行时校验

“是数组”与“是字符串数组”不同；“有 id 字段”与“id 可以用于业务请求”也不同。

#### 8.1 无空位的字符串数组

下面的窄契约允许空数组，拒绝非字符串元素、稀疏空位和超过 1000 项的数组。它面向普通数据数组；任意 Proxy、访问器或自定义行为需要额外约定。

<!-- example: d02-string-array -->
```js
function isStringArray(value, maxItems = 1000) {
  if (!Number.isSafeInteger(maxItems) || maxItems < 0) return false;
  if (!Array.isArray(value) || value.length > maxItems) return false;

  for (let index = 0; index < value.length; index++) {
    if (!Object.hasOwn(value, index)) return false;
    if (typeof value[index] !== 'string') return false;
  }
  return true;
}

const inherited = new Array(1);
const prototype = Object.create(Array.prototype);
prototype[0] = 'inherited';
Object.setPrototypeOf(inherited, prototype);

console.log(isStringArray([])); // true
console.log(isStringArray(['a', 'b'])); // true
console.log(isStringArray(['a', 1])); // false
console.log(isStringArray(new Array(1))); // false
console.log(isStringArray(inherited)); // false
console.log(isStringArray(['a', 'b'], 1)); // false
```

不能只用 `every`：它会跳过没有可访问元素的空位。`Object.hasOwn` 明确要求索引是自身属性，避免原型上的同名索引掩盖空位；取值仍可能执行访问器。

数量上限让校验成本可控，单项长度、是否允许重复等属于后续契约。外部 JSON 数组不能表达稀疏空位，但普通 JavaScript 调用可以传入这种数组。

#### 8.2 字段、范围与未知字段

以解析后的用户数据为例，本节只接受本环境的普通对象或无原型数据对象，并采用以下契约：

- 必须有自身数据属性 `id`、`name`、`age`，不接受继承字段或访问器字段。
- id 是 1～30 位十进制数字文本；不把数字自动转换成字符串。
- name 是非空白字符串，按 JavaScript 的 length 计数不超过 80，保留原文本。
- age 是 0～150 的安全整数。
- 拒绝未知字段；返回新的字段对象和稳定的错误路径。

以下函数示范窄契约，不是通用 schema 引擎；正常校验失败和输入访问异常都使用同一种结果结构。

<!-- example: d02-parse-user -->
```js
function parseUser(input) {
  const fail = (path, message) => ({
    ok: false, errors: [{ path, message }]
  });
  let currentPath = '$';

  try {
    if (input === null || typeof input !== 'object' || Array.isArray(input)) {
      return fail('$', '需要用户对象');
    }
    const prototype = Object.getPrototypeOf(input);
    if (prototype !== Object.prototype && prototype !== null) {
      return fail('$', '需要本环境的普通数据对象');
    }

    const allowed = new Set(['id', 'name', 'age']);
    for (const key of Reflect.ownKeys(input)) {
      if (typeof key !== 'string' || !allowed.has(key)) {
        return fail(typeof key === 'string' ? `$.${key}` : '$', '未知字段');
      }
    }

    const fields = Object.create(null);
    for (const key of allowed) {
      currentPath = `$.${key}`;
      const descriptor = Object.getOwnPropertyDescriptor(input, key);
      if (!descriptor || !Object.hasOwn(descriptor, 'value')) {
        return fail(`$.${key}`, '需要自身数据属性');
      }
      fields[key] = descriptor.value;
    }

    if (typeof fields.id !== 'string' || !/^\d{1,30}$/.test(fields.id)) {
      return fail('$.id', '需要 1～30 位数字文本');
    }
    if (typeof fields.name !== 'string' || fields.name.trim().length === 0 ||
        fields.name.length > 80) {
      return fail('$.name', '需要不超过 80 字符的非空白姓名');
    }
    if (!Number.isSafeInteger(fields.age) || fields.age < 0 || fields.age > 150) {
      return fail('$.age', '需要 0～150 的整数');
    }
    return { ok: true, value: { id: fields.id, name: fields.name, age: fields.age } };
  } catch {
    return fail(currentPath, '读取输入时发生异常');
  }
}

const valid = parseUser(JSON.parse('{"id":"001","name":"Alice","age":20}'));
console.log(valid.ok, valid.value.id, valid.value.age); // true 001 20
const invalid = parseUser({ id: 1, name: 'Alice', age: 20 });
console.log(invalid.ok, invalid.errors[0].path); // false $.id
const unknown = parseUser({ id: '001', name: 'Alice', age: 20, role: 'admin' });
console.log(unknown.ok, unknown.errors[0].path); // false $.role

let reads = 0;
const accessor = parseUser({
  id: '001', name: 'Alice', get age() { reads++; return 20; }
});
console.log(accessor.ok, accessor.errors[0].path, reads); // false $.age 0
```

通过描述符读取普通数据属性，可以拒绝 getter 而不执行它。Proxy 仍能拦截本例使用的查询方法，因此不能推广为“任意对象都无副作用”。本例限制原型是输入契约，不是通用的跨 realm 普通对象检测方法。

#### 8.3 类型、结构和业务分别校验

上述结果只证明这三个字段满足约定，不证明用户存在、有权限或当前状态允许修改。未知字段选择拒绝、忽略或保留，都要明确：拒绝有利于发现协议漂移；忽略更便于兼容新字段；保留会扩大后续使用范围。

TypeScript 的类型声明、类型断言和 `value is User` 标注不会自动生成这些检查。类型谓词函数如果写错，编译器仍可能相信它；运行时结果要靠实际检查和边界测试保证。

JSON 的解析与序列化协议详见 [JSON与运行时校验](17_JSON与运行时校验.md)；数字文本如何转换详见 [类型转换与比较](03_类型转换与比较.md)。

**面试口述：** 类型判断只是入口。接口数据还要校验容器、必选字段、字段自身性、取值范围和未知字段策略，成功后才能进入业务。TypeScript 不会替我们验证运行时数据，业务权限也必须由权威服务端判断。

<a id="schema"></a>

### 9. 手写校验与 schema 的工程选择

字段少、输入受控、规则稳定时，窄范围的手写校验容易阅读；字段多、嵌套深、多个入口共用协议时，优先使用项目已有的成熟 schema 库，例如 Zod 或 Ajv，避免分别维护一套近似规则。

选库和定义 schema 时，要确定以下契约：

1. **严格判断还是自动转换**：是否接受 `'20'` 并转成 20？转换前怎样处理空值？
2. **未知字段策略**：拒绝、丢弃还是保留，版本升级如何兼容？
3. **输出契约**：返回原对象还是规范化后的数据？调用方能否依赖它未被修改？
4. **错误契约**：报第一个错误还是全部错误？错误是否包含稳定字段路径？
5. **资源限制**：数组长度、文本长度、嵌套深度和响应大小怎样限制？
6. **业务边界**：schema 负责结构和局部约束，权限、状态和跨记录关系仍由业务层处理。

schema 不是自动消除风险的开关。它的读取、转换和 refinement 也可能执行代码，外部输入来源和支持范围仍要明确。

工程验证按真实输入规模进行：准备合法值、缺字段、错误类型、边界值、未知字段和超大输入；检查错误路径及输出是否被转换。需要关注性能时，复用 schema 或编译后的 validator，分别测量冷启动、热校验、有效与无效输入，不能只比较单个小对象。

假设大量记录会反复使用，通常在进入系统的边界校验一次并保存已验证结果；可变对象可能在校验后被修改，必须同时约定所有权和更新路径。一个永久的“已校验”标记，不能证明对象此后仍然有效。

**面试口述：** 窄契约可以手写，共享复杂契约优先复用成熟 schema。选择时看转换、未知字段、错误和性能，而不只看语法。校验结果要与对象后续修改的约定一起设计。

<a id="legacy"></a>

### 10. jQuery.type 的历史边界与迁移

`$.type(value)` 与 `jQuery.type(value)` 是 jQuery 提供的工具，不是 JavaScript 内建语法。它在旧项目中用来返回 `'array'`、`'date'` 等分类字符串。

根据 [jQuery 官方 API](https://api.jquery.com/jQuery.type/)，它从 jQuery 3.3 起弃用，在 4.0 中移除。现代项目不需要为了类型判断新增 jQuery 依赖。

旧项目迁移时，不能把它机械替换为 `typeof`：例如原来的 `'array'` 会变成 `'object'`，包装对象的分类结果也可能不同。

迁移步骤是：

1. 搜索调用点，确认判断结果被用于什么业务分支。
2. 针对项目实际版本与输入建立行为样本，包括原始值、包装对象、数组、日期、空值和新类型。
3. 依据目标改用 `Array.isArray`、`typeof`、明确的实例判断或字段校验。
4. 如果调用方确实依赖旧标签，集中维护明确范围的兼容适配器，并安排后续替换。
5. 用业务样本核对分支和错误行为，检查 BigInt、Symbol 和自定义标签等版本边界。

**面试口述：** `jQuery.type` 是历史工具，已经弃用并从 4.0 移除。迁移以调用方契约为依据，先覆盖真实输入再替换；不能因为现代方法名字更熟悉，就忽略分类差异。

## 四、面试题与答案

P0 表示优先掌握，P1 表示常见进阶；这是学习优先级，不代表保证必考。每题先讲直接答案，再根据追问说明边界和验证依据。

<a id="d02-01"></a>

### D02-01 [P0·基础] typeof 能判断什么，为什么不能只凭它判断对象和合法数字？

**回答：** `typeof` 返回字符串，能区分多数原始值和通常的函数值；数组、日期、Map 等对象通常都返回 `'object'`，`null` 也返回这个结果。判断数组用 `Array.isArray`，判断 null 用严格比较。`NaN`、Infinity 都属于 Number，类型正确不证明它有限、是整数或符合范围；合法页码可以用 `Number.isSafeInteger(value) && value >= 1`。

**追问：typeof 返回 function 就能直接调用吗？** 不一定。class 也返回 `'function'`，直接调用会抛错；业务回调仍需约定调用形式、参数和返回值。

对应讲解：[typeof](#typeof)、[判断目标](#goal)。

<a id="d02-02"></a>

### D02-02 [P1·原理] typeof 未声明变量不报错，为什么在暂时性死区中会报错？

**回答：** 对无法解析的名字，`typeof` 有返回 `'undefined'` 的特殊规则。对当前作用域中尚未初始化的 `let`、`const`、class 绑定，名字已经被解析到该绑定，但读取受到暂时性死区限制，所以抛 `ReferenceError`。特殊规则不等于绕过所有变量访问限制。

**追问：typeof obj.field 可以保证不报错吗？** 不能。它要先求出属性值，空值访问、getter 或 Proxy 抛错都会使表达式失败。验证时应分别测试未声明名字、TDZ 绑定和抛错属性，不能只用一个未声明变量样本。

对应讲解：[typeof 与 TDZ](#typeof)、[判断副作用](#effects)。

<a id="d02-03"></a>

### D02-03 [P0·原理] instanceof 判断的是类型、构造来源还是原型关系？

**回答：** 对采用原生默认 `Symbol.hasInstance` 行为的普通未绑定构造函数，检查右侧的 `prototype` 是否在左侧对象的原型链中；绑定函数默认委托被绑定目标函数继续判断。所以它不追溯最初构造来源，更不是不可伪造的内建类型。`Object.create(Array.prototype)` 创建的普通对象能满足 `instanceof Array`，却不是数组。原始字符串也不会因为有字符串方法就满足 `instanceof String`。

**追问：一定沿原型链判断吗？** 右侧 `Symbol.hasInstance` 可以定义自己的判定逻辑，甚至让原始值满足检查。右侧不合法还可能抛错，因此必须区分默认机制和自定义协议。

对应讲解：[instanceof](#instanceof)。

<a id="d02-04"></a>

### D02-04 [P1·原理] 跨 realm 的数组为什么可能不满足 instanceof Array？

**回答：** 不同 realm 拥有不同的内建构造器与原型。另一个 iframe 或 vm 上下文创建的数组，关联的是那个环境的 `Array.prototype`，不一定包含当前环境的原型。`Array.isArray` 不靠当前构造器的原型身份，因此能识别真实跨 realm 数组。

**追问：有 length 和数字索引就算数组吗？** 不算，那可能只是类数组；可迭代对象也未必是数组。用例应同时覆盖本地数组、跨 realm 数组、类数组和 `Object.create(Array.prototype)`，才能验证选型依据。

对应讲解：[跨 realm 与数组](#realm-array)。

<a id="d02-05"></a>

### D02-05 [P1·原理] constructor 和 prototype 能作为可靠的类型判断依据吗？

**回答：** 不能作为通用依据。`constructor` 是普通属性，能被遮蔽、改写或不存在，跨 realm 的构造器身份也不同。`.prototype` 和 `Object.getPrototypeOf` 可以分析原型关系，但原型关系能被改变，不能证明内建身份或数据结构。旧继承代码修复 constructor 只是恢复普通属性，不是建立继承的操作。

**追问：加可选链是否解决了问题？** 只解决 null/undefined 的属性访问，不能防伪、处理跨 realm 身份或阻止 getter 抛错。应测试伪造 constructor、无原型对象和非空抛错属性。

对应讲解：[constructor 与 prototype](#constructor)。

<a id="d02-06"></a>

### D02-06 [P1·原理] Object.prototype.toString.call 比直接 toString 多了什么信息，能被伪装吗？

**回答：** 直接 `toString` 可能执行类型重写的文本转换，例如数组得到逗号连接结果；通用方法通过指定接收者生成 `[object Type]` 标签，能区分很多内建对象。但 `Symbol.toStringTag` 能改标签，普通对象能伪装成 `[object Array]`，原始字符串和包装对象也可能得到相同标签。它适合受控数据分类和调试，数组身份优先用 `Array.isArray`。

**追问：仅借用原生方法就没有副作用吗？** 标签读取能执行 getter 或 Proxy trap。要用伪装标签和带 getter 的样本验证，而不只测试数组、日期等正常值。

对应讲解：[标签与伪装](#tag)、[判断副作用](#effects)。

<a id="d02-07"></a>

### D02-07 [P1·工程取舍] 类型判断遇到 getter、Proxy 或撤销代理，如何处理副作用和异常？

**场景：** 通用组件接收插件返回对象，分类时偶发抛错；调用方原本以为判断函数只会返回 true 或 false。

**回答：** 先记录失败入口并确认输入契约。如果只支持解析后的普通数据，应在边界拒绝带行为的对象，不把通用组件扩成任意对象解析器。如果必须支持代理，选择满足目标的最直接判断，并统一访问异常的处理方式：可向上抛带上下文的错误，或返回可定位的失败结果，不能把所有异常默默解释为“不符合类型”。

**追问：Array.isArray 对代理怎样表现？** 未撤销的数组代理可返回 true，且不依赖普通 get/getPrototypeOf trap；撤销代理会抛 `TypeError`。直接 `typeof` 对已撤销的对象代理仍可返回 `'object'`。

**追问：用描述符或 try/catch 就能保证安全了吗？** 描述符能避免普通 getter 执行，但 Proxy 可以拦截描述符查询；catch 能处理异常，不能撤回已执行的副作用。验证要检查返回结果、异常策略及访问计数，并分别覆盖普通 getter、代理和撤销代理。

对应讲解：[判断副作用](#effects)。

<a id="d02-08"></a>

### D02-08 [P0·编码] 怎样判断一个值是没有空位的字符串数组？

**回答：** 先明确契约是否允许空数组、包装字符串、空位和最大长度，再用 `Array.isArray` 确认容器。若不允许空位，对每个索引要求 `Object.hasOwn(value, index)`，再检查值的 `typeof` 为 `'string'`。数量上限应在循环前判断。本章示例允许空数组，但拒绝空位、继承索引和非原始字符串。

**追问：为什么不能只用 every？** every 会跳过没有可访问元素的位置，稀疏数组可能错误通过；原型属性也可能掩盖空位，所以需要自身索引检查。该函数仍不承诺任意访问器或 Proxy 都无副作用，必须注明输入范围。验证包括空数组、正常数组、混合值、稀疏数组、继承索引和超长数组。

对应讲解：[字符串数组校验](#validation)。

<a id="d02-09"></a>

### D02-09 [P1·工程取舍] 接口字段类型正确，为什么还需要结构、范围与业务校验？

**场景：** 用户更新接口返回对象，id 是字符串、age 是数字，但空 id、负数年龄和多出的 role 字段进入状态层。

**回答：** 字段类型只解决基本分类。还要明确字段是否必选、是否是自身字段、值的长度与范围、未知字段策略和缺省处理。边界校验成功后返回明确的已验证数据，再交业务层；不能让任意多余字段通过对象展开进入敏感更新路径。本章窄例拒绝未知字段，不自动转换 id，年龄要求安全整数和范围。

**追问：schema 通过就能允许操作吗？** 不能。权限、当前状态和跨记录关系需要业务校验，权威验证与授权由服务端执行。前端检查用于尽早发现契约问题并改善交互，不能替代服务端决策。

**验证依据：** 覆盖缺字段、错误类型、范围边界、未知字段与合法数据，核对错误路径和输出字段；业务测试再覆盖无权限、状态变化和并发导致的数据失效。

对应讲解：[运行时校验](#validation)、[schema 选择](#schema)。

<a id="d02-10"></a>

### D02-10 [P1·工程取舍] 手写校验与 schema 校验如何选择，错误处理和性能如何验证？

**场景：** 多个页面分别校验嵌套接口，规则逐渐不同；有的接受数字字符串，有的拒绝，错误提示也没有稳定路径。

**回答：** 窄且稳定的局部契约可以手写；多入口共享和复杂嵌套优先统一成熟 schema，复用项目已有依赖。先确定严格判断还是转换、未知字段处理、输出是否规范化、收集首个还是全部错误，以及规模限制。错误结果应包含路径和规则信息，使调用方能定位问题；不能将所有失败简单兜成空列表。

**追问：大批量校验太慢怎么办？** 先测真实规模，区分 schema 创建或编译成本与执行成本，复用 validator；比较有效和无效输入，限制数组长度、嵌套深度和文本大小。可在可信入口校验后复用结果，但必须约定数据不会被绕过更新路径修改。

**验证依据：** 同一批契约样本用于新旧实现，核对接受范围、错误路径、转换结果和原输入是否变化；性能测试测冷启动及热执行的延迟和分配，而不是只测一个小对象。

对应讲解：[手写与 schema](#schema)。

<a id="d02-11"></a>

### D02-11 [P1·原理] TypeScript 类型断言能替代接口数据的运行时校验吗？

**回答：** 不能。类型断言只是告诉编译器按某种类型看待值，不会检查接口内容；类型信息在运行时通常被擦除。外部数据应先作为 unknown 进入校验，通过实际检查得到可信输出。自定义类型谓词也不自动证明实现正确，写错判定逻辑仍会使后续静态推断不可靠。

**追问：类型检查通过后就永远有效吗？** 不一定。可变对象后续可能被其他共享引用修改，缓存的校验结论会过时。应明确所有权和更新约定，关键边界按需要重新验证。测试必须使用运行时错误数据，而不只验证 TypeScript 能否编译。

对应讲解：[运行时校验](#validation)、[结果复用](#schema)。

<a id="d02-12"></a>

### D02-12 [P1·工程取舍] 旧项目使用 jQuery.type，迁移时怎样保持原有契约？

**场景：** 升级 jQuery 4.0 后，旧工具函数中的 `$.type` 不再可用，已有分支按 `'array'`、`'date'` 等字符串执行。

**回答：** `jQuery.type` 从 3.3 弃用、4.0 移除。先盘点调用点和实际版本，建立旧行为样本，确认分类究竟服务于数组操作、实例处理还是业务校验。随后按目标替换：数组用 `Array.isArray`，原始值用 typeof，业务数据用结构校验。需要保留旧标签时，用范围明确的适配器集中兼容，并安排调用方迁移。

**追问：为什么不能统一替换成 typeof 或通用标签方法？** typeof 会把数组、日期归为 object；标签方法又存在包装值同名和标签伪装。任何替换都应以原契约和真实输入为依据，不宣称完全等价。

**验证依据：** 对原始值、空值、数组、包装对象、日期、BigInt、Symbol 和自定义对象做分类与业务分支对比，检查不支持输入的错误行为；不为解决这个历史问题重新引入整套依赖。
