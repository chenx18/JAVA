# JavaScript 垃圾回收机制、内存泄漏与资源清理

上一篇讲数据怎样保存以及函数返回后为何仍可使用，本篇继续解释：**什么数据能回收、引擎怎样回收、为什么有了 GC 仍会泄漏，以及业务结束时怎样清理。**

**口述总览：** JavaScript 引擎自动管理普通对象内存，主要检查程序是否还能通过引用找到对象。从当前活动的函数、全局状态等起点出发，已经找不到的数据才具备回收条件，具体时机不确定。标记与回收解决哪些数据可以释放，分代和增量等策略控制回收成本；业务不再需要却仍被持有的数据，需要应用解除多余引用和结束相应资源。

## 二、知识讲解

<a id="lifecycle"></a>

### 1. 内存生命周期：分配 → 使用 → 回收

**口述：** 程序创建数据时需要分配内存，执行过程中读取或修改数据，程序无法再沿引用找到数据后，它才具备回收条件。JavaScript 自动完成普通对象的内存管理，开发者仍要控制对象被谁持有，以及业务资源何时结束。

例如打开报告页，程序创建报告对象并读取其中的 rows。离开页面后，业务可能已经不需要它；但如果模块缓存或订阅回调仍持有它，引擎就可能继续保留这份数据。

这里有两种判断：

- **业务是否还需要**：由功能和生命周期决定。
- **程序还能否找到它**：看是否还有从活动函数、全局状态等起点通向它的引用路径。

GC 是 Garbage Collection，即垃圾回收。它处理内存管理，不能替业务判断报告缓存该保留多久，也不会可靠地替应用决定何时关闭连接。

<a id="k01"></a>

### 2. 程序还能找到对象吗：回收的判断依据

**口述：** 引擎会从当前活动的函数、全局状态等起点出发，沿引用检查还能否找到对象。能找到，就要支持程序继续访问；找不到，才具备回收条件。赋 null 只解除一条引用，函数返回也不保证所有相关数据立即消失。

#### 2.1 根和引用路径怎样理解？

这些检查起点通常称为“根”。回收器从它们出发，沿引用寻找对象。典型路径可能来自：

- 活动调用仍需要的数据。
- 可访问的全局对象、模块状态。
- 宿主环境仍持有的任务、监听或回调。

不是所有对象都直接连到根。根可以先访问一个容器，再通过它的属性、集合条目或回调环境访问其他数据。

```text
根 / 活动状态
    |
模块 cache
    |
报告对象
    |
rows 数组
```

沿这条路径仍能找到 rows，所以程序还可以通过 cache 访问它。回收器不会因为你认为“页面已经退出”，就自行删除 cache 中的业务记录。

#### 2.2 为什么赋 null 不等于立即回收？

<!-- example: c16-gc-two-references -->
```js
let report = { rows: ['row-1', 'row-2'] };
const cache = new Map();
cache.set('report-1', report);

report = null; // 只解除 report 这一条引用
console.log(cache.get('report-1').rows.length); // 2

cache.delete('report-1'); // 再解除缓存中的引用
console.log(cache.size); // 0
```

最后一行只证明缓存已为空。假设已经没有其他路径能让程序找到这个对象，它就具备回收条件；**输出不能证明 GC 已经发生。**

#### 2.3 循环引用为什么仍可能被回收？

<!-- example: c16-gc-cycle -->
```js
let first = {};
let second = {};

first.other = second;
second.other = first;
console.log(first.other === second, second.other === first); // true true

first = null;
second = null;
```

在这个独立例子里，最后没有其他地方持有这两个对象。从外部起点已经找不到它们，整个环仍然具备回收条件。不能把历史上引用计数难以处理循环的问题，直接套到现代引擎根据引用路径判断回收条件的方式上。

<a id="mark-sweep"></a>

### 3. 回收算法：标记清除、整理与引用计数

**口述：** 标记清除从检查起点出发，沿引用标记还能找到的对象，再回收已经找不到的对象占用的空间。两个对象即使互相引用，只要从起点找不到整个环，也能被回收。引用计数关注引用数量，简单模型会受到循环引用影响。整理用于减少碎片，与判断哪些对象能回收是不同的工作。

#### 3.1 标记清除怎样执行？

先看这个逻辑图：

```text
根 -> cache -> 对象 A -> 对象 B

对象 C <----> 对象 D
（根没有路径到 C 或 D）
```

按简化的标记清除模型，可以分成三步：

1. **标记**：从根出发沿引用访问，标记 cache、A、B 等沿这条路径还能找到的数据。
2. **识别从起点找不到的数据**：C、D 虽然相互引用，但从根找不到，因此不会因这条内部循环而被保留。
3. **清除并复用空间**：回收从检查起点已经找不到的对象所占的空间，用于后续分配。

这是一种帮助理解的算法模型，不是可以用 JavaScript 打印出来的实时 GC 过程。实际引擎会处理更多特殊引用、对象区域和执行阶段。

开发者执行 a = null 只是改变一个变量的值，不是在手动执行 GC 的“标记”阶段。

#### 3.2 为什么清除以后，还可能需要整理？

回收从检查起点已经找不到的对象后，可用空间可能分散在仍存活对象之间，形成碎片。

```text
清除后： [存活 A] [空闲] [存活 B] [空闲]
整理后： [存活 A] [存活 B] [较连续的空闲空间]
```

**整理（compaction）**会按需要移动部分存活对象，改善空间布局；引擎同时更新相关引用，程序仍访问同一个逻辑对象。

“标记—整理”与“标记—清除”是理解回收工作的常见模型。具体引擎可能清扫部分区域、整理部分区域或采用复制等策略，不保证每次都按固定顺序整理整个堆。

<a id="reference-counting"></a>

#### 3.3 引用计数为什么容易被循环引用影响？

在简单引用计数模型中：

- 增加一个持有者，就增加引用计数。
- 解除一个持有者，就减少引用计数。
- 计数降为零，就可以回收。

对前面的 first、second 例子，假设采用这种模型：即使外部变量都变成 null，两个对象之间仍各有一条引用，因此计数可能仍不为零，简单计数模型无法仅靠零计数回收它们。

标记清除则从根出发判断，即使对象之间互相引用，只要从根找不到整个环，依然能回收。

**面试要说明：** 引用计数用于对照理解历史模型，不能把现代 JavaScript 的普通对象回收描述为“引用计数为零才会回收”。

<a id="generational"></a>

### 4. 引擎进阶：怎样降低回收成本？

**口述：** GC 需要扫描关系、回收空间，有时还要移动对象，因此也消耗时间和 CPU。分代利用对象存活特征缩小部分回收的范围；增量、并行和并发分别改善工作安排或暂停成本。它们可以组合使用，具体实现由引擎和版本决定。

#### 4.1 分代：为什么区分新生代和老生代？

很多对象创建后很快就不再需要，例如临时计算结果和某次操作产生的数据。也有对象长期存活，例如应用状态和仍有用途的缓存。

以 V8 常见的分代思路理解：

- **新生代**主要容纳新创建的对象，通常需要较频繁地处理短命对象。
- **老生代**管理较长期存活的对象；对象可能按引擎规则从新生代晋升。
- **Minor GC**主要针对新生代。
- **Major GC**涉及老生代及更广范围；具体范围、命名和算法组合依实现而定，不能理解为永远只扫描老生代。

新生代的常见方案包括复制存活对象，例如 V8 的 Scavenger；也存在其他回收策略。老生代常涉及标记、清扫及按需整理。不要把某篇旧 V8 文章中的空间大小、晋升次数或算法组合当成永久规则。

分代的主要收益来自：**许多新对象已经不再需要，不必每次都为它们执行与整个大堆相同范围的工作。**

#### 4.2 老生代指向新生代，怎样避免漏掉对象？

假设一个长期缓存已经位于老生代，又保存了一个新创建的对象：

```text
程序仍能访问的老生代缓存 -> 新对象
```

如果新生代回收完全忽略这条引用，就可能错误地认为程序已经无法访问这个新对象。因此引擎需要知道这些跨代关系。

**写屏障（write barrier）**可以理解为：程序修改引用时，引擎执行的一段辅助记录逻辑。相关记录通常称为**记忆集（remembered set）**等结构。

新生代回收利用这些记录检查来自老生代的引用，避免每次完整扫描整个老生代。这些记录由引擎维护，不是开发者手写的引用计数器。

<a id="gc-scheduling"></a>

#### 4.3 增量、并行和并发有什么区别？

有些 GC 阶段需要暂停 JavaScript，这通常称为 **Stop-the-world**。暂停是针对相关运行时的程序执行，不是让整台电脑停止。

三种优化解决不同问题：

- **增量**：把部分回收工作切成多段，让 JavaScript 在这些工作片段之间运行，减少单次长暂停。
- **并行**：多个 GC 线程同时处理回收工作，加快这一阶段；对应阶段的 JavaScript 仍可能暂停。
- **并发**：部分 GC 工作与 JavaScript 同时进行，但仍可能需要暂停或协调来完成某些阶段。

并行和并发的区别在于：前者强调多个 GC 工作者一起干活，后者强调 GC 与业务执行能同时推进。两者可以结合，增量也可以与它们配合。

增量或并发期间，程序可能继续修改引用关系；引擎需要写屏障等机制维护标记的正确性。并发并不等于没有暂停，这些优化也不保证降低所有总耗时或 CPU 成本。

#### 4.4 没有泄漏，为什么也可能频繁 GC 或卡顿？

大量临时对象虽然最终可以回收，但反复分配、扫描、复制和回收仍会产生开销。

因此，要区分：

- **持续多余保留**：业务结束的数据仍被持有，可能形成泄漏。
- **频繁临时分配**：数据能回收，但回收成本和暂停可能影响性能。
- **合理的高占用**：当前业务确实需要的大数据或有界缓存。

优化时先找实际分配热点和运行开销，再考虑减少无意义的临时对象、降低重复频率或限制数据规模。不要没有测量就把所有对象池化或随意延长对象寿命。

<a id="k02"></a>

### 5. 内存泄漏：有了 GC，为什么还会泄漏？

**口述总结：** 内存泄漏是业务已经不需要的数据，仍被缓存、回调等持有者长期保留，程序依然能沿引用找到它。常见持有者包括缓存、长期监听器、定时器和订阅中的回调。排查时先固定操作、观察趋势，再比较快照，沿引用找到谁还持有它；修复后用同样操作复测。一次内存升高不能直接证明泄漏。

#### 5.1 是什么：业务结束了，引用却没有结束

假设用户进入一个报告页面时加载数据，退出时已经不需要保留报告。但模块中的 `Map` 仍不断保存旧报告：

<!-- example: c16-leak-cache -->
```js
const reportCache = new Map();

function openReport(id) {
  const report = { rows: new Array(1000).fill('row') };
  reportCache.set(id, report);
}

for (let id = 1; id <= 3; id += 1) {
  openReport(id);
  // 假设每次看完就退出，且业务不需要缓存旧报告。
}

console.log(reportCache.size); // 3

// 缓存所有者在适当的结束时机删除不再需要的数据。
reportCache.clear();
console.log(reportCache.size); // 0
```

问题不是 `Map` 不能回收，而是 **`reportCache` 仍保留报告对象**。如果持续加入报告，又没有删除或容量限制，就可能持续占用内存。

反过来，如果缓存有明确用途和合理容量，保留数据可以是正常设计。是否泄漏要结合业务用途和引用路径判断。

#### 5.2 为什么：长期持有者延长了短期数据的生命周期

常见引用路径：

```text
长期模块 → Map 缓存 → 旧报告
window → 事件监听器 → 回调闭包 → 已退出页面的数据
活动定时器 / 订阅表 → 回调 → 页面状态
应用集合 → 已移除的 DOM 节点
```

理解它们时抓住三个点：

- **闭包本身不等于泄漏。** 当回调仍被长期对象保存时，它需要的数据也可能继续被保留。
- **移除 DOM 不等于解除所有引用。** 例如节点已从页面删除，但仍被数组、监听器或回调使用。
- **清理一条引用不等于清理所有引用。** 清掉定时器后，还可能有监听器、订阅或缓存持有同一份数据。

真正要问的是：**这个持有者为什么还存在？它什么时候应该解除对旧数据的持有？**

<a id="k05"></a>

#### 5.3 怎么排查：趋势 → 快照 → 持有者 → 复测

以 Chrome DevTools 为例：

1. **固定复现操作。** 例如“进入页面 → 加载固定数据 → 退出 → 等清理完成”，重复相同轮数。比较相同空闲阶段，控制预热和数据量。
2. **观察趋势。** 先看 JS heap、DOM 节点和监听器数量等是否跨轮增长。若主要现象是卡顿，也用 Performance 检查重复任务、长任务和渲染耗时。
3. **比较快照。** 在 Memory 的 Heap snapshot 中取基线快照 A，重复操作后取 B。在 B 的 Comparison 中选择 A，寻找不应跨轮增加的对象。
4. **追踪谁还持有它。** 选中存活实例，在 Retainers 沿引用往回找，直到找到实际根持有者，例如模块缓存、window 监听器或活动任务。再核对它的业务生命周期。
5. **修复并复测。** 删除多余缓存、解绑监听或结束任务，再用同样输入、轮数和观察点复测；同时覆盖失败、取消和卸载路径。

先把这几个现象分开：

- **瞬时峰值**：大量临时数据分配时会升高，之后可能回落。
- **高占用**：可能来自正常大数据、有界缓存，也可能来自多余保留，需要继续定位。
- **持续泄漏**：已经结束的功能仍不断积累不应保留的数据。
- **频繁 GC**：大量临时分配也可能频繁触发 GC 并造成性能问题，未必存在泄漏。

JS heap 主要反映 JavaScript 堆；Node.js 的 RSS 是进程驻留内存，还包含其他内存开销。浏览器进程也有图片、原生资源等开销，不能把进程总量都当成 JS 对象。

一次手动 GC 后数字下降，只说明当时存在可回收数据。**修复依据是多余保留链消失，且相同操作不再每轮积累。** 控制台日志、选中的 DOM 节点和暂停调试也可能保留对象，排查时要控制这些干扰。

<a id="k03"></a>

### 6. 资源清理：业务结束时怎样正确收尾

**口述总结：** GC 负责回收内存，资源清理负责结束业务工作，两者不能互相替代。创建监听、定时器、订阅或任务的所有者，要在完成、失败、取消和卸载时统一清理。清理应允许重复调用，一个释放动作失败也要继续处理其他资源；共享服务由其所有者关闭，使用者只释放自己取得的部分。

#### 6.1 是什么：停止工作，并解除不再需要的持有

资源清理不只是把变量设成 `null`。它通常包含：

- 停止继续触发的工作，例如清除定时器、取消支持取消的请求。
- 解除注册关系，例如解绑监听、退订消息、断开 Observer。
- 释放专用资源，例如终止 Worker、撤销 Blob URL、关闭自己拥有的连接。
- 解除应用对大数据和旧状态的持有，例如删除缓存项、清空已结束对象里的数据字段。

这些动作有明确业务时机。即使对象以后能被 GC，任务也不应该在页面结束后继续工作。

#### 6.2 为什么：垃圾回收不能决定业务什么时候结束

例如，一个组件已卸载，但它的定时器还在执行。定时器持有回调，回调持有组件状态，GC 仍可能沿这条路径找到数据。此时需要组件所有者主动清除定时器，而不是等待 GC 帮忙决定何时停止。

监听器清理还要求匹配注册时的回调身份和 `capture`：

<!-- example: c16-listener-identity -->
```js
const target = new EventTarget();
let calls = 0;

function onMessage() {
  calls += 1;
}

target.addEventListener('message', onMessage);
target.dispatchEvent(new Event('message'));

target.removeEventListener('message', onMessage);
target.dispatchEvent(new Event('message'));

console.log(calls); // 1
```

注册和解除时用了同一个 `onMessage`。两次调用 `handler.bind(this)` 会生成两个不同的函数，不能靠第二次 `bind` 解除第一次注册的监听。

同样，`AbortController` 只发送取消信号。接收并支持该信号的 API 才会响应，普通定时器和第三方订阅不会因此自动清理。

#### 6.3 怎么做：由所有者统一收尾

先确定三件事：

1. **谁拥有资源？** 组件通常拥有自己的监听和订阅，共享连接由服务所有者管理。
2. **什么时候结束？** 完成、失败、取消和卸载应接入同一收尾路径；初始化失败也要释放已经取得的资源。
3. **结束后还允许什么？** 迟到回调要检查状态；重复清理应安全；一次释放失败不能阻断其他清理。

先用一个基础例子理解：挂载时注册监听和定时器，结束时同时解除；`closed` 让重复清理安全，也阻止迟到回调继续工作。

<!-- example: c16-owner-basic -->
```js
function mount(target) {
  let closed = false;
  let handled = 0;

  function onMessage() {
    if (!closed) handled += 1;
  }

  target.addEventListener('message', onMessage);
  const timer = setInterval(onMessage, 60000);

  return {
    get handled() { return handled; },
    dispose() {
      if (closed) return;
      closed = true;
      clearInterval(timer);
      target.removeEventListener('message', onMessage);
    },
  };
}

const target = new EventTarget();
const scope = mount(target);
target.dispatchEvent(new Event('message'));
console.log(scope.handled); // 1

scope.dispose();
scope.dispose();
target.dispatchEvent(new Event('message'));
console.log(scope.handled); // 1：结束后不再处理事件
```

基础例子只展示正常结束。真实项目取得多个资源时，每成功取得一个就登记释放动作；初始化失败也清理已经取得的部分。释放时逐项处理并收集错误，避免一个失败阻断其他资源。

共享服务由更长寿命的所有者关闭，组件通常只解除自己的订阅。资源和回调停止后，还要解除已结束对象对大数据的持有。完整代码和异常验证放在[进阶补充 E](#cleanup-code)，第一遍先把所有者与结束时机讲清楚。

真实项目按资源协议注册释放动作：

- 定时器用 `clearTimeout` / `clearInterval`。
- 监听器用同一个回调和匹配的 `capture` 解绑，或由支持 `signal` 的监听器接收取消信号。
- 订阅用 `unsubscribe`，Observer 用 `disconnect` 或按需 `unobserve`。
- 请求向支持取消的 API 传递 `AbortSignal`；不支持取消时也要拒绝过期结果，但这不等于底层工作停止。
- Worker 用 `terminate` 并处理被中断的待办任务，专用连接按协议 `close`。
- Blob URL 用 `URL.revokeObjectURL`；流的取消和读取锁释放要区分，见进阶补充。

生产代码需要同时报告原始任务错误和清理错误，并按资源协议决定是否重试；异步释放需要等待和汇总结果，不能直接套用同步清理。`FinalizationRegistry` 的回调时机不确定，不能替代上述结束协议。

### 进阶补充：第一遍可先略读

<a id="k04"></a>

#### A. 容量、TTL、LRU 与 WeakMap 各自解决什么

**口述总结：** 容量管保留多少，TTL 管多久有效，LRU 管优先淘汰谁，WeakMap 适合跟随对象键寿命的元数据。它们解决不同问题，可以按场景组合，不能互相替代。

- **容量**：最多保留多少条，必要时再控制可估算的字节预算。条目数上限不是固定内存上限。
- **TTL**：超过有效时间就过期。只在 `get` 时删除过期项，会让永不再访问的旧项继续占位，需要容量或周期清理配合。
- **LRU**：优先淘汰最近最少访问的项。它决定淘汰顺序，不自动提供过期时间。
- **WeakMap**：不会仅凭映射关系延长对象键的寿命，适合对象元数据；它不提供 `size`、枚举或可预测的回收时间。

如果对象键仍被其他业务集合长期保存，换成 WeakMap 也不能让它消失。业务需要字符串 ID、可枚举记录和可控预算时，通常使用有界 Map 策略。LRU 编码例子见 [C30-03](#c30-03)。

#### B. 引擎机制复习入口

具体机制已在正文解释：[标记、清除与整理](#mark-sweep)、[分代及跨代引用](#generational)、[增量、并行与并发](#gc-scheduling)。先会说每种机制解决什么问题，再按岗位深入某个 V8 版本。


#### C. 流的 releaseLock、cancel 和 abort 不一样

**口述总结：** 释放读取锁，只是不再由这个 reader 占用流；取消消费、取消网络请求和停止服务器任务，是不同层次的动作，需要按协议传播。

- `reader.releaseLock()` 释放读取锁，其他 reader 才能取得锁；它不表示取消流或服务器工作。
- `reader.cancel(reason)` 表示消费者不再需要数据，向底层源发出取消请求。
- `AbortController.abort()` 可以取消接收对应信号的 fetch 等操作；它不会自动取消任意业务任务。
- 服务器是否停止生成内容，需要应用协议把取消传播到任务的实际所有者。客户端停止读取，不能单独证明服务端任务已经结束。

由谁取得 reader、谁发起请求、谁拥有远端任务，决定应由谁执行哪一层清理。不要把“释放 JS 引用”与“停止外部业务”混成同一动作。

#### D. 快照中的大小只是排查线索

Shallow Size 是对象自身在该快照中的大小；Retained Size 还包括那些必须经过它才能从根访问到的数据。当程序无法再找到这个对象时，这些数据可能随它一起具备回收条件。通过其他路径仍能访问的共享数据不归它独占，父子对象的 Retained Size 可能重叠，不能相加。

Comparison 的分配和释放大小差值也不能直接当成 Retained Size。需要时用 Allocation 记录查“在哪里创建”，再用 Retainers 查“谁还持有”；结合业务结束时机才能判断是否多余保留。

<a id="cleanup-code"></a>

#### E. 完整实现：异常路径、重复清理与共享所有权

下面是完整的统一清理例子。共享服务保存订阅，组件取得监听、定时器、订阅和缓存项；`dispose` 逐项清理，并解除大数组的持有。为了验证异常路径，第二个组件还注册了一项会抛错的模拟释放动作。

<!-- example: c16-owner-cleanup -->
```js
function createService() {
  const subscribers = new Set();

  return {
    closed: false,
    subscribe(callback) {
      if (this.closed) throw new Error('service closed');
      subscribers.add(callback);
      return () => subscribers.delete(callback);
    },
    emit() {
      for (const callback of subscribers) callback();
    },
    close() {
      this.closed = true;
      subscribers.clear();
    },
    get size() { return subscribers.size; },
  };
}

function mount(target, service, cache, options = {}) {
  const controller = new AbortController();
  const cacheKey = {};
  const cleanups = [() => controller.abort()];
  const errors = [];
  let rows = new Array(1000).fill('row');
  let closed = false;
  let handled = 0;

  function onMessage() {
    if (closed) return;
    handled += 1;
  }

  function dispose() {
    if (closed) return errors.slice();
    closed = true; // 先禁止迟到回调继续工作

    while (cleanups.length > 0) {
      const cleanup = cleanups.pop();
      try {
        cleanup();
      } catch (error) {
        errors.push(error);
      }
    }

    rows = null; // 即使外部保存 scope，也不再通过它保留大数组
    return errors.slice();
  }

  try {
    target.addEventListener('message', onMessage);
    cleanups.push(() => target.removeEventListener('message', onMessage));

    const timer = setInterval(onMessage, 60000);
    cleanups.push(() => clearInterval(timer));

    cleanups.push(service.subscribe(onMessage));

    cache.set(cacheKey, rows);
    cleanups.push(() => cache.delete(cacheKey));

    if (options.releaseThrows) {
      cleanups.push(() => { throw new Error('release failed'); });
    }
    if (options.fail) throw new Error('init failed');

    return {
      dispose,
      signal: controller.signal,
      get handled() { return handled; },
      get retainedRows() { return rows?.length ?? 0; },
    };
  } catch (error) {
    const cleanupErrors = dispose();
    if (cleanupErrors.length > 0) {
      throw new AggregateError([error, ...cleanupErrors],
        'initialization and cleanup failed', { cause: error });
    }
    throw error;
  }
}

const target = new EventTarget();
const service = createService();
const cache = new Map();

const first = mount(target, service, cache);
const second = mount(target, service, cache, { releaseThrows: true });

target.dispatchEvent(new Event('message'));
service.emit();
console.log(first.handled, second.handled, service.size, cache.size);
// 2 2 2 2

first.dispose();
first.dispose(); // 重复调用安全
console.log(first.signal.aborted, first.retainedRows,
  service.size, cache.size, service.closed);
// true 0 1 1 false：只清理自己的资源，共享服务仍可用

target.dispatchEvent(new Event('message'));
service.emit();
console.log(first.handled, second.handled); // 2 4

const errors = second.dispose();
console.log(service.size, cache.size, second.retainedRows,
  second.signal.aborted, errors[0].message);
// 0 0 0 true release failed：某项抛错，其他清理仍完成

try {
  mount(target, service, cache, { fail: true });
} catch (error) {
  console.log(error.message, service.size, cache.size); // init failed 0 0
}

service.close(); // 共享服务由它的所有者最后关闭
console.log(service.closed); // true
```

这个例子验证的是**可确定的清理行为**：解绑和退订后不再响应事件，缓存项被删除，取消信号已发出，已结束的 scope 不再保存大数组。它没有证明 GC 已执行，也没有请求整页内存归零。

释放异常可能是任意抛出值，因此先原样收集，不能在清理循环里假设它一定有 `message`。示例输出读取的是已知模拟 Error 的 `message`。初始化与释放同时失败时，`AggregateError` 保留两类错误，并以 `cause` 标明初始化错误，避免清理问题被吞掉。

## 三、知识小结与分层复习

**整章口述：** JavaScript 自动管理普通对象内存，GC 主要检查程序是否还能通过引用找到对象。标记阶段从检查起点沿引用找到仍能访问的对象，清除阶段回收已经找不到的对象所占的空间，整理按需要减少碎片；分代、增量、并行和并发用于降低不同方面的回收成本。业务已经结束的数据如果仍被多余引用保留，GC 不能替业务解除这条路径，资源要由所有者明确清理。

- **初级：讲清概念。** 能解释自动管理、沿引用查找对象，以及赋 null 与函数返回为什么不等于立即回收；理解内存占用高不一定泄漏。
- **中级：解释机制。** 能画根与对象的引用图，推导标记清除为什么能回收从根找不到的循环，比较引用计数；能说明常见泄漏路径和正确解绑。
- **高级：分析与验证。** 能解释分代、跨代引用和暂停优化的目的，区分内存增长、频繁分配和 GC 暂停；能找到根持有者、选择清理策略，并用同条件复测说明效果。

优先复习 C30-06、C30-13、C30-14，再练 C30-01、C30-08、C30-09；进阶机制看 C30-15、C30-16，工程练 C30-02、C30-10、C30-12。缓存与流的细节按需要查附录。

参考：[MDN：内存管理](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Memory_management)、[V8：Trash talk](https://v8.dev/blog/trash-talk)、[V8：Concurrent marking](https://v8.dev/blog/concurrent-marking)、[Chrome DevTools：Heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)。V8 博文用于说明具体实现思路，不代表所有版本都采用相同空间、阈值或算法组合。

<a id="c30-01"></a>

### C30-01 [P0·原理] 循环引用或闭包一定泄漏吗？

**回答：** 不一定。现代 GC 主要检查从根出发还能否找到对象，从根已经找不到的循环仍能回收。闭包也只是让函数继续访问所需环境；只有业务已结束的数据还被长期回调、缓存等保留，才需要排查多余持有。不能只根据“有环”或“用了闭包”下结论。

对应讲解：[垃圾回收](#k01)、[长期保留链](#k02)。

<a id="c30-02"></a>

### C30-02 [P0·工程取舍] 如何排查页面越用越占内存？

**回答：** 固定进入、加载、退出等操作和空闲观察点，先看跨轮增长趋势，再对比 Heap Snapshot。在 Comparison 找不应持续增加的对象，沿 Retainers 找根持有者，核对缓存、监听、订阅或任务的结束时机。修复后重复相同操作，并覆盖失败和取消路径。

**追问：刷新恢复就能证明泄漏吗？** 不能。刷新会重置许多状态，重复工作、任务积压或缓存过大也可能恢复，需要保留路径和业务用途等证据。

对应讲解：[排查与证明修复](#k05)。

<a id="c30-03"></a>

### C30-03 [P1·编码] 实现容量有界的LRU缓存。

**回答：** 用 Map 的插入顺序保存访问顺序，读取命中项时移动到末尾，超容量时删除开头。下例只按条目数量限制容量，不包含 TTL、字节预算或持久化。

<!-- example: c16-lru -->
```js
class LRU {
  constructor(capacity) {
    if (!Number.isSafeInteger(capacity) || capacity < 1) {
      throw new RangeError('positive capacity required');
    }
    this.capacity = capacity;
    this.cache = new Map();
  }

  has(key) { return this.cache.has(key); }

  get(key) {
    if (!this.cache.has(key)) return undefined;
    const value = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, value);
    return value;
  }

  set(key, value) {
    this.cache.delete(key);
    this.cache.set(key, value);
    if (this.cache.size > this.capacity) {
      this.cache.delete(this.cache.keys().next().value);
    }
    return this;
  }
}

const cache = new LRU(2);
cache.set('a', 1).set('b', 2);
cache.get('a');
cache.set('c', 3);
console.log(cache.has('a'), cache.has('b')); // true false
```

**追问：怎么测试？** 验证 get 刷新顺序、重复 set、容量 1、值为 undefined 和持续插入。`has` 用来区分“没有这个键”与“值恰好为 undefined”。

对应讲解：[容量、TTL、LRU 与弱引用](#k04)。

<a id="c30-04"></a>

### C30-04 [P1·工程取舍] WeakMap、TTL、LRU是不是三种等价缓存？

**回答：** 不是。WeakMap 让对象元数据不单独延长对象键寿命，TTL 管业务有效时间，LRU 管淘汰顺序，容量限制管数量或预算。需要可枚举缓存、字符串键和确定淘汰规则时，不能只把 Map 换成 WeakMap。

对应讲解：[容量、TTL、LRU 与弱引用](#k04)。

<a id="c30-05"></a>

### C30-05 [P1·原理] 释放reader锁是不是取消服务器生成？

**回答：** 不是。`releaseLock` 只释放读取锁，`reader.cancel` 和 fetch 的 abort 分别作用于消费和请求。服务器是否停止生成，还需要应用协议把取消传播到远端任务所有者。解除内存引用和停止外部工作不能混为同一动作。

对应讲解：[资源清理](#k03)、[流的取消边界](#advanced)。

<a id="c30-06"></a>

### C30-06 [P0·基础] JavaScript 的垃圾回收依据是什么？赋 null 会立即回收吗？

**回答：** 现代引擎主要检查程序是否还能通过引用找到对象。从当前活动的函数、全局状态等起点出发，还能找到的数据要保留；找不到才具备回收条件。赋 null 只是让这个变量不再持有原对象，缓存、监听或其他变量仍可能持有它；即使程序已无法找到对象，具体回收时机也由引擎决定。

对应讲解：[垃圾回收](#k01)。

<a id="c30-07"></a>

### C30-07 [P0·工程取舍] 内存占用高就等于内存泄漏吗？

**回答：** 不等于。正常大数据、有界缓存和临时分配都可能提高占用。泄漏需要结合业务已结束的数据是否仍被多余引用保留来判断；观察相同阶段的长期趋势，再查对象和持有者。频繁 GC 可能是临时分配过多，进程 RSS 也不能直接等同于 JS heap。

对应讲解：[内存泄漏与增长趋势](#k02)、[排查步骤](#k05)。

<a id="c30-08"></a>

### C30-08 [P0·原理] 闭包、监听器和缓存为什么容易长期保留数据？

**回答：** 它们本身是正常工具，但长期对象可能通过它们持有短期数据。例如 window 保存监听回调，回调访问已退出页面的数据；模块 Map 也会保留缓存项。问题在于所有者结束后没有解除这条路径。移除 DOM、清掉一个定时器或给一个变量赋 null，都不保证其他路径同时消失。

对应讲解：[长期保留链](#k02)。

<a id="c30-09"></a>

### C30-09 [P0·工程取舍] 资源清理为什么要统一到所有者的结束路径？

**回答：** GC 不能替业务确定停止时机。所有者取得资源后，要在完成、失败、取消和卸载时结束工作，并解除监听、订阅和数据持有。统一收尾能减少某条分支遗漏；组件只释放自己的资源，共享服务或连接由更长寿命的所有者关闭。

对应讲解：[统一资源清理](#k03)。

<a id="c30-10"></a>

### C30-10 [P1·工程取舍] 清理函数应怎样处理初始化失败、重复调用和释放异常？

**回答：** 每取得一个资源就登记释放动作，初始化失败时清理已经取得的部分。清理先设置结束状态，避免迟到回调继续工作，再逐项释放并收集错误，某项失败仍继续处理其他项。重复调用应安全；已结束对象若仍被外部保存，也要解除它对大数据的持有。异步释放还需等待结果。

对应讲解：[清理步骤](#k03)、[完整实现](#cleanup-code)。

<a id="c30-11"></a>

### C30-11 [P1·工程取舍] AbortController 能自动清理所有资源吗？

**回答：** 不能。它发送取消信号，只有接收并实现该信号的 API 才响应。定时器、第三方订阅和自定义缓存仍要显式处理。不支持取消的操作可以拒绝过期结果，但这不表示底层工作停止，也不保证解除所有引用。

对应讲解：[资源清理](#k03)、[取消协议](#advanced)。

<a id="c30-12"></a>

### C30-12 [P1·工程取舍] 如何证明内存泄漏和资源清理问题已经修复？

**回答：** 用修复前后相同的输入、轮数和空闲观察点复测，确认原来的多余保留链消失，不应保留的对象不再每轮积累。同时验证监听、订阅、缓存和任务回到预期基线，覆盖失败、取消、卸载和重复清理。不能只凭一次 GC 后内存下降，也不能要求精确回到零。

**追问：怎样写回归测试？** 对可确定行为做断言，例如退出后不响应事件、订阅数量恢复、缓存符合预算、晚到结果不写旧状态、重复清理安全。GC 时机不可控，不应写成“调用 dispose 后对象立即被回收”的普通单元测试。

对应讲解：[排查步骤](#k05)、[统一资源清理](#k03)。

<a id="c30-13"></a>

### C30-13 [P0·原理] 标记清除怎样判断和回收垃圾？标记整理又解决什么问题？

**口述回答：** 标记清除从检查起点出发，沿引用标记还能找到的对象，再回收已经找不到的对象所占的空间。它检查的是从起点还能否找到对象，因此即使对象互相引用，只要整个环无法再从起点找到，也能处理。清除可能留下碎片，整理会按需要移动部分存活对象并更新相关引用，改善空间布局；不保证每次回收都整理全部内存。

对应解释：[标记、清除与整理](#mark-sweep)。

<a id="c30-14"></a>

### C30-14 [P0·原理] 引用计数与标记清除有什么区别？循环引用为什么不一定泄漏？

**口述回答：** 简单引用计数依据引用数量，计数为零时回收；相互引用的对象即使从外部已经无法访问，计数也可能仍大于零。标记清除检查从根出发还能否找到对象，找不到的整个环都可回收。现代 JavaScript 的普通对象回收不能仅套用简单引用计数模型。

对应解释：[引用计数对照](#reference-counting)、[从起点找不到的循环](#k01)。

<a id="c30-15"></a>

### C30-15 [P1·原理] 为什么分代回收？新生代回收怎样处理老生代指向它的引用？

**口述回答：** 很多对象创建后很快失去用途，分代让新对象所在区域与长期存活对象采用不同策略，减少每次处理的范围。长期存活对象可能按引擎规则晋升；minor 主要针对新生代，major 涉及老生代及更广范围，具体机制依引擎版本。老生代到新生代的引用由写屏障等机制记录，新生代回收利用这些记录找到程序仍能访问的新对象，避免每次遍历整个老生代。

对应解释：[分代与跨代引用](#generational)。

<a id="c30-16"></a>

### C30-16 [P1·原理] 增量、并行和并发 GC 有什么区别？为什么仍可能暂停 JavaScript？

**口述回答：** 增量把部分工作切成小段，让 JavaScript 在间隙运行；并行让多个 GC 线程同时处理工作，对应阶段仍可能暂停业务线程；并发让部分 GC 工作与 JavaScript 同时进行，但仍有需要暂停或协调的阶段。这些策略可以组合，分别改善单次停顿或处理效率，不能承诺零暂停，也不等于减少所有总成本。

**追问：引用关系在 GC 期间被修改怎么办？** 引擎需要写屏障等机制维护必要的标记信息和引用记录，不能把增量或并发理解成“扫描完就不管后续变化”。

对应解释：[暂停优化](#gc-scheduling)。
