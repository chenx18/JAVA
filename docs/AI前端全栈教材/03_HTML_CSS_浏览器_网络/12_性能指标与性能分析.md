# 12 性能指标与分析方法

性能应从用户任务出发，分别看加载速度、交互响应和视觉稳定性。指标是定位与验收的证据，不是把页面压成一个总分。

## 二、知识讲解

<a id="k01"></a>

### 1. 加载、交互与稳定性指标

| 指标 | 观察维度 | 不能直接推出 |
| --- | --- | --- |
| TTFB | 等待首字节 | 不只包含数据库耗时 |
| FCP | 首次内容绘制 | 不代表主要内容已完成 |
| LCP | 主要大块内容的绘制时机 | 不等于所有资源下载完 |
| INP | 用户交互响应的综合延迟 | 不只是事件处理函数执行时间 |
| CLS | 意外布局偏移的累计体验 | 不等于帧率 |

常用Core Web Vitals良好参考线为LCP不高于2.5秒、INP不高于200毫秒、CLS不高于0.1，现场评估通常关注第75百分位并区分设备等条件。它们不是项目唯一验收标准，也不是沿一条TTFB→INP→CLS时间线顺序发生。

INP已替代FID成为核心指标之一，旧资料只谈首次输入会遗漏整个访问期间的交互问题。

<a id="k02"></a>

### 2. 实验室与真实用户数据

实验室测试固定网络、设备和脚本，适合复现与对比；真实用户监控反映设备、网络、地区和交互分布，适合评估实际覆盖。一次Lighthouse分数不能代表所有用户，实验室代理指标也不能直接等同真实INP。

性能预算应具体到路由、资源体积、交互目标或任务耗时，并使用相同采样口径。平均值可能掩盖慢用户，关注p75/p95及样本规模、分群和版本。

<a id="k03"></a>

### 3. 从网络瀑布到主线程

先看请求是否串行、TTFB、资源体积、压缩和缓存；再看JS下载/解析/执行、长任务、样式布局、绘制和图片字体。大包、第三方脚本、过多DOM与重复计算可能同时存在。

INP可拆到输入等待、事件处理及后续呈现延迟。处理函数很短但主线程被此前长任务占满，交互仍慢；事件回调结束后还可能有渲染工作。

LCP慢时区分资源发现晚、下载慢、主线程忙或内容本身延后生成。CLS常从未预留图片尺寸、字体替换或后插入内容找原因，不是把所有动画都禁止。

<a id="k04"></a>

### 4. 测量 API 与优化验证

```js
// browser-only
function observeLongTasks(report) {
  if (!('PerformanceObserver' in window) ||
      !PerformanceObserver.supportedEntryTypes.includes('longtask')) return () => {};
  const observer = new PerformanceObserver(list => {
    for (const entry of list.getEntries()) report(entry.duration);
  });
  observer.observe({ type: 'longtask', buffered: true });
  return () => observer.disconnect();
}
```

Long Task常以超过50ms的主线程任务为观察阈值，不代表50ms是理想帧预算。Performance marks/measures可标业务阶段，日志需避免暴露敏感数据。

优化流程是建立基线→形成瓶颈假设→做最小相关改动→同条件复测→真实用户观察。拆包、缓存、SSR、虚拟列表、Worker和按帧更新分别解决不同瓶颈，不能只背优化清单。

<a id="summary"></a>

## 三、知识小结

先定义用户体验目标，再分加载、交互和稳定性测量；现场数据与实验室互补；沿网络与主线程证据定位，优化后用同口径对比验证。

参考：[MDN Performance API](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API)；[Web Vitals](https://web.dev/articles/vitals)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="web12-01"></a>

### WEB12-01 [P0·基础] LCP、INP、CLS分别衡量什么？

**回答：** LCP关注主要内容加载体验，INP关注交互响应，CLS关注意外布局偏移。它们是不同维度，不是一个顺序流水线，也不能互相替代。

对应讲解：[加载、交互与稳定性指标](#k01)。

<a id="web12-02"></a>

### WEB12-02 [P0·工程取舍] 页面慢应该先做哪些优化？

**回答：** 先测量定位而非直接选方案。看网络瀑布和缓存，再看主线程长任务、解析执行、布局绘制及DOM量，确认瓶颈后选择拆包、缓存、减少计算或其他对应改动。

对应讲解：[从网络瀑布到主线程](#k03)。

<a id="web12-03"></a>

### WEB12-03 [P1·原理] 事件处理只有10ms为什么INP仍差？

**回答：** 交互可能先等待主线程空闲，处理后还有呈现延迟。INP不是只测回调本身，要结合前序长任务、状态更新和浏览器绘制分析。

对应讲解：[从网络瀑布到主线程](#k03)。

<a id="web12-04"></a>

### WEB12-04 [P1·工程取舍] Lighthouse满分就能证明性能好吗？

**回答：** 不能，它是在特定实验条件下的结果，真实用户设备和行为不同。应结合现场分位数、分群、业务任务和回归监控，并用一致条件验证改动。

对应讲解：[实验室与真实用户数据](#k02)。

<a id="web12-05"></a>

### WEB12-05 [P1·工程取舍] Long Task记录和业务Performance标记各有什么价值？

**回答：** Long Task帮助定位长时间主线程占用，业务marks/measures标明用户流程阶段；两者结合网络和渲染证据更易定位。阈值不是理想帧预算，观测数据也需同口径比较。

对应讲解：[测量 API 与优化验证](#k04)。
