# 04 CSR、SSR、SSG 与混合渲染

渲染策略决定内容在什么时候、由哪里生成，缓存和交互又在另一层。选择应依据页面时效、个性化、SEO和部署成本，而不是认定SSR总比CSR高级。

## 二、知识讲解

<a id="k01"></a>

### 1. 四种策略与成本

| 策略 | HTML主要生成时机 | 适合与代价 |
| --- | --- | --- |
| CSR | 浏览器执行JS后 | 强交互应用，初始内容依赖下载执行 |
| SSR | 服务器处理请求时 | 动态首屏与个性化，需要服务器成本和隔离 |
| SSG/预渲染 | 构建或预生成阶段 | 稳定内容、CDN分发，更新与路由枚举有成本 |
| Hybrid | 按路由组合 | 兼顾不同页面，缓存与部署规则更复杂 |

SSR可改善内容可见性，但服务器等待数据也可能拉长TTFB，客户端仍要执行JS接管。SSG不是内容永远不更新，需发布或再生成机制。

<a id="k02"></a>

### 2. Hydration 与一致性

服务器HTML提供初始内容，客户端hydrate将组件运行、事件和状态接到对应DOM。两端初始输出应保持可解释的一致性。

随机数、Date.now、不同locale/时区、浏览器专有状态、无效HTML结构或两端获取不同数据，都可能导致不匹配。服务端获取结果通过payload共享，浏览器差异放到合适生命周期，不用无条件抑制警告代替修复。

SSR不是把客户端所有工作消除，首屏HTML显示与可交互时间需要分别测量。

<a id="k03"></a>

### 3. 路由规则、再验证与缓存边界

Nuxt routeRules等可为不同路由配置预渲染、缓存或渲染方式，具体SWR/ISR能力依部署适配。不要写一份配置就假定所有Node、Serverless、Edge平台提供相同行为。

公共文章可以长缓存，用户账单或权限相关页面需要隔离或不共享缓存。页面HTML、payload、API与CDN是多个层，任一层混淆用户键都可能产生错误内容。

再验证要明确何时变新、失败时是否允许旧数据、如何失效，不能只背“过期后台刷新”。

<a id="k04"></a>

### 4. 流式SSR与实际选型

流式SSR可在部分内容就绪时先发送，帮助缩短可见等待，但错误状态码一旦头部发出就受限，后续失败需应用协议或边界处理。代理缓冲、浏览器接管和组件异步依赖也会影响实际收益。

选型流程是按页面列内容时效、身份依赖、搜索需求、交互复杂度和部署限制，建立性能基线后验证。可以同一产品公共页SSG、内容页SSR、工作台偏CSR，不必整站一种答案。

<a id="summary"></a>

## 三、知识小结

渲染策略看生成时机，hydration看两端一致，缓存看时效与身份，部署看平台能力。用页面需求和测量选择组合，而不是套固定排名。

参考：[Nuxt Rendering](https://nuxt.com/docs/4.x/guide/concepts/rendering)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="build04-01"></a>

### BUILD04-01 [P0·基础] SSR和CSR有什么主要区别？

**回答：** SSR先在服务器生成HTML，CSR主要由浏览器执行JS生成；SSR仍需要客户端接管交互，并增加服务器数据等待与隔离成本，不能只说一个快一个慢。

对应讲解：[四种策略与成本](#k01)。

<a id="build04-02"></a>

### BUILD04-02 [P0·原理] 为什么SSR还要hydration？

**回答：** 静态HTML没有完整客户端组件状态和事件运行关系，hydrate把运行时与已生成DOM接合。两端初始内容不一致会出问题，需要共享数据和确定性渲染。

对应讲解：[Hydration 与一致性](#k02)。

<a id="build04-03"></a>

### BUILD04-03 [P1·工程取舍] 为什么不能缓存所有SSR页面？

**回答：** 个性化和权限数据可能被共享缓存串给其他用户，还可能陈旧。要按页面/接口区分公共与私有内容，明确缓存键、失效和部署支持。

对应讲解：[路由规则、再验证与缓存边界](#k03)。

<a id="build04-04"></a>

### BUILD04-04 [P1·工程取舍] 一个产品如何选择混合渲染？

**回答：** 按每条路由的内容时效、个性化、SEO、交互和成本选策略，再验证TTFB、内容可见、交互与缓存正确性。不是因为框架支持某特性就全站开启。

对应讲解：[流式SSR与实际选型](#k04)。
