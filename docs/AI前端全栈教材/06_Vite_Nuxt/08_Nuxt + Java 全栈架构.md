# 08 Nuxt 与 Java 的全栈交付边界

前端主力加Java横向能力，应能把页面请求、认证、领域事务与部署连成闭环。BFF是可选边界工具，设计它要有具体职责，而不是为了多一层而多一层。

## 二、知识讲解

<a id="k01"></a>

### 1. 一条业务请求的路径

```text
Browser：展示、交互、提交意图
  → Nuxt/Nitro：SSR或页面数据聚合、必要的入口适配
  → Spring Boot：身份与资源授权、领域规则、事务
  → MySQL：约束与持久化
  → Redis：合适的缓存/短期状态
```

简单页面也可以通过安全设计的API直接访问Java，不必强制所有请求经过BFF。引入BFF要能解释减少了哪些调用、适配或耦合，以及增加了哪些延迟、运维与失败点。

<a id="k02"></a>

### 2. 契约、身份与错误

前后端约定DTO字段、空值、时间时区、金额和大整数ID编码，错误码与HTTP状态保持一致。静态类型可由OpenAPI等生成辅助，但仍需运行时校验与兼容演进。

服务器建立可信用户上下文，BFF转发身份时有明确目标和信任方式；Java不能只相信任意客户端传来的userId或role。Cookie与Bearer方案各有CSRF/XSS和刷新边界。

失败按输入、权限、冲突、限流、技术异常区分。requestId/traceId贯穿各层，日志不要记录密码、长期密钥或完整敏感请求体。

<a id="k03"></a>

### 3. 事务、取消与长任务

数据库事务属于领域服务的确定边界，不应跨整个浏览器交互一直持有连接。创建长任务时先持久化任务与状态，异步执行，前端查询或订阅进度。

取消信号从页面向BFF、Java和下游传播，但服务器已提交事务不能被前端abort自动撤销。写请求重试需要幂等键和结果查询，不能因客户端超时就再次创建业务对象。

AI网关可以统一供应商适配、配额、审计和成本，模型密钥保留服务端；工具执行仍回到可信领域接口，不允许模型绕开业务授权。

<a id="k04"></a>

### 4. 交付与验收路径

先定义一个可完成业务：表单输入→前端校验→请求DTO→服务端授权与校验→事务写入→响应映射→UI成功/失败。再加列表、分页、缓存、并发和异常恢复，避免一开始堆完整微服务名词。

开发环境与生产环境分别配置服务地址、凭据、代理和数据库迁移。部署验证健康、日志、回滚、备份和关键用户流程，不能只证明某个端口能响应。

面试用真实负责范围、技术选择、失败案例和可复现证据说明能力；不把教程里的架构图包装成已经上线的项目经历。

<a id="summary"></a>

## 三、知识小结

全栈闭环靠职责和契约：页面负责体验，领域服务负责规则与事务，数据库负责约束，缓存负责特定加速。认证、错误、追踪、取消和部署必须贯穿链路。

参考：[Nuxt Data Fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching)。示例按标注环境运行，版本相关能力以目标版本为准。

## 四、面试题与答案

<a id="build08-01"></a>

### BUILD08-01 [P0·工程取舍] 前端是否必须先经过BFF再访问Java？

**回答：** 不必须。需要SSR聚合、页面适配或受控网关时BFF有价值；简单安全接口可直接访问。引入一层应说明收益和新增延迟、运维及失败成本。

对应讲解：[一条业务请求的路径](#k01)。

<a id="build08-02"></a>

### BUILD08-02 [P1·原理] 客户端取消能回滚已完成数据库事务吗？

**回答：** 不能。取消是协作停止请求或任务的信号，已提交副作用需要业务补偿或状态查询。重试和幂等应由服务端协议设计，不依赖按钮停止显示。

对应讲解：[事务、取消与长任务](#k03)。

<a id="build08-03"></a>

### BUILD08-03 [P0·工程取舍] 如何防止前后端类型契约漂移？

**回答：** 统一字段和编码规则，维护OpenAPI/schema及生成类型，配运行时验证和契约测试，发布时考虑兼容。类型生成不替代数据库约束和授权。

对应讲解：[契约、身份与错误](#k02)。

<a id="build08-04"></a>

### BUILD08-04 [P1·工程取舍] 怎样证明具备Nuxt+Java交付能力？

**回答：** 展示完整业务请求、校验授权、事务、异常、部署和回滚的证据，并说明自己负责范围。能画技术栈图或跑一个成功接口不足以证明全链路能力。

对应讲解：[交付与验收路径](#k04)。
