# 真实开发流程手把手教学

## 本节目录与学习路线

1. 看清项目最终要交付什么。
2. 按依赖顺序安排需求、设计、编码、测试和发布。
3. 理解每个阶段的产物与验收方式。
4. 从用户管理开始，逐步完成登录、权限和前后端联调。

前置能力：能读懂 Java 类和方法，知道 Controller、Service、Mapper 的职责，能执行基本 SQL。写代码时允许查文档，验收标准是能实现、测试和解释一个完整功能。

## 一、先看一个实际需求

需求示例：**管理员可以新增用户、搜索用户、修改资料和停用用户，普通用户只能访问被授权的功能。**

拿到需求后，先明确业务规则：

| 问题 | 本教程的约定 |
| --- | --- |
| 用户名能否重名？ | 不能；Service 提前检查，数据库唯一约束兜底 |
| 用户名能否修改？ | 可以，但必须排除当前用户检查重名 |
| 密码如何保存？ | 创建用户时立即 BCrypt 哈希；查询响应不包含密码 |
| 修改资料能否顺便修改密码？ | 不可以；改密作为独立流程，要求额外身份校验 |
| 用户状态有哪些？ | 1 启用，0 停用 |
| 删除用户怎么处理？ | 基础 CRUD 采用物理删除；有角色关联后，明确清理或拒绝删除的策略 |
| 只有一个管理员怎么办？ | 权限阶段补上保护规则，不能删除或停用最后一个管理员 |
| 谁能操作这些接口？ | 基础阶段仅本机联调；发布前必须接入登录与权限校验 |

由此得到开发产物：

```text
需求说明：字段、权限、边界
  ↓
接口契约：URL、参数、响应、HTTP 状态
  ↓
表结构：sys_user、唯一约束、状态约束
  ↓
代码：Controller → Service → Mapper/XML → MySQL
  ↓
测试：正常用例 + 参数错误 + 重名 + 越权
  ↓
交付：代码、数据库变更、启动说明、发布与回滚步骤
```

前后端可以先约定接口，再分别开发。数据库和接口设计也允许互相调整，无需把所有表一次性设计完才开始编码。

## 二、项目约定

| 项目 | 约定 |
| --- | --- |
| 名称 | `pulse-admin-server`，单体后台管理服务 |
| 建议位置 | `E:\JAVA\projects\pulse-admin-server` |
| Java 包 | `com.example.admin` |
| Web 端口 | 本地 `8081`，避免与旧练习项目冲突 |
| 技术基线 | Java 17、Spring Boot 3.5.14、MyBatis 3.0.5、springdoc 2.8.9 |
| 数据库 | MySQL 8.4 LTS，库名 `pulse_admin` |
| 字段命名 | SQL `user_name`，Java 与 JSON `userName` |
| 主键类型 | SQL `bigint`，Java `Long`；当前自增值在前端安全整数范围内 |
| 分页参数 | `pageNum` 从 1 开始，`pageSize` 默认 10、最大 100 |
| 返回格式 | `ApiResponse<T>`；分页 `ApiResponse<PageResponse<UserResponse>>` |
| HTTP 状态 | 成功 200；错误分别使用 400、401、403、404、409、500 |

这些版本用于复现教程，不代表长期固定或最新版本。正式发布前检查依赖维护状态和安全更新，升级时进行兼容验证。不要把 Spring Boot 4、MyBatis 4 与本教程的 Spring Boot 3 配置混用。

如果将来改用雪花 ID 等超大整数，需统一将 ID 序列化成字符串，避免 JavaScript 超出安全整数范围后精度丢失。

建议目录在 `E:\JAVA` 内，可能继承外层 Git 仓库。本教程不要求重复 `git init`。如要独立版本管理，应先选择外层仓库以外的目录，例如 `E:\Projects\pulse-admin-server`。

## 三、从哪里开始，到哪里结束

```text
01 明确范围与接口契约
  ↓
02 创建项目、统一响应、异常处理、健康接口
  ↓
03 Docker MySQL、建表、MyBatis、数据库连通验证
  ↓
04 用户 CRUD、BCrypt、分页、校验、接口验收
  ↓
05 登录签发 JWT → 请求认证 → 当前用户
  ↓
06 角色/菜单 CRUD → 关联关系 → 接口权限与菜单树
  ↓
07 Redis 登录态 → 退出登录 → 停用和权限变更生效
  ↓
08 Vue 联调 → 测试 → 镜像 → 部署 → 回滚演练
```

**先完成用户 CRUD 和登录，再扩展角色菜单。** 登录本身不需要先做好完整 RBAC；授权才依赖用户、角色、菜单之间的关系。部门和字典可以复用 CRUD 模板，不是登录功能的前置条件。

## 六、一个接口具体怎么推进

以新增用户为例：

1. 写契约：`POST /system/users/add`，输入 `userName/password/nickname/email/status`。
2. 确定表约束：`user_name` 唯一，`password` 非空，状态只能为 0/1。
3. 写输入与输出：创建请求允许密码，响应不含密码。
4. 写 Mapper/XML：先能查询重名，再能插入并回填主键。
5. 写 Service：检查重名、哈希密码、入库、查询并组装响应。
6. 写 Controller：`@Valid @RequestBody` 接参并返回结果。
7. 测试：正常新增、同名新增、空密码、非法邮箱、响应有无密码。
8. 检查真实数据：库内是 BCrypt 哈希，唯一约束确实存在。

先做完这一条，再做详情、分页、修改、删除。不要等所有文件写完才第一次运行。

## 七、每次提交前检查什么

- [ ] 参数与返回值符合接口契约。
- [ ] 正常、空值、不存在、重复、分页边界均测试过。
- [ ] 参数校验在入口，业务规则在 Service，SQL 在 Mapper。
- [ ] 多次相关数据库写操作有事务，异常没有被吞掉。
- [ ] 密码不出现在响应、异常消息、日志或 Git 中。
- [ ] `sql/` 保存数据库变更，已有数据库有明确升级方式。
- [ ] 编译、测试通过，应用可以启动。
- [ ] Git 仅暂存本次功能相关文件，提交信息说明具体功能。

线上接口还必须验证 401/403 和越权场景；只在 Swagger 中点通一次不足以证明可发布。

## 八、知识沉淀

**CRUD 不是全部开发流程。** 需求和契约决定写什么，分层实现解决怎么写，测试和交付证明别人能用。

**请求对象按边界设计。** 简单查询可直接用 `@RequestParam`，需要分页、多个筛选条件时再使用查询 DTO。用户创建、改资料和返回结果的字段差异明显，因此这里保留请求与响应对象。无需给所有模块机械复制相同数量的类。

**校验和密码保护从第一版就存在。** 后续才引入更复杂的权限、缓存和发布能力。新增用户不能为了先跑通而暂存明文密码。

**框架配置允许查阅。** 常用 CRUD 和调用链应逐渐熟练；JWT、拦截器、异常体系要理解职责和边界，不要求背诵第三方库全部 API。

## 九、面试小题

1. **接到新增用户需求，先写哪个文件？** 先确认字段、唯一规则、权限和接口契约，再按请求/响应、Mapper、Service、Controller 实现。
2. **Service 查重后为什么还需要唯一索引？** 并发请求可能同时查到不存在，数据库约束防止最终写入重复数据。
3. **接口返回 200 就表示开发完了吗？** 还要检查参数、业务异常、鉴权、事务、数据正确性和部署可复现性。
4. **是否必须先完成角色菜单才能登录？** 不需要。先做用户模块和登录，再围绕身份逐步增加授权。
