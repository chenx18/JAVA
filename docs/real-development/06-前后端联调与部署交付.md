# 前后端联调与部署交付

## 本节目录与路线

1. 用 Vue 页面串起登录、资料、菜单和用户管理。
2. 区分浏览器跨域、开发代理和线上反向代理。
3. 打包后端，使用镜像在本地演练完整运行。
4. 准备生产配置、数据库升级和回滚步骤。

前置：第 05 篇的登录、后端权限和 Redis 登录态已按验收清单完成。本节给出联调与发布流程，前端 UI 可使用已有 Vue 技术栈实现。

## 一、先看最终访问链路

```text
浏览器
  ↓ HTTPS
反向代理（例如 Nginx）
  ├── /              → Vue 构建产物
  └── /api/...       → Spring Boot（移除 /api 前缀）
                         ├── MySQL
                         └── Redis
```

前端不直接连接 MySQL、Redis，也不保存数据库密码或 JWT 签名密钥。浏览器只调用后端公开的 HTTP 契约。

## 二、先完成最小前端闭环

建议按下面顺序做页面：

1. 登录页提交 userName/password，收到 token。
2. 后续请求加 `Authorization: Bearer <token>`。
3. 调用 `/system/users/info`，保存用户资料、roles、permissions。
4. 调用 `/system/users/menus`，建立菜单和允许的动态路由。
5. 用户列表页展示 records/total；翻页时发送 pageNum/pageSize。
6. 新增、编辑、删除成功后刷新列表；错误响应展示 message。
7. 退出登录时先请求 logout，再清理前端状态、token 和动态路由。

统一处理 HTTP 401：清理失效会话并回到登录页；403：展示无权限，不能误当作密码过期反复登录。请求库遇到 4xx 会进入异常分支，应从错误响应体读取 message。

示例分页响应结构：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 1,
    "pageNum": 1,
    "pageSize": 10,
    "records": [{ "id": 1, "userName": "alice", "nickname": "小林", "status": 1 }]
  }
}
```

示例仅展示部分用户字段。前端不能用 `records.length` 代替 total；当前页 10 条不等于数据库总共 10 条。

### 开发代理示例

如果使用 Vite，在**前端项目**已有的 `vite.config.js` 配置里合并 server.proxy，保留现有 plugins 等配置：

```javascript
server: {
  proxy: {
    '/api': {
      target: 'http://127.0.0.1:8081',
      changeOrigin: true,
      rewrite: path => path.replace(/^\/api/, '')
    }
  }
}
```

前端请求 `/api/system/users/list`，代理转发后端 `/system/users/list`。开发代理仅在 Vite 开发服务中生效，构建产物不会自动携带这个代理。

如果直接跨域请求，应在后端明确允许开发前端的 origin、HTTP 方法和 Authorization 头，并正确处理 OPTIONS 预检；不要用“所有请求都放行”来修复 CORS。

token 放浏览器存储时存在 XSS 窃取风险，需要按产品要求选择会话方案并防止脚本注入；如果改用 HttpOnly Cookie，还要配合 CSRF 和跨站 Cookie 策略，不能只换一个存储位置。

## 三、测试完成后再打包

除了已有健康测试，还应逐步补充以下有价值的自动化测试：

| 层次 | 应覆盖的风险 |
| --- | --- |
| Service | 唯一冲突、密码 matches、状态判断、关联写入回滚 |
| Mapper 集成测试 | 真实 MySQL 的约束、JOIN、分页与动态 SQL |
| HTTP | 输入校验、401/403/404、响应无密码 |
| 会话测试 | 退出、过期、停用、Redis 故障处理 |

数据库集成测试使用独立测试库或 Testcontainers，不连接生产库。H2 与 MySQL 在语法、排序规则和约束上可能不同，不能完全代替 MySQL 验证。

在后端项目执行：

```powershell
.\mvnw.cmd clean verify
```

保留一次完整验收记录：正常登录、普通账号越权被拒、用户 CRUD、分页、退出后 token 失效。具体账号和 token 不写入公开文档。

## 四、本地容器化演练

下面是**本机联调环境**，目标是理解 Java 从 Windows 进程变为容器后，网络地址和配置如何改变。先停止原来占用 8081 的 Java 进程。

文件：`Dockerfile`

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/pulse-admin-server.jar app.jar
USER 10001:10001
EXPOSE 8081
ENTRYPOINT ["java", "-jar", "app.jar"]
```

文件：`.dockerignore`

```gitignore
*
!Dockerfile
!target/
target/*
!target/pulse-admin-server.jar
```

文件：`src/main/resources/application-container.yml`

```yaml
server:
  address: 0.0.0.0
spring:
  datasource:
    url: ${DB_URL}
    username: ${MYSQL_USER}
    password: ${MYSQL_PASSWORD}
  data:
    redis:
      host: redis
      port: 6379
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
```

公共 application.yml 中保留 MyBatis 和 JWT 配置。container profile 不加载 dev 文件，因此不再监听容器里的 127.0.0.1。

创建应用的 Compose 补充文件：`docker-compose.app.yml`。它与前面含 mysql、redis 的 `docker-compose.yml` 合并使用：

```yaml
services:
  app:
    build: .
    image: pulse-admin-server:0.1.0
    environment:
      SPRING_PROFILES_ACTIVE: container
      SERVER_PORT: 8081
      DB_URL: jdbc:mysql://mysql:3306/pulse_admin?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&sslMode=DISABLED
      MYSQL_USER: ${MYSQL_USER:?set MYSQL_USER}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:?set MYSQL_PASSWORD}
      JWT_SECRET_BASE64: ${JWT_SECRET_BASE64:?set JWT_SECRET_BASE64}
    ports:
      - "127.0.0.1:8081:8081"
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
```

新增 container 配置后重新打包并构建：

```powershell
.\mvnw.cmd clean verify
docker compose -f docker-compose.yml -f docker-compose.app.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.app.yml up -d --build app
docker compose -f docker-compose.yml -f docker-compose.app.yml ps
docker compose -f docker-compose.yml -f docker-compose.app.yml logs --tail 80 app
```

复用原命名卷，不自动删除或重置数据库。初始化 SQL 仍只作用于空卷；第 05 篇的 RBAC 迁移必须已执行。

使用 Apifox 验证 `/health`、登录、用户列表、权限拒绝和退出流程。Swagger 在这个 profile 已关闭，访问不到文档页面不代表应用失败。

## 五、从本地演练到生产

正式环境单独创建 `application-prod.yml`，至少把服务地址与凭据外置：

```yaml
server:
  address: 0.0.0.0
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT:6379}
      password: ${REDIS_PASSWORD}
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
```

生产设置 `SPRING_PROFILES_ACTIVE=prod`，JWT 密钥通过部署环境注入。数据库 URL 按实际证书使用 `sslMode=VERIFY_IDENTITY` 等经过验证的 TLS 配置；不能直接复制本地明文连接 URL。如果 Redis 要求 TLS，也应在配置中启用对应 SSL 参数并校验证书。

发布前逐项落实：

- 只由反向代理暴露公网 HTTPS，MySQL、Redis 保留在受保护的内部网络。
- 使用应用专用的最小权限数据库账号，生产不使用 root；建表迁移使用独立受控账号。
- 初始管理员通过受控初始化建立，登录、权限、失败限制等功能已测试。
- 密钥、密码由运行环境或密钥管理注入，不打进镜像或前端包。
- SQL 增量迁移有顺序记录；应用回滚与表结构兼容性已确认。
- 镜像使用明确版本标签，保留上一版；需要严格复现时固定镜像 digest。
- 日志、磁盘、错误率、数据库备份和恢复方法有负责人及操作记录。
- 应用探针区分存活与就绪，`/health` 为 200 不等于全部依赖可用。

真实部署还需要服务器地址、域名、证书、网络和备份策略。本教程不假定这些已经存在；到发布阶段根据实际环境填写，不能仅运行本地 Compose 就宣布上线完成。

## 六、实际发布与回滚顺序

```text
完成代码审查与测试
  ↓
生成带版本的镜像，记录对应 Git 提交
  ↓
备份数据库并验证可恢复
  ↓
执行向前兼容的数据库迁移
  ↓
部署新镜像和配置
  ↓
验证存活、依赖、登录、权限和核心写操作
  ↓
观察日志和错误率，再宣布发布完成
```

失败时先定位应用还是数据库问题。旧镜像只能回滚应用，不能自动还原表结构；破坏性迁移需要另行恢复计划。不要把删除卷、重建库当作回滚办法。

## 八、知识沉淀与面试小题

1. **开发代理能解决线上跨域吗？** 不能。Vite 代理只在开发服务运行，线上需要反向代理或明确的 CORS 配置。
2. **为什么容器里不能用 localhost 访问 MySQL？** localhost 指向当前容器；同 Compose 网络使用服务名 mysql。
3. **depends_on 保证数据库一直正常吗？** 不保证；它可控制启动时等待健康，运行期间仍需超时、故障处理和监控。
4. **镜像回滚是否等于系统回滚？** 不等于。数据库结构、数据、缓存与配置也影响兼容性。
